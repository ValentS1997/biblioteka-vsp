# Глава 11 — cheatsheet

**Основание:** только RAG `p0175:c01–p0192:c01` (PDF 175–192). Описаны **авторские нормы оформления Bash**, а не проверенная конфигурация пользовательского репозитория.

## Symptom / problem framing

Код работает, но трудно читается, содержит повторения, неясные переменные, недокументированные флаги и неявные зависимости; при последующих изменениях растёт риск ошибок. Авторы предлагают создать **командное руководство по стилю**, соблюдать KISS и DRY и документировать причины решений, особенно опасных. [PDF 175–179]

## Read-only checks

- Проверьте на **тексте** выбранного сценария: наличие заголовка, читаемых имён, комментариев с назначением функций, обработки `-h`/ошибок и ясного формата строк. Это проверка по критериям PDF 178–189, не утверждение о файлах пользователя.
- `grep -P '^\s*function '` **упомянут** как способ найти объявления функций, но его доступность и результат в среде пользователя: **[Needs confirmation]**. [PDF 183]
- `python -c "import this"` авторы приводят для вывода «Дзен Python»; это дополнительная справочная демонстрация, не средство проверки Bash. [PDF 177]
- ShellCheck упомянут как linter, но его рекомендации не всегда совпадают с предпочтениями авторов, и доступность инструмента **[Needs confirmation]**. [PDF 191–192]

## Interpretation

- Руководство по стилю — **договорённость**, а не набор бесспорных синтаксических законов. При сопровождении проекта лучше соблюдать уже принятую норму. [PDF 175, 179, 190]
- Размещайте `local my_input` отдельно от `my_input="$(some-command)"`, чтобы объявление не маскировало неуспешный код возврата. [PDF 183–184]
- Предпочитайте `[[ ... ]]` и `$(...)` для Bash, но если требуется переносимость на другую оболочку, рекомендации необходимо переработать. [PDF 177, 187]
- Шаблон сценария с `PROGRAM=${0##*/}` и секцией функций **содержит заглушки**. Его нельзя считать законченным исполняемым сценарием. [PDF 188–189]

## Next action

Выберите правила для проекта по разделам главы (читаемость → комментарии → имена → функции → кавычки → форматирование → синтаксис → обработка ошибок), зафиксируйте их в одном руководстве и соблюдайте при изменении кода. Сверяйте с существующими соглашениями, учитывайте совместимость оболочек и поясняйте исключения. [PDF 175–190]

## Modifying action

`readonly` и `declare -r` меняют атрибуты переменных; `set -euo pipefail` меняет обработку ошибок и неопределённых переменных; `IFS` меняет разбиение слов; `source` **исполняет** подключаемый конфигурационный файл, а не просто читает его текст. Примеры `rm -rf` с неопределённой переменной даны авторами как **опасные антипаттерны**, их не выполнять. [PDF 176–178, 182, 188]

## Verification / acceptance checks

Сравнить предлагаемое соглашение с текущим стилем проекта, отдельно проверить поведение затронутых сценариев, совместимость shebang и доступность внешних средств. Чисто косметические преобразования не доказывают корректность логики. Реальные тесты, окружение, целевой shell и вывод команд **[Needs confirmation]**.

## Rollback

В RAG отсутствует универсальный сценарий отката преобразования репозитория или смены политики `set`, `IFS` и `readonly`. Исходное состояние/версия и порядок восстановления: **[Needs confirmation]**. Самостоятельные массовые изменения файлов и запуск опасных примеров в этой работе не выполнялись.
