# Приложение «Руководство по стилю» — cheatsheet

**Источник:** только RAG `p0193:c01–p0202:c01`, PDF 193–202. Правила ниже — **стилевые предпочтения авторов Bash Idioms**, не независимая проверка чьей-либо кодовой базы.

## Symptom / problem framing

Неясные имена, повторения, громоздкие выражения, пропущенные комментарии, разнородные отступы и ошибки использования команд затрудняют сопровождение сценариев. Приложение сводит рекомендации главы 11 в компактный свод правил для написания собственного руководства. [PDF 193–195]

## Read-only checks

- По тексту проверять заголовок, наличие разделов `-h`/помощи, ясность имён, оправданность комментариев и единообразие отступов. Это **критерии аудита**, а не измерение пользовательского кода. [PDF 194–199]
- `grep -P '^\s*function '` приведён авторами как способ отыскать объявление вида `function Name {`; доступность и результат не установлены. [PDF 196]
- `[ -x /path/to/tool ]` приведено как проверка доступности внешней программы; `/path/to/tool` — **заглушка**. [PDF 200]
- Посмотреть, указаны ли коды `exit` и выводятся ли сообщения об ошибках в STDERR. Фактические результаты: **[Needs confirmation]**. [PDF 200]

## Interpretation

- Это **сжатая версия главы 11**, а не отдельная двенадцатая глава. Каждая рекомендация имеет контекст выбора; например, длинные ключи удобнее читать, но их переносимость вне GNU/Linux требует проверки. [PDF 193–195]
- `local my_input`, затем `my_input="$(some-command)"` рекомендуются раздельно, чтобы объявление не маскировало неуспешный статус подстановки команды. [PDF 197]
- Авторы предпочитают `$(...)` обратным кавычкам, `[[ ... ]]` обычным `[ ... ]` для Bash, а для арифметики — `(( ... ))` и `$(( ... ))` вместо `let` и `expr`. [PDF 199–200]
- Цепочку `[[ expression ]] && block || block` не рекомендуют использовать вместо полноценного `if`: результат первого блока может влиять на последующую ветвь. [PDF 200]
- Исключение о regex в источнике написано как `~=`; **не исправлять молча** — [source-findings.md](source-findings.md). [PDF 198]

## Modifying action

`source` **исполняет** подключаемый файл; `readonly`/`declare -r` меняют свойства переменных, `set -euo pipefail` — политику ошибок, `IFS=$'\n\t'` — правила разбиения. Примеры с `exit` меняют поток исполнения, журналирование в syslog создаёт записи вне shell. Реальные эффекты в пользовательской системе и права доступа **[Needs confirmation]**. [PDF 194–200]

## Verification / acceptance checks

Проверить, что изменения оформления не меняют смысл кавычек, подстановок, `IFS`, окружения или обработки ошибок. Проводить проверку в корректном Bash, отдельно сверяя shebang, статус команды и читаемость; в RAG не приведено результатов тестов читателя. **[Needs confirmation]**.

## Rollback

В приложении нет универсальной процедуры возврата для изменённых скриптов, состояний `set`/`IFS`/`readonly` и записей журналов; план восстановления конкретного проекта: **[Needs confirmation]**. Никаких изменений пользовательских сценариев в этой работе не выполнялось.
