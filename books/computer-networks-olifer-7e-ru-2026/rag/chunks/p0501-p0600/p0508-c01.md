Конструкция условий протокола О F позволяет очень тонко выделить поток данных и тем
самым обеспечить его индивидуальную обработку коммутатором. Сравните это с возмож

ностями стандартных коммутаторов и маршрутизаторов, которые считают одним потоком
все пакеты, у которых совпадает лишь один признак - адрес назначения.
Набор возможных действий некоторого правила включает в себя передачу пакета на один
из выходных портов коммутатора и операции по изменению значений полей заголовка
пакета. Например, для того чтобы пакеты потока были переданы на порт 8 и чтобы при
этом номер VLAN был изменен на 1002, а МАС-адрес назначения -  на bc:30:7e:d4:5d:8f,
достаточно определить набор из трех действий:

Actions:
{Ротt=8; VLAN ID = 1002, МАС Dst = bc:30:7e:d4:5d:8/}

Счетчики позволяют коммутатору измерять статистические характеристики потока: его
интенсивность (количество поступивших пакетов за секунду) и продолжительность суще
ствования. Коммутатоr "акже должен поддерживать агрегатные счетчики для каждого порта.
Счетчики обновляются при поступлении каждого нового пакета в коммутатор, но непосред
ственно на обработку пакетов не влияют. Контроллер SDN может запросить у коммутатора
значения счетчиков и на основании этих данных принять решение, например, заблокировать
некоторый подозрительный поток, если его интенсивность слишком велика.
Для принятия решения контроллеру нужно знать топологию сети и для этой цели был
разработан протокол BDDP (Broadcast Domain Discovery Protocol}, с помощью которого
устройства сети обнаруживают соседей и сообщают об этом контроллеру.
Помещение всех правил, учитывающих всевозможные сочетания условий, в одну таблицу
не является масштабируемым решением, поэтому устройства OpenFlow поддерживают
конвейер таблиц, в который может входить до 255 таблиц. При обработке пакета устрой
ство последовательно просматривает все таблицы конвейера, если только в одной из них
не содержится правило выхода из конвейера.

Таблицы не хранят информацию о состоянии потоков данных (кроме специальной таблицы
счетчиков, которые подсчитывают скорость потока для его динамического профилиро
вания). Состояние потока может переноситься самими пакетами потока в специальном
дополнительном поле заголовка - поле метаданных.
У протокола OpenFlow имеются несколько проблем, препятствующих его широкому при
менению. Одной из главных является проблема унификации конвейера таблиц. Другими
словами, проблемой является создание единой модели сетевого устройства, которой бы
следовали все производители сетевого оборудования, желающие выпускать оборудова
ние SDN.
Решением этой проблемы явилось создание программируемых протокольно-независимых
процессоров Р4, которые позволяют создавать нужную модель сетевого устройства за
счет программирования процессора этого устройства. Таким образом, вместо нахождения
единой унифицированной модели коммутатора предлагается коммутатор, характеристики

которого можно изменить по желанию проектировщика сети, а потом уже управлять им
