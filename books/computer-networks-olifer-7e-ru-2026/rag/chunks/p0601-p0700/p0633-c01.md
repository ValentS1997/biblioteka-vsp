Пакет передается следующему хопу, которым является узел назначения LER5.
В первом примере мы в списке SR-Policy задали путь, совпадающий с путем SPF, - и он
был соблюден. Можно задать такой путь и короче, только указав финальную метку, в на
шем случае 16005 - результат был бы тот же.

Теперь посмотрим, как задать ТЕ-путь, отличающийся от SРF-пути. Пусть мы хотим по
слать трафик к узлу LER5 по длинному маршруту, через узлы LSR4. Составить список
меток для соответствующего ТЕ-пути можно двумя способами.
Первый - использовать в списке только идентификаторы узлов Node-SID и указать все
промежуточные узлы ТЕ-пути: [ 16001, 16002, 16003, 16004, 16005]. Для топологии нашего
примера такой список будет работать. Узел LSR2, удалив собственную метку из стека (дей
ствие Рор), делает активной следующую метку 16003, поэтому он передает пакет не узлу
LER5, а узлу LSR3, точно следуя инструкциям из списка SR-Policy. Этот способ можно
оптимизировать, если заметить, что после посещения узла LSR3 ТЕ-путь к узлу LER5 со
впадает с SРF-путем к этому узлу. Поэтому не обязательно указывать в списке SR-Policy
метки всех промежуточных узлов. Достаточно тех, которые указывают на •сворачивания•
с SРF-пути на ТЕ-путь. Поясним эту мысль примером: в списке ТЕ-пути к узлу LER5
можно оставить только промежуточный узел LSR3, те есть сократить список до [16003,
16005], и результат продвижения пакета будет тот же самый.
Второй способ состоит в использовании меток связей Adj-SID в списке SR-Policy для
ТЕ-пути. Например, предыдущий список можно представить так: [16002, 24023, 16005].
Вторая метка списка является меткой связи LSR2 с LSR3 через интерфейс ge-0/1, и она
вынуждает узел LSR2 передать пакет узлу LSR3, а не LER5. Применение меток Adj-SID
в нашем примере не является обязательным, список, состоящий из последовательности
меток узлов Node-SID, выполняет ту же работу. Однако существуют топологии, для кото
рых применение меток Adj-SID является единственным способом задать требуемый ТЕ
путь. Представим, что между LSR2 и LSR3 имеются две связи, помеченные метками 24023
и 24123, и мы по какой-то причине хотим задать путь, проходящий через одну из них. Без
метки Adj-SID эту задачу решить невозможно, узел LSR2 не будет точно знать, по какой
из связей передавать пакет. Задание в списке SR-Policy метки Adj-SID решит эту задачу,
список будет выглядеть так: [16002, 24123, 16005].
Обычной практикой является применение меток обоих типов для задания ТЕ-пути.
Теперь рассмотрим варианты архитектуры сети SR-MPLS, отличающиеся друг от друга
типом элемента сети, вычисляющего ТЕ-путь и устанавливающего его в первый узел пути,
то есть в пограничный маршрутизатор сети.
В первом варианте это делает каждый пограничный маршрутизатор LER. Для этого он
собирает топологическую информацию о графе сети, включающую ТЕ-метрики и значе
ния Node-SID и Adj-SID каждого маршрутизатора и каждой связи, используя протокол
OSPF или IS-IS с соответствующим расширениями. Затем этот маршрутизатор запускает
алгоритм CSPF для нахождения ТЕ-пути и формирует список меток SR-Policy для этого
пути, а также формирует запись в таблице FТN, отображающую класс FECn на данный
путь. При приходе пакета из класса FECn, пограничный маршрутизатор помещает в его
заголовок стек меток SR-Policy и отправляет в путь.
