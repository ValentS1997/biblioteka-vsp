## Главный принцип

**Чтобы Ethernet стал операторской транспортной технологией, одного frame forwarding недостаточно: нужны изоляция клиентских адресных пространств, управляемые/отказоустойчивые пути и полноценный OAM.** Глава показывает, как Carrier Ethernet добавляет к обычному Ethernet service boundaries, continuity/fault monitoring, QoS measurement и provider-specific VLAN encapsulation.

## Что важно вынести

1. **Carrier Ethernet — это не просто “длинный Ethernet-кабель”.** Source рассматривает Ethernet как WAN service и как внутреннюю L2 transport technology провайдера. `p0351:c01`–`p0352:c01`.
2. **UNI — граница пользователь ↔ провайдер.** Пользователь получает Ethernet interface/service, а внутренняя реализация провайдера может быть отдельной транспортной системой. `p0351:c01`.
3. **Классический Ethernet не удовлетворяет операторским требованиям автоматически.** Source выделяет reliability, fault tolerance, scalability и manageability. `p0352:c01`.
4. **Flat customer MAC/VLAN state плохо масштабируется в provider core.** Provider should not depend on globally unique customer VLAN IDs or learn every customer endpoint indiscriminately. `p0352:c01`–`p0353:c01`.
5. **STP/RSTP недостаточны для operator-style traffic engineering.** Source отмечает слабый контроль пути и сравнительно медленную failover reaction against transport-network expectations. `p0353:c01`.
6. **OAM закрывает visibility gap Ethernet.** Needed capabilities: reachability/continuity, fault localization, delay and loss measurement. `p0353:c01`–`p0354:c01`.
7. **CFM monitors logical Ethernet connectivity using MEP/MIP.** MEP generate/receive CCM; MIP observe transit control traffic and help localize the failing segment. `p0354:c01`–`p0356:c01`.
8. **CFM measurements are active.** CCM frames are generated by the protocol; they are not passive observation of user traffic. `p0354:c01`.
9. **Maintenance domains are hierarchical.** Different administrative domains use different levels so operator/provider/customer can monitor the same end-to-end service independently. `p0356:c01`–`p0357:c01`.
10. **Y.1731 extends monitoring toward performance.** Source lists one-way delay, delay variation and frame loss measurements between maintenance endpoints. `p0357:c01`.
11. **Physical Ethernet remote loopback is disruptive.** Source explicitly states that loopback testing breaks normal service and should be performed during a maintenance window. `p0357:c01`.
12. **E-LMI exposes service state to the CE side.** A customer edge device can query status and service parameters such as VLAN mapping/capacity information from the provider edge. `p0358:c01`.
13. **Provider Bridge separates VLAN namespaces using stacked VLAN identifiers.** Provider edge inserts S-VID outside customer C-VID; core forwarding uses the provider tag; egress removes it. `p0358:c01`–`p0359:c01`.
14. **Q-in-Q does not fully solve provider scaling.** Source lists continued customer-MAC learning, 12-bit S-VID service-space limits and spanning-tree traffic-engineering constraints. `p0359:c01`–`p0360:c01`.
15. **PBB is presented as stronger address-space separation through Ethernet-in-Ethernet encapsulation.** Source then states that large provider networks commonly use MPLS-based approaches instead; this is preserved as an edition/source statement. `p0360:c01`.
