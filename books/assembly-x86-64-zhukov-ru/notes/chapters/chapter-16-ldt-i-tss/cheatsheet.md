# Глава 16 — operational cheatsheet: LDT, TSS и переключение задач

**Provenance:** canonical RAG PDF 269–286, листинги 16.1–16.8. Ни DOS/Bochs, ни реальное оборудование не запускались.

## Symptom → trace path

Сегмент по селектору не находится, `LDTR.valid=0`, LLDT ошибочно запущена в real mode, TSS-переход приводит к GP, контекст сопрограммы испорчен или тест скорости даёт необычные результаты. Сначала проверить **активный режим → GDT descriptor LDT/TSS → TI селектора → LDTR/TR → hidden descriptor cache → EIP/ESP/сегменты TSS → код отказа**. Не изменять систему в ходе чтения исходника.

## 1. LDT (p. 269–272)

| Объект | Смысл |
|---|---|
| `GDT` | Системный дескриптор LDT указывает на локальную таблицу (8-байтовые записи) |
| `GDTR` | Линейная база GDT и её предел |
| `LDTR` | Селектор LDT-дескриптора **в GDT**, загружается `LLDT` в protected mode |
| TI, бит 2 | `0` → GDT; `1` → LDT; остальные биты задают индекс/уровень |
| `LLDT 0` | LDT не действует; дальнейшая попытка доступа по TI=1 вызывает отказ |
| LDT selector 0 | В учебной LDT дескриптор с нулевым *смещением* можно использовать: не путать с null selector GDT |

Листинг 16.1 показывает заполнение 80 точек на второй строке текстового экрана через дескриптор LDT. В 16.2 автор наблюдает `fetch_raw_descriptor: LDTR.valid=0` при отсутствии LDT и `LLDT: not recognized in real or virtual-8086 mode`, если команду выполнить до перехода в protected mode.

## 2. Программный контекст (p. 272–276)

- В `sw.asm` два стека размещены внутри PSP по **128 байт**, с вершинами у `0100h` и `0080h`. Это изменение PSP опасно вне одноразового DOS-сеанса.
- Набор контекста: 8 регистров общего назначения, ES, FLAGS, CS, IP. В примере `DS/SS/FS/GS` не меняются между сопрограммами; FPU/MMX исключены.
- При прерывании сохраняются FLAGS, CS, IP, затем `push es; pushad`. Сохранённый SP обменивается с `next_sp`, после чего `popad; pop es; iret` продолжает другую сопрограмму.
- `POPAD` игнорирует сохранённый слот ESP; поэтому нельзя рассчитывать на восстановление стека одним `POPAD`.
- Вновь создаваемой сопрограмме заранее вручную приготовлен образ стека **как после прерывания**, её IP направлен на тот же `thread`; различаются значения EAX и ES.

## 3. Аппаратный контекст (p. 276–285)

- TSS хранит `EIP/EFLAGS`, 32-битные регистры, сегментные селекторы; дополнительные поля — `CR3`, prior link, `LDT` selector, стеки CPL 0–2, offset I/O bitmap.
- Дескрипторы TSS — системные записи GDT. `LTR` выбирает текущую задачу в `TR`. Far JMP к другому TSS вызывает аппаратный переход в `hw1/hw2`.
- **Отказ на реальном ПК:** в примере `hw2.com` `FS/GS` наследуют значения FreeDOS, не подходящие для GDT; Bochs этого сбоя не продемонстрировал. Исправление автора — нулевые неиспользуемые FS/GS в `hw3.asm`.
- Два начальных ESP можно сделать одинаковыми лишь если **стек пуст** при переключении; иначе задачи перезапишут оставленные друг другом данные.
- Тип TSS Available `1001`, Busy `1011`. Попытка перехода на уже занятой дескриптор — диагностическая ошибка.
- Для `CPL=0` проверку I/O bitmap автор откладывает: ограничение доступности портов относится к CPL выше 0.

## 4. Бенчмарк — ограниченная доказательность

| Метод | 10 млн итераций, авторский ПК | Указанная автором длительность |
|---|---:|---:|
| Software `sw.com` | 72 с | 7,2 мкс |
| Hardware TSS `hw3.com` | 39 с | 3,9 мкс |

**Условия:** Core 2 Duo E8400, 3 GHz (p. 284, 286); software-вариант не сохраняет часть сегментных регистров и арифметическое состояние. Нельзя выдавать эти времена за измерения в данной сессии или современную производительность.

## Read-only verification / preflight

Сверить по RAG расположение структуры TS и TSS, наличие нужных дескрипторов GDT и нулевых FS/GS, различить TI и TSS Busy, проверить неизменяемость DS/SS в программной модели и границы сравнения времени. Рискованные эксперименты (LLDT в неверном режиме, удаление GDT-descriptor, изменение IVT/FS/GS, повторный переключатель) требуют полностью изолированного образа и восстановимого состояния.
