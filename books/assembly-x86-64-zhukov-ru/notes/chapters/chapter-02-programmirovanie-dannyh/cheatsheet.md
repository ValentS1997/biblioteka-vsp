# Глава 2 — практическая шпаргалка

**Источник:** RAG PDF 21–30, `p0021:c01`–`p0030:c01`. Только книга Жукова; действия относятся к описанной в ней среде a86/FreeDOS.

## Symptom / problem framing

Нужно создать строго заданный набор байтов либо корректный BMP **без машинных команд**. Основные проблемы: ошибки строк, неопределённые имена, несоответствие ожидаемого и фактического объёма данных, переполнение COM и несогласованная палитра/растр.

## Baseline / context

- `a86 исходный_файл.8` транслирует `db/dw/dd/equ`; успешные выходы `.com` и `.sym` (p. 21–22).
- `db` — байты; `dw` — слова; `dd` — двойные слова; `equ` — константы без выделения места (p. 22–23, 29).
- `dup` создаёт повторы; `$` — текущее значение счётчика адресов, изначально 256 для примера (p. 23).
- В числовых многобайтовых значениях у Intel младший байт расположен первым (p. 25).
- Для BMP исходные параметры: 64×32, 1 бит/пиксель, два элемента палитры; пиксели описаны растром `Pixels` (p. 26–27).

## Read-only checks

1. По исходному тексту проверить ожидаемую длину `sz`, выражение `$ - seq`, число повторов `dup`.
2. Сравнить байты с эталонным `.dat` через `fc /b var_<n>.com var_<n>.dat` после трансляции (p. 25).
3. Проверить, что имена `fast` и `tiny` не остались в `.und` после исправления (p. 22).
4. Для BMP сверить вычисленные `Colors`, `bytesPerLine`, `byteCount`, `Palette` и `Pixels` с фактически заданными данными (p. 26–28).

## Interpretation

| Наблюдение | Значение по книге |
|---|---|
| `#ERROR 32: Bad String` | Незакрытая строка в `test1.8`; `^` показывает позицию (p. 21–22). |
| Файл `.und` | Неопределённые `fast`, `tiny`, которые a86 не отметил в исходном тексте (p. 22). |
| `Conflicting multiple definition` | Повторное `equ` вычислило другое значение: несоответствие объёма или структуры (p. 23, 28). |
| `Object Overflow` | Программа попыталась сформировать COM чрезмерного размера из-за ошибочного выражения (p. 24). |
| BMP отвергает повторные `equ` | Не совпадает ожидаемая палитра, кратность четырём или размер растра (p. 27–28). |

## Next action

Исправлять сначала исходные определения размера и порядок операндов; затем заново транслировать, сравнить байты и визуально проверить BMP утилитой `bitmap`. Команда запуска BMP из книги: `a86 bmp_0.8 TO bmp_0.bmp`, далее `bitmap bmp_0.bmp`, затем `F5` для цветного отображения (p. 26).

## Modifying action

- **Трансляция `a86` меняет файловое состояние:** создаёт результат, а при ошибке может переписать исходный `.8`, создать `.old` или `.und` (p. 21–24). Вначале сохранить копию исходника.
- Редактирование `dup`/палитры/`Pixels` меняет генерируемые данные. Перед правкой зафиксировать исходные параметры и ожидаемые размеры.
- **Запуск `.com`, содержащего только данные, недопустим по источнику** (p. 22).

## Verification / acceptance checks

1. Успешная трансляция без `#ERROR`, появление нужных выходных файлов.
2. Сопоставление `.com` с эталонным `.dat` через `fc /b` для задач последовательностей (p. 25).
3. Проверка значений `equ` повторным определением; ошибки размеров должны обнаруживаться до использования файла (p. 23, 28).
4. BMP открывается программой `bitmap`, а ожидаемая картинка видна после `F5` (p. 26).

## Rollback

- При внезапном повреждении исходника из-за механизма сообщений a86 восстановить `.8` из предварительно созданного `.old` — стратегия непосредственно указана в p. 24; конкретная команда копирования **[Needs confirmation]**.
- При экспериментальных изменениях BMP вернуть исходные параметры и удалённые/добавленные строки (p. 28); команды восстановления **[Needs confirmation]**.
- При потере эталонного файла порядок его восстановления не приведён: **[Needs confirmation]**.

## Формулы памяти и BMP

- `bytesPerLine = iWidth / (8 / bitsPerPixel)`; `byteCount = bytesPerLine × iHeight` — как в листинге 2.8 (p. 26).
- При 64×32×1: 8 байт/строка, 256 байт растра. Это вычисление по формулам главы.
- `Colors = bit bitsPerPixel` — оператор a86 `bit` задаёт единицу в указанном бите (p. 26, 30).
- Линии BMP читаются снизу вверх, биты каждого байта — от старших к младшим (p. 27).
