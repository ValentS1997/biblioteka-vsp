# Глава 20. Переход в 64-битовый режим

**Книга:** А. В. Жуков, «Ассемблер и программная модель процессоров x86/64», инв. 0017, часть III «64-битовые режимы».  
**Источник:** canonical RAG PDF **331–340** (`rag/chunks/p0301-p0400/p0331-c01.md`–`p0340-c01.md`); следующая глава 21 «Особенности 64-битового режима» начинается с PDF **341**.  
**Приёмка:** `rag/acceptance.yaml: ACCEPTED`, manifest `READY_WITH_KNOWN_LIMITATIONS`; source SHA256 `f65a7ec88148cb29d7e75d1ce34ef14c3a7ddf8af264ec7abcf9b8a0437220c2`.  
**Источник истины:** `rag_only`, никакого прямого чтения PDF, внешних источников или подстановки знаний модели.

## Что изменяется

По изложению автора в 64-битовом подрежиме long mode сегментная модель **почти** исчезает: базовые адреса обычных сегментов нулевые, сегментные пределы не проверяются. **Исключение — FS/GS**, которые могут иметь ненулевую базу (примечание 1, p.339). Разделение адресных пространств зависит от страничного преобразования (прим. 2). Для кода важны атрибуты дескриптора `P/DPL/L/C/D`; код с `L=1, D=0` 64-битный, код с `L=0` сохраняет режим совместимости. При `L=1` размер данных по умолчанию остаётся **32 бита**, 64-битные операнды используют REX (прим. 3, p.339).

## Шесть ключевых выводов

1. **Плоская адресация** уменьшает значимость base/limit обычного кодового дескриптора, но не отменяет GDT, селекторы или страничную адресацию. Поля `FS/GS` сохраняют оговорённое исключение (p.331, 339).
2. **Вход в 64-битный код** связан с переключением CS на дескриптор с `L=1`, а не просто с наличием 64-битных регистров. Показанный в 20.3 прыжок с `long_mode` переводит исполнение из совместимости в `use64` (p.334–335). **Подготовительные действия из пропусков извлечения RAG не восстанавливаются по памяти**.
3. **Возврат к совместимости** в 20.4 производится косвенным `jmp far qword [addr80]`, потому что непосредственный far-переход с константным адресом в 64-битном коде источник считает неподдерживаемым (p.335–336). Примечание 12 объясняет: при нулевом селекторе из эксперимента обратного переключения не происходит, хотя переход приводит к адресу.
4. **64-битный call gate** содержит расширенный адрес и занимает **16 байт** (p.331, 337); `retfq` возвращает 64-битные offset и selector, оба сохраняются в стеке с 64-битной разрядностью (p.337 и прим.14, p.340).
5. **Вложенный gate-вызов** использует косвенный far-call внутри `use64`, тогда как прямое указание gate в 20.6 остаётся в коде совместимости. `iter=8` уменьшается перед рекурсией, `loop` в 64-битном режиме по умолчанию использует **RCX** (p.338–340).
6. **Фиксированная точка**: автор предлагает делить 64-битное слово на старшие 32 бита целой и младшие 32 бита дробной части (p.339). Его оценки точности и ускорения по отношению к floating-point приведены как **авторские предположения**, а не подтверждены измерениями.

**Критический риск:** `ld0` изменяет нижнюю память с IVT и запрещает IRQ; другие образцы обращаются к видеопамяти и могут зависнуть в циклах.
