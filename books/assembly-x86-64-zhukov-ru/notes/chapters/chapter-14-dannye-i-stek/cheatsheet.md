# Глава 14 — шпаргалка: данные, стек, unreal, A20

**Основание:** canonical RAG PDF **235–252**, листинги 14.1–14.11. Это аналитическая справка, а не исполненный тест.

## Карта диагностики

При `write beyond limit`, `expand down` или ошибке загрузки SS проверить **селектор → дескриптор → base/limit/G/E/B/RW/DPL → эффективный адрес → права/stack pointer → внешние ограничения A20**.

| Область | Инвариант | Основание |
|---|---|---|
| Локальный DS | Base = линейная база COM, limit = `end1−1` | 14.1, p.235–237 |
| Плоский ES/FS | Base = 0, 4-Гбайтный предел при G=1 и максимальных полях limit | 14.1/14.5, p.236,241 |
| Expand-down | E=1: нижняя граница исключается, верхняя зависит от B | 14.2–14.3, p.238–239 |
| B=0 | Верхний адрес `0xFFFF`; стековые адреса используют SP | p.239–240, прим. 4 p.250 |
| B=1 | Верхний адрес `0xFFFFFFFF`; стековые адреса используют ESP | p.239, прим. 4 p.250 |
| Stack segment | RW и `CPL=DPL=RPL` обязательны для загрузки SS | 14.4/14.11, p.240,249–250 |
| Unreal | Скрытая часть FS сохраняет ранее загруженный плоский дескриптор | 14.5, p.241–242 |
| A20 | Доступ `0x100000` может отражаться на физический 0 при блокировке линии | 14.5–14.7, p.242–244 |
| Сегмент данных | Доступ при `max(CPL,RPL) ≤ DPL` в авторском опыте | 14.8, p.244–245 |

## Read-only контроль

1. Проследить в 14.1, почему исходная командная строка PSP читается через локальные DS:ESI, а видеопамять — через плоский ES:EDI. Авторский `jcxz` дизассемблируется как `jecxz` при 32-битном адресном режиме (p.236–237).
2. В 14.2 `STD/STOSB` уменьшают EDI; в 14.3 `CLD/STOSB` увеличивают EDI. Попытка доступа к `0x10000` при E=1/B=0 нарушает верхнюю границу (p.238–239).
3. В 14.4 ошибка базового адреса `dsc6` приводит к записи в неверное место: наличие fault по SS-limit **не подтверждает** правильность базы (p.240).
4. На A20-тесте сравниваются логические адреса 0 и `0x100000`. Автор различает представление CPU и физическую память в отладчике Bochs; состояние A20 **не универсально** (p.243–244).
5. При CPL=0, DPL=2 и RPL от 0 до 3 отказывают только на RPL=3; это проверка сегмента данных, **не** правила SS (p.244–250).
6. Для вывода GDT в `_dsc.asm` до перехода используется очистка экрана через BIOS, а в protected mode — прямой вывод через flat ES; экран 200 позиций по 10 знако-мест (p.245–249).

## Экспериментальные отклонения

- Слишком широкий доступ у конца локальных данных → fault; с G=1 и малым limit можно вместо fault испортить соседний код (p.237).
- Продолжение записи под нижний limit E=1 → `write beyond limit, r/w expand down` (p.239).
- Неинициализированная база стека и неправильный RW ведут к разным эффектам (p.240–241).
- Настройка RPL> DPL для данных или несовпадение уровней SS вызывает отказ загрузки селектора (p.244–250).

## Риски, preflight и восстановление

Никакого исполнения: изменения A20, физического нулевого адреса, `0x100000`, IVT/PSP, SS и GDT относятся к высокорисковым экспериментам. Если когда-либо исследовать их, изолированная VM со снимком **до** опыта и возможностью полнейшего перезапуска обязательна. Автор не даёт универсального алгоритма безопасного отката аппаратного состояния — **[Needs confirmation]**.
