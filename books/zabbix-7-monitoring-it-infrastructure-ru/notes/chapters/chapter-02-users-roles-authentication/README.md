## Основная модель доступа

**Это три связанных, но не тождественных задачи.**

1. **Группа пользователей** определяет, какие группы хостов/шаблонов могут читаться или изменяться; пример Buying and Inventory имеет **Read**, а Networking / Infrastructure — целевые права на свои объекты ([p0061](../../../rag/chunks/p0001-p0100/p0061-c01.md)–[p0064](../../../rag/chunks/p0001-p0100/p0064-c01.md)).
2. **Роль пользователя** определяет доступные разделы интерфейса, API, сервисы и действия. Пример **User+ role** использует тип `Admin` и выборочно разрешает функцию Maintenance, а не становится автоматически эквивалентом обычного пользователя с Read-only ([p0065](../../../rag/chunks/p0001-p0100/p0065-c01.md)–[p0071](../../../rag/chunks/p0001-p0100/p0071-c01.md)).
3. **Аутентификация** (встроенная, SAML, LDAP) проверяет личность и управляет паролями. Без JIT аккаунт и права в Zabbix должны быть созданы заранее; с JIT сопоставление групп/атрибутов создаёт пользователя при входе ([p0077](../../../rag/chunks/p0001-p0100/p0077-c01.md), [p0085](../../../rag/chunks/p0001-p0100/p0085-c01.md)–[p0086](../../../rag/chunks/p0001-p0100/p0086-c01.md), [p0091](../../../rag/chunks/p0001-p0100/p0091-c01.md)–[p0092](../../../rag/chunks/p0001-p0100/p0092-c01.md)).

## Разбор авторских примеров

- **Networking:** доступ к шаблонам сетевых устройств, группа `Networking`; `s_network` — Super admin, `y_network` — Admin ([p0063](../../../rag/chunks/p0001-p0100/p0063-c01.md), [p0074](../../../rag/chunks/p0001-p0100/p0074-c01.md), [p0077](../../../rag/chunks/p0001-p0100/p0077-c01.md)).
- **Infrastructure:** группа `Infrastructure`, группа хостов Linux servers; `r_infra` демонстрационно назначен Super admin ([p0063](../../../rag/chunks/p0001-p0100/p0063-c01.md), [p0075](../../../rag/chunks/p0001-p0100/p0075-c01.md)–[p0077](../../../rag/chunks/p0001-p0100/p0077-c01.md)).
- **Buying and Inventory:** `Read` к двум группам объектов; `e_buy` — роль User или User+; **User+ может разрешить создание периодов обслуживания** ([p0064](../../../rag/chunks/p0001-p0100/p0064-c01.md), [p0076](../../../rag/chunks/p0001-p0100/p0076-c01.md)).
- **SAML:** корпоративное приложение и группа `zbx_admin` для сопоставления с `JIT_Admin`; при включении JIT вводятся атрибуты групп, имени, фамилии и mapping ([p0078](../../../rag/chunks/p0001-p0100/p0078-c01.md)–[p0084](../../../rag/chunks/p0001-p0100/p0084-c01.md)).
- **LDAP:** в учебном рецепте настраивается OpenLDAP, затем в Zabbix включается LDAP, а на внутренней группе `Internal` сохраняется отдельный путь входа для Admin ([p0087](../../../rag/chunks/p0001-p0100/p0087-c01.md)–[p0089](../../../rag/chunks/p0001-p0100/p0089-c01.md)).

## Проверки перед изменением доступа

- Определить выбранный способ аутентификации **до** массового создания пользователей ([p0060](../../../rag/chunks/p0001-p0100/p0060-c01.md)).
- Проверить, к каким объектам дано `Read`/`Read-write`, какие UI/actions доступны роли и есть ли обходной внутренний аккаунт при переключении LDAP ([p0062](../../../rag/chunks/p0001-p0100/p0062-c01.md), [p0068](../../../rag/chunks/p0001-p0100/p0068-c01.md), [p0088](../../../rag/chunks/p0001-p0100/p0088-c01.md)).
- На отдельном тестовом пользователе проверить фактические права после логина; настройка должна соответствовать требуемому уровню доступа, а не только роли с названием «User» или «Admin» ([p0071](../../../rag/chunks/p0001-p0100/p0071-c01.md), [p0091](../../../rag/chunks/p0001-p0100/p0091-c01.md)).
- Не использовать приведённые в книге тестовые пароли и контейнеры как production-профиль ([p0087](../../../rag/chunks/p0001-p0100/p0087-c01.md)). Производственные значения IdP/LDAP и rollback: `[Needs confirmation]`.
