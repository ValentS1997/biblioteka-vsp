# Глава 2 — cheatsheet

**Только RAG:** PDF 59–92. Основа и SHA-256: [README](README.md).

## Symptom / problem framing

- Пользователь не видит хосты или шаблоны → проверить **группу пользователя, объектный scope и уровень Read/Read-write** ([p0062](../../../rag/chunks/p0001-p0100/p0062-c01.md)–[p0064](../../../rag/chunks/p0001-p0100/p0064-c01.md)).
- Пользователь видит лишние пункты меню или может менять конфигурацию → проверить **роль**, включая `User type`, UI elements, actions и API, а не только группу ([p0066](../../../rag/chunks/p0001-p0100/p0066-c01.md)–[p0071](../../../rag/chunks/p0001-p0100/p0071-c01.md)).
- Успешная внешняя аутентификация не создаёт пользователя → отличать **SAML/LDAP без JIT** (предварительный аккаунт обязателен) от **JIT** (создание и назначение доступа по mapping) ([p0077](../../../rag/chunks/p0001-p0100/p0077-c01.md), [p0084](../../../rag/chunks/p0001-p0100/p0084-c01.md), [p0091](../../../rag/chunks/p0001-p0100/p0091-c01.md)).
- После перевода на LDAP возможна потеря привычного входа → авторы **перед переключением** назначают Admin группу `Internal` ([p0088](../../../rag/chunks/p0001-p0100/p0088-c01.md)–[p0089](../../../rag/chunks/p0001-p0100/p0089-c01.md)).

## Baseline / context

Zabbix уже установлен и доступен через UI (предусловие главы). Авторский пример Cloud Hoster: три группы `Networking`, `Infrastructure`, `Buying and Inventory`. Для тестовой SAML/JIT-схемы — Azure AD / Microsoft Entra ID; для LDAP/JIT — подготовленный OpenLDAP. Учётные записи и политики ролей предприятия необходимо определить отдельно ([p0059](../../../rag/chunks/p0001-p0100/p0059-c01.md)–[p0061](../../../rag/chunks/p0001-p0100/p0061-c01.md), [p0078](../../../rag/chunks/p0001-p0100/p0078-c01.md), [p0087](../../../rag/chunks/p0001-p0100/p0087-c01.md)).

## Interpretation

- `Read` / `Read-write` относятся к определённым группам хостов или шаблонов; UI/API/action permissions задаются отдельной ролью.
- Тип `User` ограничен возможностями чтения; `Admin` может получить доступ к настройкам; `Super admin` обладает широкими разрешениями. **Название группы Networking не ограничивает автоматически Super admin** ([p0074](../../../rag/chunks/p0001-p0100/p0074-c01.md)).
- У `User+ role` в примере исходным типом служит `Admin`; специальный доступ к Maintenance и право `Create and edit maintenance` означают возможность изменения состояния, а не просто чтение ([p0067](../../../rag/chunks/p0001-p0100/p0067-c01.md), [p0071](../../../rag/chunks/p0001-p0100/p0071-c01.md)).
- SAML и LDAP без JIT централизуют проверку паролей, но **не заменяют** локальную настройку пользователей. JIT связывает внешнюю группу и локальную роль при первом входе ([p0077](../../../rag/chunks/p0001-p0100/p0077-c01.md), [p0085](../../../rag/chunks/p0001-p0100/p0085-c01.md)–[p0086](../../../rag/chunks/p0001-p0100/p0086-c01.md), [p0092](../../../rag/chunks/p0001-p0100/p0092-c01.md)).

## Next action

Сначала определить требования к конкретной группе: **какие хосты/шаблоны** доступны, **какие действия и разделы UI** допустимы, **как проверяется личность**, и **кто создаёт учётную запись**. Затем применить только нужные изменения. При переходе на LDAP сначала сохранить внутренний путь входа Admin в соответствии с рецептом.

## Modifying action

- `Users → User groups → Create user group`: определить имя, Frontend access, разрешения к целевым группам; эффект — изменённая политика доступа к объектам; риск — чрезмерный доступ или отсутствие видимости; проверка — контроль прав после сохранения ([p0061](../../../rag/chunks/p0001-p0100/p0061-c01.md)–[p0064](../../../rag/chunks/p0001-p0100/p0064-c01.md)).
- `Users → User roles → Create user role`: выбрать `User type`, UI/services/API/actions; эффект — изменение возможностей пользователя; риск — предоставление административных действий; проверка — вход тестового аккаунта ([p0065](../../../rag/chunks/p0001-p0100/p0065-c01.md)–[p0071](../../../rag/chunks/p0001-p0100/p0071-c01.md)).
- `Users → Users → Create user`: username, группа, пароль при внутреннем методе, `Permissions → Role`; эффект — новая учётная запись с конкретными разрешениями ([p0072](../../../rag/chunks/p0001-p0100/p0072-c01.md)–[p0077](../../../rag/chunks/p0001-p0100/p0077-c01.md)).
- `Users → Authentication → SAML settings` или `LDAP settings`: настройка IdP/LDAP и JIT mapping; эффект — меняется вход/создание пользователей, особенно чувствительный этап — метод по умолчанию ([p0083](../../../rag/chunks/p0001-p0100/p0083-c01.md)–[p0084](../../../rag/chunks/p0001-p0100/p0084-c01.md), [p0088](../../../rag/chunks/p0001-p0100/p0088-c01.md)–[p0090](../../../rag/chunks/p0001-p0100/p0090-c01.md)).

## Verification / acceptance checks

1. Права в группе соответствуют выбранным host/template groups (`Read` или `Read-write`).
2. Пользователь имеет ожидаемую роль и видит только нужные разделы и действия; отдельно проверить API и Maintenance при User+.
3. Для SAML/LDAP без JIT — внешняя аутентификация проходит **для заранее созданного локального пользователя**.
4. Для JIT — первый вход создаёт пользователя и выдаёт ожидаемую группу/роль. В OpenLDAP-рецепте результат сверяется в `Users → Users`.
5. При LDAP default сохраняется проверенный внутренний административный путь; его тестирование после изменения источником подробно не расписано: `[Needs confirmation]`.

## Rollback

Авторы показывают **сохранение внутреннего доступа Admin** через группу Internal перед переходом на LDAP — превентивный механизм сохранения доступа ([p0088](../../../rag/chunks/p0001-p0100/p0088-c01.md)). Полная пошаговая обратная миграция с LDAP/SAML на исходный способ, откат mapping/JIT-пользователей, cleanup тестовой БД или контейнеров **в тексте главы отсутствуют**: `[Needs confirmation]`. Не считать прежние полномочия восстановленными без повторной проверки.

## Границы источника

Некоторые точные SAML-URI, атрибуты и LDAP-поля помещены только на рисунки 2.32–2.48; в текстовом RAG они отсутствуют, поэтому их значения = `RAG_MISS`. Пример `Super admin` и тестовые LDAP-учётные данные требуют отдельной оценки перед production; [source-findings.md](source-findings.md).
