## Главное: повторное использование при сохранении смысла

**Один шаблон объединяет общие правила**, применимые к нескольким хостам: items, triggers, tags и макросы. Когда item создаётся на уровне шаблона, связанный хост получает его, сохраняя **собственное значение item** ([p0205](../../../rag/chunks/p0201-p0300/p0205-c01.md)–[p0207](../../../rag/chunks/p0201-p0300/p0207-c01.md)). Пользовательский префикс в имени отличает собственные шаблоны от стандартных; книга советует клонировать стандартный шаблон, а не редактировать оригинал ([p0199](../../../rag/chunks/p0101-p0200/p0199-c01.md), [p0200](../../../rag/chunks/p0101-p0200/p0200-c01.md)).

**SNMP item** в примере получает hostname с числового OID `.1.3.6.1.2.1.1.5.0`. Автор использует символическое имя `sysName` как item key, но для `SNMP OID` рекомендует **числовой вид**, чтобы не зависеть от установленной MIB ([p0204](../../../rag/chunks/p0201-p0300/p0204-c01.md), [p0207](../../../rag/chunks/p0201-p0300/p0207-c01.md)). Детальные значения authentication/host macros в формах — `RAG_MISS`.

**Macros**: пользовательский `{$MACRONAME}` можно задать на уровне шаблона и переопределить на конкретном host. Пример меняет ожидаемый префикс `lar-` на `dev-`. Встроенный `{HOST.HOST}` получает hostname из хоста, то есть один шаблон может порождать разные содержательные выражения на разных узлах ([p0212](../../../rag/chunks/p0201-p0300/p0212-c01.md)–[p0214](../../../rag/chunks/p0201-p0300/p0214-c01.md)).

**LLD**: правило обнаружения сетевых интерфейсов создаёт `{#IFNAME}` (например, `lo`, `ens192`) и `{#SNMPINDEX}` (например, 1/2); item prototypes становятся отдельными item для каждого интерфейса, trigger prototypes — отдельными триггерами ([p0215](../../../rag/chunks/p0201-p0300/p0215-c01.md)–[p0224](../../../rag/chunks/p0201-p0300/p0224-c01.md)). **Немедленное удаление потерянных ресурсов — учебная настройка, не безопасный default для production**: при кратковременной потере обнаружения можно потерять items, triggers и историю ([p0217](../../../rag/chunks/p0201-p0300/p0217-c01.md)).

**Вложенные шаблоны**: родитель `Custom Linux by SNMP` связывается с `Custom Linux uptime by SNMP`. Host наследует его uptime item, хотя к host подключён один верхнеуровневый шаблон. Книга отмечает выигрыш от повторного использования и сложность поддержки дерева шаблонов ([p0225](../../../rag/chunks/p0201-p0300/p0225-c01.md)–[p0228](../../../rag/chunks/p0201-p0300/p0228-c01.md)).

## Операционная последовательность

1. Выбрать единое имя, группу шаблонов, описание; создать отдельный собственный шаблон.
2. Добавить `class:os` и `target:linux`; проверить видимость тегов в `Monitoring → Problems`.
3. Подтвердить фактический SNMP OID через `snmpwalk` и `snmptranslate`; создать item `sysName` на уровне шаблона.
4. Связать шаблон с host, задать SNMP credentials как локальные значения, проверить `Monitoring → Latest data`.
5. Добавить триггер на уровне template; тестовое переименование hostname **изменяет системное состояние**, требует отдельного окна и rollback.
6. Создать/переопределить macros, проверить получившиеся выражения триггеров.
7. Для LLD сначала Value mapping, затем Discovery rule, prototypes и тест JSON/объектов на host. Не выбирать `Immediately` для потери ресурсов, пока не определена политика жизненного цикла.
8. Создать второй шаблон uptime, вложить его в первый, убедиться, что новый item появился у host.
