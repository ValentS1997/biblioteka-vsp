## Source-supported managerial tools / practices

| Прием | Тип | Эффект | Риск / ограничение | Проверка | Rollback |
|---|---|---|---|---|---|
| Оценить соответствие задачи уровню исполнителя | read-only | Снижает лишние вопросы и вероятность провала | Оценка может быть ошибочной | Исполнитель понимает задачу и способен двигаться самостоятельно | Выбрать другого исполнителя или добавить обучение |
| Явно задать срок и критерии результата | planning | Уменьшает неоднозначность делегирования | Критерии могут оказаться неполными | Исполнитель может повторить критерии своими словами | Уточнить критерии |
| Разбить большую задачу на логические этапы | planning | Дает точки раннего контроля | Слишком мелкая декомпозиция превращается в микроменеджмент | Контрольные точки редкие, но достаточные | Укрупнить этапы |
| Инвестировать в обучение на повторяемой задаче | workload-generating | Повышает будущую автономность сотрудника | Не всегда окупается для разовой экзотической задачи | Следующие похожие задачи требуют меньше помощи | Передать разовую задачу более опытному сотруднику |
| Публично обозначить ответственного | state-changing communication | Дает сотруднику реальные полномочия во взаимодействиях | Нельзя передавать ответственность без необходимых прав | Остальные участники признают его решения в оговоренной зоне | Пересогласовать зону ответственности |
| Разрешить самостоятельные решения | delegation | Развивает ответственность и самостоятельность | Ошибка может стоить дорого | Ошибки находятся в допустимой зоне риска | Для критичных решений ввести обязательную контрольную точку |
| Публично признать вклад | communication | Усиливает мотивацию и видимость сотрудника | Нельзя приписывать вклад, которого не было | Вклад конкретного человека заметен окружающим | Not applicable |
| Критику обсуждать лично | communication | Снижает защитную реакцию и публичное унижение | Критика не должна исчезать совсем | Ошибка разобрана, отношения с командой не разрушены | Повторный личный разбор |
| Разобрать провал по причинам процесса | read-only → process change | Помогает предотвращать повторение | Источник не задает формальный postmortem-шаблон | Получен список причин и будущих мер | [Needs confirmation] |
| Фильтровать внешнюю турбулентность | communication boundary | Снижает ненужный стресс команды | Нельзя скрывать информацию, необходимую людям для работы | Команда знает существенное, но не живет во всех внешних переговорах | Расширить коммуникацию при нехватке контекста |
| Сказать «нет» чрезмерной нагрузке | state-changing negotiation | Защищает емкость команды | Возможность отказа зависит от организации | Объем работы соответствует ресурсам лучше, чем до пересогласования | Пересогласовать объем/сроки |
| Проверить доступные корпоративные льготы | read-only | Позволяет использовать уже существующие ресурсы | Набор зависит от компании | Команда знает и использует доступные возможности | Not applicable |

## Delegation decision tree

```text
есть задача
  -> сотрудник достаточно компетентен?
       no -> другой исполнитель / обучение
       yes
  -> срок и критерии ясны?
       no -> уточнить постановку
       yes
  -> задача повторяемая?
       yes -> обучение может окупиться
  -> передать задачу и достаточную свободу
  -> определить логические checkpoints
  -> не вмешиваться в мелочи при нормальном направлении
  -> признать вклад
```

## Safety boundary

Источник прямо различает допустимые ошибки и ошибки, критичные для бизнеса. Для критичных действий свобода эксперимента не предполагается: такие риски нужно заранее выявлять и предотвращать. Конкретные технические механизмы защиты источник не задает.
