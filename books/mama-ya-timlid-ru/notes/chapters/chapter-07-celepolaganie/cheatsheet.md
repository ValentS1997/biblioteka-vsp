# Cheatsheet — глава 7 «Целеполагание»

## Symptom / problem framing

Признаки потери фокуса:

- каждый делает локально интересную задачу, но общий результат не приближается;
- команда помнит дату, но не понимает минимально приемлемое качество;
- люди «полируют» детали, которые не влияют на запуск;
- проект конкурирует с другими задачами и проигрывает более настойчивому менеджеру;
- бизнес-цель не вызывает у команды эмоционального отклика;
- важные новости растворяются в общем чате;
- заказчики не понимают, что происходит;
- удаленные или смежные участники ощущают себя внешними исполнителями;
- специалисты не видят конечный продукт и потому мало предлагают улучшений.

## Baseline / context

Для управляемой работы команда должна понимать:

- **куда идем**;
- **что считается результатом**;
- **какое качество достаточно**;
- **почему это важно**;
- **что изменилось с прошлой синхронизации**;
- **как текущая задача связана с общей целью**.

## Read-only checks

### Цель
1. Может ли каждый участник одним предложением назвать цель текущего этапа?
2. Есть ли явный deadline, если он действительно важен?
3. Понятно ли, что считается готовой работой?
4. Понятна ли нижняя планка качества?
5. Какие текущие задачи не влияют на достижение цели?
6. Не тратится ли время на второстепенные улучшения в ущерб критическому пути?

### Мотивация
1. Работает ли бизнес-цель как мотиватор именно для этой команды?
2. Если нет, что людям ближе:
   - качество;
   - польза пользователю;
   - новая технология;
   - профессиональная публикация;
   - выступление;
   - признание коллег?
3. Видит ли команда реальные отзывы и проблемы пользователей?

### Коммуникация
1. Какой канал является каноническим для важных новостей?
2. Не теряются ли ключевые сообщения в неформальном чате?
3. Как часто команда слышит повтор цели и изменение контекста?
4. Видят ли заказчики регулярный промежуточный результат?
5. Есть ли короткий письменный итог после демо/отчетного периода?
6. Получают ли удаленные коллеги тот же контекст, что локальная команда?

### Вовлеченность
1. Понимают ли разработчики, дизайнеры, тестировщики конечный результат?
2. Видят ли они контекст решений смежных ролей?
3. Есть ли место, где разные специалисты могут обсуждать продукт вместе?
4. Не превышает ли стоимость погружения внешнего исполнителя длительность самой задачи?

## Interpretation

- **Команда занята, но цель стоит на месте** → локальные задачи не связаны с критическим результатом.
- **Работа сделана вовремя, но непригодна к запуску** → критерий качества не был договорен заранее.
- **Работа слишком долго «полируется»** → граница достаточного качества не определена.
- **Людям все равно на финансовую цель** → требуется другой мотивирующий смысл, не противоречащий цели бизнеса.
- **Важная информация пересылается только в чате** → канал коммуникации ненадежен.
- **Заказчики нервничают при нормальном ходе работ** → промежуточная видимость недостаточна.
- **Удаленная команда ощущает себя аутсорсом** → ей не хватает контекста и участия.
- **Исполнители не предлагают улучшений** → возможно, они видят только свою задачу, а не конечный продукт.

## Next action

1. Записать цель текущего этапа одним предложением.
2. Явно определить:
   - срок, если он важен;
   - минимально достаточное качество;
   - критерий готовности.
3. Проверить все активные задачи на связь с этой целью.
4. Убрать или отложить локально интересную работу, не влияющую на результат.
5. Выбрать один надежный канал для ключевых обновлений.
6. Ввести короткий повтор цели и статуса с понятной периодичностью.
7. Показывать промежуточный результат заказчикам/руководству.
8. Писать краткий итог после демонстрации или отчетного периода.
9. Дать команде больше продуктового контекста: пользователи, жалобы, смежные решения.
10. Проверить, начали ли люди предлагать улучшения исходя из общего результата.

## Modifying action

Источник поддерживает такие изменения:

- регулярно повторять цель;
- заранее определять качество и критерий готовности;
- ограничивать работу, не связанную с критической целью;
- подбирать мотивирующее объяснение цели под людей;
- показывать реальные проблемы пользователей;
- использовать отдельный надежный канал для важных новостей;
- проводить регулярные короткие презентации/демо;
- рассылать итоги отчетного периода;
- поддерживать общий информационный канал для широкого круга заинтересованных коллег;
- вовлекать удаленные команды в общий контекст;
- собирать смежных специалистов для совместного обсуждения проекта;
- давать участникам возможность влиять на решения.

## Verification / acceptance checks

- каждый участник может назвать текущую цель;
- критерий готовности не зависит от догадок;
- второстепенная работа не вытесняет критический результат;
- ключевые новости имеют понятный канал;
- заказчики регулярно видят прогресс;
- после отчетного периода остается короткий письменный след;
- удаленные/смежные участники получают достаточный контекст;
- команда предлагает улучшения, исходя из понимания конечного результата.
