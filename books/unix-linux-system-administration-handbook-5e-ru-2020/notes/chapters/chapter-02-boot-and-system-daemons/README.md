## Краткий анализ

Глава описывает загрузку как цепочку состояний, а не как единичное действие. Сначала firmware выбирает загрузочный путь, затем bootloader выбирает ядро и передаёт ему параметры, ядро инициализирует систему и запускает PID 1, после чего init/systemd приводит службы к требуемому рабочему состоянию.

Для современных Linux основная operational-модель главы — systemd. Unit-файлы описывают службы и другие системные объекты; targets представляют режимы работы; зависимости определяют, какие units нужны, а директивы порядка определяют последовательность. Эти два понятия в systemd разделены: наличие зависимости само по себе не означает порядок запуска.

Локальные изменения systemd следует хранить отдельно от файлов пакета. Глава прямо предупреждает не редактировать vendor unit files в `/usr/lib/systemd/system`; для локальных units и overrides используется `/etc/systemd/system`. После изменения unit-конфигурации выполняется `systemctl daemon-reload`, а затем при необходимости перезапуск конкретной службы.

Для FreeBSD используется отдельная модель rc. Значения по умолчанию не следует менять в `/etc/defaults/rc.conf`; локальные настройки задаются через `/etc/rc.conf` или `/etc/rc.conf.local`.

При boot failure глава предлагает три стратегии: вернуть систему к known-good state, получить минимальную оболочку через rescue/single-user/emergency mode либо загрузить отдельную recovery-систему и исследовать неисправный диск. Для облака подчёркивается ценность snapshots и замены неисправного экземпляра заведомо рабочей копией.

## Основной принцип

Диагностировать загрузку нужно по этапам:

`firmware → bootloader → kernel → PID 1 → target/services`.

Сначала определить, на каком этапе возник сбой, собрать read-only данные и журнал, затем менять только соответствующий слой. После изменений загрузочной конфигурации глава рекомендует проверить систему реальной перезагрузкой.
