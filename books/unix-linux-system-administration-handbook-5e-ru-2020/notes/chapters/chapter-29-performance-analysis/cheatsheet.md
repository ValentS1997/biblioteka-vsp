# Шпаргалка: сервер тормозит

Цель: локализовать bottleneck без случайного tuning.

## 0. Зафиксировать симптом и baseline

Сначала определить, что именно стало медленнее и когда это началось. Сравнить текущее состояние с историческими данными и журналами.

Read-only:

```bash
uptime
sar
```

Проверка: есть ли отклонение от обычного load/CPU/I/O/network профиля.

## 1. CPU

```bash
top
ps auxww
vmstat 5 5
mpstat -P ALL
```

Смотреть:

- высокий `us` — вычислительная нагрузка;
- высокий `sy` — много системной работы/системных вызовов;
- высокий `wa` — ожидание I/O;
- высокий `st` на VM — CPU забирает гипервизор;
- один процесс стабильно забирает большую долю CPU;
- дисбаланс между CPU.

Next action: подтвердить процесс или источник нагрузки; при необходимости использовать `perf top`.

## 2. Память и paging

```bash
vmstat 5 5
cat /proc/meminfo
```

Смотреть:

- `si` / `so`;
- особенно постоянный `so` — признак принудительного вытеснения страниц;
- нехватку физической памяти во время пиков.

Next action: проверить рабочий набор процессов и необходимость дополнительной RAM. Не начинать с изменения `swappiness`.

## 3. Диск

```bash
iostat
lsof
fuser
```

Смотреть:

- высокий или устойчивый disk I/O;
- процессы и файловые системы, конкурирующие за один диск;
- размещение данных, журналов и swap на одних и тех же устройствах.

Для контролируемого benchmark:

```bash
fio <job>.fio
```

Риск: `fio` создаёт реальную нагрузку. Не запускать на production без понимания профиля job и допустимого воздействия.

## 4. Сеть и внешние зависимости

```bash
ip a
ss
sar -n DEV
```

Для FreeBSD:

```bash
ifconfig -a
netstat
```

Проверить не только локальную сеть, но и внешние зависимости: DNS, NFS, Kerberos и другие удалённые сервисы. Глава отдельно отмечает, что задержки DNS могут выглядеть как «медленный сервер».

## 5. Проверка подозрительного процесса

Изменяющее действие:

```bash
kill -STOP <PID>
```

Что меняет: приостанавливает процесс.

Acceptance check: если симптом исчезает после остановки, гипотеза о процессе усиливается.

Rollback:

```bash
kill -CONT <PID>
```

`kill -CONT` — операционный rollback для `STOP`; он не приводится как отдельный пример главы, но необходим для безопасного применения проверки.

## 6. Ограничение влияния подтверждённого процесса

CPU:

```bash
renice ...
```

I/O:

```bash
ionice -c 3 -p <PID>
```

После изменения повторить `top`, `vmstat`, `iostat` и сравнить с baseline.

## 7. I/O scheduler

Read-only:

```bash
cat /sys/block/<disk>/queue/scheduler
```

Изменение:

```bash
echo noop > /sys/block/<disk>/queue/scheduler
```

Не считать конкретный scheduler универсально лучшим. Проверить доступные варианты на конкретной workload и измерить результат до/после.

## Минимальный operational flow

```text
symptom
  ↓
baseline/history
  ↓
CPU?
  ↓
memory/paging?
  ↓
disk I/O?
  ↓
network/external dependency?
  ↓
targeted profiling
  ↓
one controlled change
  ↓
remeasure
  ↓
keep or rollback
```
