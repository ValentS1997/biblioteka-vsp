# Шпаргалка: зачем нужен Kubernetes и где проходит граница ответственности

Цель: быстро восстановить модель главы 1 — от проблем масштабирования приложений до базовой архитектуры Kubernetes — без добавления сведений из следующих глав или внешних источников.

## Symptom / problem framing

Глава описывает несколько взаимосвязанных проблем:

- монолит сложно независимо масштабировать и изменять;
- микросервисы легче развивать по отдельности, но их становится трудно размещать, связывать и сопровождать вручную;
- компоненты могут требовать конфликтующие версии библиотек;
- окружения разработки и production различаются и меняются со временем;
- ручное размещение на большом количестве серверов плохо масштабируется;
- аппаратные отказы требуют автоматического переразмещения workload;
- разработчикам нужна возможность выпускать приложения чаще, не изучая физическую топологию дата-центра.

## Baseline / context

### Монолит → микросервисы

```text
Монолит
└─ один тесно связанный deployable unit
   ├─ изменения требуют общей выкладки
   └─ масштабирование часто затрагивает систему целиком

Микросервисы
├─ отдельные процессы
├─ явные API
├─ независимая разработка
├─ независимая выкладка
└─ независимое масштабирование
```

Цена микросервисов — больше компонентов и связей, которые требуется автоматически размещать, конфигурировать и восстанавливать.

### VM → контейнер

```text
VM:
application → guest OS/kernel → hypervisor → host

Container:
application process → host kernel → hardware
```

VM даёт отдельное ядро. Контейнер использует ядро хоста и поэтому легче по ресурсам.

Механизмы контейнерной изоляции, названные в главе:

- Linux namespaces — ограничивают представление ресурсов системой процессу;
- cgroups — ограничивают объём CPU, RAM, network bandwidth и других ресурсов.

### Docker

Три понятия:

- image — приложение, файловая система и метаданные;
- registry — хранилище и точка распространения образов;
- container — изолированный процесс, запущенный из image.

### Kubernetes

```text
Control plane
├─ API server
├─ Scheduler
├─ Controller Manager
└─ etcd

Worker node
├─ Container runtime
├─ Kubelet
└─ kube-proxy
```

## Interpretation

### Если компоненты требуют конфликтующие зависимости

Глава направляет к контейнеризации: приложение получает своё ожидаемое файловое окружение вместо совместного использования набора библиотек хоста.

### Если один компонент нужно масштабировать независимо

Микросервисная декомпозиция позволяет масштабировать конкретный сервис отдельно от остальных компонентов.

### Если нужно выбрать, где запускать workload

Это задача Kubernetes scheduler на основе требований workload и доступных ресурсов узлов.

### Если контейнер должен быть реально запущен на worker node

Kubelet взаимодействует с API server и поручает container runtime получить image и запустить контейнер.

### Если фактическое количество экземпляров отклоняется от заданного

Kubernetes стремится вернуть фактическое состояние к описанному желаемому состоянию.

### Если рабочий узел отказал

Глава описывает перенос контейнеров на другие узлы как функцию Kubernetes.

### Если клиентам нужна стабильная точка доступа к перемещающимся репликам

Kubernetes предоставляет единый стабильный IP для службы; обнаружение может выполняться через environment variables или DNS, а kube-proxy балансирует подключения между контейнерами службы.

## Next action

Использовать модель локализации:

```text
Проблема приложения
├─ зависимости / окружение
│  └─ image + container
├─ распространение image
│  └─ registry
├─ размещение workload
│  └─ scheduler
├─ запуск на узле
│  └─ Kubelet + container runtime
├─ удержание желаемого состояния
│  └─ controller-side logic
└─ доступ клиентов к репликам
   └─ service discovery + kube-proxy
```

Дальнейшую командную диагностику брать из следующих глав, а не достраивать из памяти.

## Modifying action

Явного CLI-синтаксиса глава не предоставляет.

Поддержанный главой state-changing workflow описан концептуально:

1. упаковать приложение в image;
2. поместить image в registry;
3. опубликовать описание приложения через Kubernetes API;
4. scheduler назначает workload рабочим узлам;
5. Kubelet поручает runtime получить image и запустить контейнеры.

## Verification / acceptance checks

На уровне главы ожидаемый результат таков:

- заявленное количество экземпляров поддерживается;
- при отказе экземпляра Kubernetes восстанавливает его;
- при потере узла workload может быть запущен на других узлах;
- клиенты используют стабильную точку доступа к службе, а не адрес конкретного контейнера;
- приложение не привязано к конкретному серверу без явно заданного требования к оборудованию.
