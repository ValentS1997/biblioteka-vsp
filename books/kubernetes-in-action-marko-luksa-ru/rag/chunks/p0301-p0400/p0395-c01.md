  Планировщик не предписывает выбранному узлу (или агенту Kubelet, ра-
ботающему на этом узле) запускать модуль. Планировщик лишь обновляет
определение модуля через сервер API. Затем сервер API уведомляет Kubelet
(опять же, через механизм наблюдения, описанный ранее) о том, что модуль
назначен. Как только агент Kubelet на целевом узле увидит, что модуль назна-
чен на его узел, он создает и запускает контейнеры модуля.
  Хотя в крупном плане вид данного процесса назначения модулю узла ка-
жется тривиальным, фактическая задача выбора самого лучшего узла для
модуля не так проста. Разумеется, самый простой планировщик может вы-
бирать случайный узел и не заботиться о модулях, уже работающих на этом
узле. С другой стороны, планировщик может использовать передовые мето-
ды, такие как машинное обучение, чтобы предвидеть, какие модули должны
быть назначены в ближайшие минуты или часы, и назначать модули с целью
максимизировать предстоящую задействованность оборудования, не требуя
никакого переназначения существующих модулей. Используемый по умолча-
нию планировщик Kubernetes находится где-то посередине.
