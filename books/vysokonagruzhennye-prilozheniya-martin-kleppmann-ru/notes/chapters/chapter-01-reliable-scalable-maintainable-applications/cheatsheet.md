# Шпаргалка главы 1 — надежность, масштабируемость, сопровождение

## Symptom / problem framing

Проблема главы: информационная система может работать сегодня, но ломаться при сбоях, росте нагрузки или накоплении эксплуатационной/архитектурной сложности.

Три вопроса:

1. Продолжает ли система предоставлять требуемый сервис при сбоях?
2. Что произойдет при конкретном росте нагрузки и какие ресурсы потребуются для сохранения производительности?
3. Насколько легко систему эксплуатировать, понимать и изменять?

## Baseline / context

### Надежность

- `fault` — отклонение одного компонента от рабочих характеристик.
- `failure` — система в целом перестала предоставлять требуемый пользователю сервис.
- Свести вероятность fault к нулю невозможно; цель — не дать fault перерасти в failure.
- Источники проблем: аппаратные сбои, программные ошибки и человеческий фактор.

### Масштабируемость

Сначала описывается нагрузка через параметры, относящиеся именно к данной системе:

- requests/sec;
- read/write ratio;
- число одновременно активных пользователей;
- cache hit rate;
- fan-out;
- другие параметры, определяющие узкое место.

Производительность описывается отдельно:

- batch: throughput / время выполнения задания;
- online: response time;
- latency distribution: median/p50 и высокие процентили p95/p99/p999.

### Удобство сопровождения

Три принципа:

- operability — удобство эксплуатации;
- simplicity — снижение побочной сложности;
- evolvability — удобство изменения при новых требованиях.

## Read-only checks

1. Определить пользовательский сервис, который должен оставаться доступным.
2. Разделить наблюдаемое событие на `fault` компонента и `failure` системы.
3. Зафиксировать допущения системы и внешние зависимости.
4. Проверить monitoring/telemetry: ошибки, производительность, состояние зависимостей.
5. Определить реальные load parameters; не использовать слово «масштабируемость» без числового контекста.
6. Измерить производительность:
   - throughput для batch;
   - response time со стороны клиента для online;
   - p50 и хвостовые процентили.
7. Проверить очередь и head-of-line blocking.
8. Для сложного пользовательского запроса учитывать самый медленный downstream-вызов.
9. Проверить, соответствует ли выбранная архитектура частым и редким операциям.
10. Оценить operability: мониторинг, automation hooks, документация, понятная operational model, разумные defaults.
11. Оценить complexity: скрытые зависимости, тесное сцепление, особые случаи и неявные допущения.
12. Оценить evolvability: насколько безопасно менять систему при новых требованиях.

## Interpretation

- Локальный fault при сохранении пользовательского сервиса → fault-tolerance работает по целевому сценарию.
- Один и тот же программный дефект одновременно поражает много узлов → проблема систематическая; простая аппаратная избыточность недостаточна.
- Рост нагрузки ухудшает latency при неизменных ресурсах → нужно установить зависимость performance от конкретного load parameter.
- Среднее время ответа выглядит хорошо, а p99/p999 плохи → проблема скрыта в хвосте распределения.
- Load test отправляет следующий запрос только после ответа → тест искусственно уменьшает очереди и искажает измерение.
- Частота чтения и записи сильно различается → архитектура должна учитывать соотношение операций, как в примере Twitter.
- Рост архитектуры приводит к скрытым взаимодействиям и ошибкам изменений → проблема maintainability/complexity.
- Операторы не могут понять состояние системы или предсказать эффект действия → operability недостаточна.

## Next action

1. Выбрать одну ось: reliability, scalability или maintainability.
2. Зафиксировать измеримый baseline.
3. Найти параметр/механизм, который ограничивает систему.
4. Выбрать минимальное целевое изменение.
5. Выполнить изменение контролируемо.
6. Повторить те же измерения.
7. Оставить изменение только если acceptance criteria выполнены.

## Modifying action

Source-confirmed виды изменений:

- intentional fault injection для проверки fault-tolerance;
- restart процесса после fatal failure;
- быстрый rollback конфигурационных изменений;
- gradual rollout нового кода;
- добавление вычислительных ресурсов;
- vertical scaling;
- horizontal scaling;
- изменение read/write architecture, включая гибридный подход;
- автоматизация эксплуатационных задач;
- введение/улучшение абстракций для снижения сложности.

Перед изменением необходимо определить, какой load/failure scenario проверяется. Универсальное изменение «для масштабируемости» без модели нагрузки глава не поддерживает.

## Verification / acceptance checks

### Reliability

- fault не превращается в пользовательский failure;
- после сбоя система продолжает предоставлять требуемый сервис;
- monitoring обнаруживает нарушение инварианта/ограничения;
- восстановление или rollback доступно для ошибки изменения.

### Scalability

- load parameter измерен до и после;
- response time измеряется со стороны клиента;
- p50 и выбранные tail percentiles не ухудшились сверх целевого уровня;
- throughput/latency сопоставлены при одинаковой методике;
- load generator не зависит от response time;
- добавленные ресурсы дают ожидаемый эффект при росте нагрузки.

### Maintainability

- оператор видит состояние системы;
- действие имеет предсказуемый эффект;
- automation не исключает возможность ручного управления при необходимости;
- снижение complexity не скрывает нужную функциональность;
- изменение требований не требует разрушительного переписывания без необходимости.

## Rollback

Source-confirmed:

- быстрый rollback изменений конфигурации;
- постепенное внедрение кода, ограничивающее blast radius;
- перезапуск процесса после fatal failure.

Для конкретных команд отката, orchestration-процедур и rollback vertical/horizontal scaling: `[Needs confirmation]`.

## Короткая operational петля

`baseline → failure/load model → measurement → controlled change → remeasure → keep/rollback`.
