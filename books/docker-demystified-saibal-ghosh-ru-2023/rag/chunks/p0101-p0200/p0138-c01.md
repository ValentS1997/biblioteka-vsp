При ближайшем рассмотрении можно увидеть, что у сети docker _gwbri dge имеется
некоторая информация о нашем контейнере (IР-адрес, МАС-адрес и  т. д.), а для
com. docker . network. bridge . еnаЫе _ icc установлено значение false.

Этот параметр не позволяет контейнерам на одном мосте взаимодействовать друг
с другом. Дело в том, что, поскольку контейнеры уже подключены к оверлейной
сети, они используют ее для обмена данными друг с другом.
В таком случае зачем нужна docker_gwbridge?
Сеть docker_gwbridge имеет особое назначение. Контейнеры в оверлейной сети могут
прекрасно взаимодействовать друг с другом, но у них нет никакой связи с внешним
миром. Для этого и нужна сеть docker _gwbridge. На рис. 6.50 показана архитектура

сети.

Два контейнера сообщаются между собой по оверлейной сети, как показано на
рис. 6.50. Каждый контейнер имеет два интерфейса: один для оверлейной сети,
другой -  для подключения к docker _gwbri dge. Оба контейнера подключены к docker_
gwbridge, но каждый использует свой отрезок сети docker _gwbridge, и единственная
цель docker _gwbridge -  обеспечить взаимодействие контейнеров с внешним миром.
Если внимательно изучить выходные данные исследования сети  docker gwbridge
(см. выше), можно увидеть, что для com . docker . network . bridge. enaЬle  i p masquerade ус
тановлено значение true; это значит, что IР-адреса могут коммуницировать с внеш
ним миром, «маскируясь» под хает, на котором находится контейнер.

Теперь разберемся в том, как функционирует оверлейная сеть.
Прежде всего проверим, может ли контейнер в хает-системе 1 (управляющий узел
Swarm) взаимодействовать с контейнером в хает-системе 2 (рабочий узел) и на
оборот.
