У правление журналами в Docker -  весьма важная функция, потому что в системе
с сотнями и даже тысячами контейнеров от качества этого процесса зависит эффек
тивность диагностики неисправностей. Обработка информации от такого большого
количества контейнеров для получения конструктивного результата -  далеко не

тривиальная задача.

Большинство драйверов журналирования могут отправлять журналы в центральное
расположение или даже к инструментам управления, но у них нет функций анализа
и нормализации данных. Для этого требуется отдельный инструмент, известный
как отправитель журншюв, или конвейер данных, например Logstash и Filebeat,

которые считывают данные из различных источников, анализируют и нормализуют
их, а затем отправляют в центральное расположение в формате, поддерживаемом
такими инструментами , как Kibana или Elasticsearch.

Базовая архитектура контейнера

На рис. 2.22 изображена схема базовой архитектуры контейнера:
Docker Engine -   это один из центральных компонентов Docker. На схеме видно,
что Docker Engine состоит из интерфейса командной строки (CLI), REST API и сер
вера Docker.
Сервер Docker, ключевой компонент Docker Engine, включает демон Docker,
dockerd, -  часть ПО, отвечающая за создание образов, контейнеров, сетей и т. д.
Интерфейс REST (REST API) взаимодействует с сервером Docker, а Docker CLI
позволяет пользователю взаимодействовать с Docker.
Далее схема показывает, что сервер Docker также включает containerd- часть ПО,
выполняющая всю тяжелую работу для сервера Docker, включая создание контей

неров и управление ими.
Containerd, в свою очередь , связан с другой частью ПО -   runC, которую можно
определить как низкоуровневую реализацию среды выполнения (запуска) контей
нера. Работая на базе runC, containerd добавляет такие функции, как управление
образами, контейнерами, сетями и т. д.
