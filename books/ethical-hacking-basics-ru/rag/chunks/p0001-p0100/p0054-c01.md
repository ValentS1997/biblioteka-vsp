   Фильтры пакетов могут иметь политику, управляющую поведением фильтра. Это означает, что существует общее правило,
   которое применяется ко всему, если не применяются исключения. По умолчанию, Политика запрета - наиболее безопасный
   способ реализации фильтра пакетов, которая отбрасывает все, что не разрешено явно. У вас также может быть настроена
   политика принятия, которая означает, что все разрешено, если что-то явно не заблокировано.

   Возможно, вы сталкивались с фильтрами пакетов, если используете системы Linux. Брандмауэр, включенный в большинство
   дистрибутивов Linux, имеет и другие возможности: он также может функционировать как базовый пакетный фильтр. Вы
   можете установить политику для разных цепочек с помощью брандмауэра iptables  , который находится в ядре Linux.

   В качестве примера, в следующих строках кода показан запуск iptables для установки Политики запрета по умолчанию.
   Она отбрасывает (DROP - дропает) сетевые пакеты в цепочках INPUT (входящий трафик), OUTPUT (исходящий трафик) и
  FORWARD (пересылаемый трафик):

     [iptables Policy Settings]
     iptables -P INPUT DROP
     iptables -P OUTPUT DROP
     iptables -P FORWARD DROP

   Фильтрация пакетов является базовой по своей функциональности. Хотя эти фильтры пакетов могут быть полезны для
   входящего трафика или даже для предотвращения доступа внутренних пользователей к определенным портам или IP-
   адресам, они не подходят для более сложной фильтрации, например разрешения входящего трафика из внутренней, и
   запрета входящего из Интернета. Для этого нам нужно нечто большее, чем просто пакетный фильтр.

  Шаг 3

   Фильтры с отслеживанием состояния

   Вскоре после первоначальной разработки фильтров пакетов появились межсетевые экраны с отслеживанием состояния.
   Первый межсетевой экран с отслеживанием состояния был разработан в конце 1980-х годов, как и пакетные фильтры.
   Это типы межсетевых экранов, которые нам следует хорошо знать, поскольку они существуют уже порядка сорока лет.
   Однако это не означает, что эти фильтры с отслеживанием состояния использовались все это время. =)

   Межсетевой экран с отслеживанием состояния отслеживает состояние сообщений в ходе диалога между сервером и
   клиентом, другими словами, между отправителем и получателем. Это означает, что брандмауэр должен иметь таблицу
   состояний, чтобы он знал обо всех транспортных потоках, проходящих через него.

   В случае TCP-протокола теоретически это проще, поскольку флаги в сетевых пакетах предоставляют всю необходимую
   информацию. Сообщение, в котором установлен только флаг SYN, является новым (NEW) соединением. В этом состоянии он
   остается до тех пор, пока не завершится трехстороннее рукопожатие. В этот момент подключение считается установленным
   (ESTABLISHED). В некоторых случаях у вас могут быть связанные (RELATED) потоки сообщений. Например, протокол
   передачи файлов (FTP - File Transfer Protocol) иногда создает соединения с изнутри наружу, то есть от сервера к клиенту. В
   этом случае соединение сервер-клиент для передачи файла связано с управляющим соединением от клиента к серверу. Но
   даже при использовании TCP, флаги не рассказывают всей истории подключения. Ведь это было бы достаточно легко -
   отправлять сообщения с правильными установленными флагами, чтобы пройти через брандмауэр, который проверяет
   только правильность выставленного флага, чтобы определить состояние связи.

   Протокол UDP не имеет состояния, присущего предыдущему протоколу. Там нет никакого рукопожатия, и, соответственно, это
   делает невозможным контроль по любым флагам или заголовкам, чтобы определить состояние. Однако брандмауэры с
   отслеживанием состояния не просто смотрят на флаги или заголовки. Они отслеживают все потоки связи, поэтому не
   полагаются на сам транспортный протокол.
