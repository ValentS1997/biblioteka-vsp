   yy 3 — идентификатор проекта из коллекции;
   yy tasks — коллекция задач проекта с идентификатором 3;
   yy 1 — идентификатор задачи из коллекции.
  Кроме того, при доступе к ресурсам в конец URL при обращении от клиента
можно добавлять строку запроса:
   http://www.domain.com/api/v1/todo/projects/3/tasks?id=1
  По сути, эти два примера равнозначны и различаются только способами обраще
ния к сервису для получения ресурса. В первом случае идентификаторы ресурсов
указываются в формируемом пути: projects/{proj-id}/tasks/{task-id}, а во втором
используется комбинация первого и строки запроса (query string), добавляемой
к заголовку отправляемого HTTP-сообщения: projects/{proj-id}/tasks?id={task-
id}. Можно даже сформировать доступ к задаче, перенеся идентификатор проекта
в строку запроса:
   http://www.domain.com/api/v1/todo/projects/tasks?projID=3&taskID=1
   Строка запроса может использоваться даже для замены тела отправляемого
сообщения, так как, по сути, представляет собой связку пар «ключ=значение», ко
торая начинается с символа вопросительного знака. В качестве разделителя между
парами выступает символ &.
  Хорошее правило при формировании REST URL — представлять ресурс су
ществительным, а не глаголом. Да и вообще наличие глаголов в пути к ресурсу
нежелательно (но иногда имеет место). Это связано с тем, что существительные
обладают свойствами, тогда как глагол описывает действия. В связи с этим для
того, чтобы на стороне сервера понять, какие действия необходимо выполнить над
ресурсом, нужно проанализировать, каким из HTTP-запросов было выполнено
обращение по URL: GET, PUT, POST или DELETE.
  Кроме того, рекомендуется использовать версионирование API, поскольку
оно позволяет избежать проблем, связанных с переходом на новую версию: не все
клиенты могут сделать это мгновенно, а разработчикам нужно время на доработку
и тестирование. В некоторых ситуациях требуемый функционал новой версии API
может работать не совсем корректно либо быть обратно несовместимым с преды
дущей версией, и тогда можно вернуться на старую версию с проверенной годами
функциональностью. Конечно, со временем старые версии будут удаляться, но
главное, что это происходит не слишком резко!

8.5.4. Разработка спецификации и документирование API
Для проектирования и документации API разрабатываемого сервиса мы восполь
зуемся такими расширениями, как OpenAPI (Swagger) Editor и Swagger Viewer для
VS Code. Первое будем использовать для разработки спецификации в формате
OpenAPI v.3, а второе — для ее визуализации. Кроме того, для этих действий можно
использовать и веб-редактор сервиса Swagger (https://editor.swagger.io/, но на сего
