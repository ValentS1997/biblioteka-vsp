2.2.3. Удаление неиспользуемых зависимостей
Иногда при создании приложения в коде указываются внешние зависимости, кото
рые потом нигде не используются. Чтобы они не включались в финальную сборку
приложения, используйте следующую команду:

   go mod tidy
  Она гарантирует, что в файле go.mod есть только используемые внешние за
висимости.
  Чтобы вы могли увидеть пример такой ситуации, добавим в предыдущий проект
новую, неиспользуемую зависимость, введя в терминале команду:

   go get golang.org/x/time/rate

   После этого файл go.mod будет выглядеть примерно так:
   module golang/first

   go 1.24

   require github.com/google/uuid v1.6.0

   require golang.org/x/time v0.0.0–20220411224347–583f2d630306 // indirect
   Теперь запустите команду go mod tidy и удостоверьтесь, что модуль golang.org/x/
time/rate был удален из файла go.mod.

2.2.4. Версионирование модулей в Go
Вы, наверное, обратили внимание, что у каждой зависимости есть своя версия.
Разработчики этих библиотек могут достаточно часто вносить в них изменения:
исправлять ошибки, добавлять функциональность, перерабатывать архитекту
ру и т. д. Чтобы вы понимали, стоит ли переходить на новую версию библиотеки,
выступающую в виде зависимости в проекте, разберем, как в Go работает управ
ление версиями.
  В Go используется семантическое управление версиями. Версия состоит из трех
частей, разделенных точками:

   v{major_version}.{minor_version}.{patch_version}
   Буква v просто указывает на то, что это версия модуля (библиотеки). Далее идет
мажорная версия, значение которой увеличивается при внесении разработчиком
изменений в API (application programming interface), которые приводят к обратной
несовместимости и при переходе проекта на более новую версию потребуют дора
