## F-01 — [Source contradiction] — область действия namespace

- **p0219:** автор пишет, что «все операции с кластером, выполняемые с помощью утилиты kubectl, будут ограничены выбранным пространством имен» и что действия не затронут другое пространство.
- **p0230–p0231:** тот же источник прямо перечисляет cluster-scoped ресурсы `Node`, `Namespace`, `PersistentVolume` и команды `kubectl api-resources --namespaced=false`. **p0221/p0233** предупреждают, что Namespace не обеспечивает полной сетевой изоляции.
- **Смысловое противоречие:** нельзя трактовать первое обобщение как универсальную границу для `kubectl`, cluster-scoped API или изоляции сетевых соединений.
- **Решение:** читать Namespace как логическую область *namespaced* объектов; реальные допуски, RBAC и NetworkPolicy — **[Needs confirmation]**.

## F-02 — [Source wording/code mismatch] — YAML и команда создания Namespace

- **p0224:** текст раздела о декларативном Namespace предлагает `kubectl create` с путем к YAML.
- **p0225:** показанная команда — `kubectl apply -f custom-ns-2.yaml`, результат `namespace/custom-ns-2 created`.
- **Решение:** сохранить обе исходные записи, не отождествлять исходные процессы молча; `commands.md` показывает именно полный `apply` из p0225.

## F-03 — [Needs confirmation] — «все ресурсы» и kubectl get all

- **p0229:** `kubectl get all -n custom-ns` описан как способ получить «список всех ресурсов» в namespace.
- **p0230–p0231:** рядом обсуждается наличие других видов namespaced и cluster-scoped объектов.
- **Граница:** глава не проверяет исчерпывающий состав объектов, возвращаемых `get all`; нельзя считать её вывод полным инвентарём namespace для очистки/backup/аудита.
- **Решение:** команда сохранена как авторский пример; полнота **[Needs confirmation]**.

## F-04 — [Needs confirmation] — kubectl apply -n и metadata.namespace

- **p0226:** YAML `pod-in-namespace.yaml` задаёт `metadata.namespace: custom-ns`.
- **p0230:** текст утверждает, что флаг `-n` для `kubectl apply` переопределяет Namespace из YAML, позволяя дублировать ресурс между тестовой и production средами.
- **Граница:** в главе нет полной демонстрации CLI/result с конфликтующими значениями `-n` и `metadata.namespace`. Реальный результат зависит от неизвестного контекста/версии.
- **Решение:** не использовать утверждение как доказанный безопасный способ переноса между namespaces. **[Needs confirmation]**.

## F-05 — [Source wording/code mismatch] — межпространственный DNS

- **p0221:** указывается доступность сервисов из других namespaces через полное DNS-имя (FQDN); общение межпространственное по умолчанию разрешено.
- **p0231:** текст сначала утверждает, что под может обратиться к Service «только в том случае, если сервис находится в том же пространстве имен», а затем даёт FQDN `<сервис>.<пространство>.svc.cluster.local` для сервисов *других* namespaces.
- **Решение:** интерпретировать ограничение в контексте **короткого имени**, не переносить буквально на весь DNS и сеть; разрешения/полный DNS суффикс целевого кластера **[Needs confirmation]**.

## F-06 — [Needs confirmation] — minikube и доступные ресурсы

- **p0238:** указано, что minikube c Podman/Docker драйвером показывает ресурсы физической хостовой машины вместо ресурсов узла, поэтому рекомендуется VirtualBox.
- **Граница:** реальная топология и источник метрик не проверены, а данные `kubectl top node` — лишь авторский пример.
- **Решение:** не применять утверждение как универсальный закон драйвера; подтвердить среду и показания метрик отдельно.

## F-07 — [Source wording/code mismatch] — квоты против фактического расхода

- **p0240–p0241:** ResourceQuota описывается как предел суммарно **потребляемой** памяти и CPU namespace.
- **p0241–p0242:** конкретный YAML задаёт `hard.requests.cpu`, `requests.memory`, `limits.cpu`, `limits.memory`; `kubectl get quota` показывает Used/Hard по requests/limits. `kubectl top pod` выводит фактическое использование отдельно.
- **Граница:** пример доказывает контроль **учитываемых requests/limits** при создании объектов, а не реальную метрику потребления всех процессов.
- **Решение:** раздельно описывать quota admission, requests/limits и `top`; точное runtime enforcement **[Needs confirmation]**.

## F-08 — [Needs confirmation] — настройки LimitRange по умолчанию

- **p0245:** `default`, `defaultRequest`, `min`, `max` объясняются и приводится YAML. Текст также обещает fallback `max→default` и `min→defaultRequest`, если значения явно не заданы.
- **p0246:** `describe limitranges` демонстрирует фактические настройки для одного примера, а не проверяет все варианты fallback/отклонений.
- **Граница:** работа admission, влияние других LimitRange, точное поведение при неуказанных полях в текущем кластере **[Needs confirmation]**. Source-значения сохранены без изменений.

## F-09 — [Needs confirmation] — абсолютные рекомендации и влияние limits

- **p0234–p0237:** автор пишет, что Pod без limits по умолчанию может потреблять все ресурсы узла и что `requests` *всегда* должны сопровождаться `limits`. В тексте разграничены CPU-throttling и возможное завершение при memory limit.
- **Граница:** это исходная учебная рекомендация, а не проведённая проверка текущей политики конкретного кластера, соседних Pod или аварийного завершения приложения.
- **Решение:** сохранить смысл и не выводить универсальных SLA либо настроек без проверки.

## F-10 — [Needs confirmation] — восстановление Namespace

- **p0225:** прямо предупреждается об необратимом удалении Namespace со всеми ресурсами; советует хранить YAML.

- **Решение:** удаление Namespace выделять как деструктивное действие, не как автоматический rollback после создания.
