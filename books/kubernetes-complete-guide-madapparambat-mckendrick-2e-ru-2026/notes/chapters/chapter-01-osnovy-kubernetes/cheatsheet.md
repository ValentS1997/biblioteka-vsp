# Cheatsheet — Глава 1. Основы Kubernetes

Source: RAG `kubernetes-complete-guide-madapparambat-mckendrick-2e-ru-2026:p0034:c01` — `kubernetes-complete-guide-madapparambat-mckendrick-2e-ru-2026:p0070:c01`; PDF 34–70. Source policy: `rag_only`.

## Symptom / problem framing

**Проблема главы:** частые релизы, неодинаковые зависимости сервисов, рост числа серверов и контейнеров делают ручное развертывание и эксплуатацию трудоемкими. Контейнерный движок решает задачи упаковки и локального жизненного цикла; Kubernetes координирует множество контейнеров в рабочей среде (стр. 35–36, 48–52, 57–58).

## Read-only checks

В главе **нет готового набора read-only команд диагностики кластера**. Перед практической работой допустима лишь концептуальная оценка, без изменения среды:

1. Установить, используются ли контейнеры вообще (стр. 69).
2. Оценить число независимо сопровождаемых сервисов и сложность выпуска (стр. 43–48, 69).
3. Зафиксировать потребности в высокой доступности, изменении количества экземпляров, сетевых ограничениях и данных с сохранением состояния (стр. 62–69).
4. Определить границу container engine / orchestrator и характер платформы — локальная инфраструктура или облако (стр. 43, 57–58).

## Interpretation

- Небольшой проект с редкими обновлениями может оставаться монолитом (стр. 44, 47–48).
- Микросервисы помогают выпускать и масштабировать компоненты отдельно, но увеличивают сложность зависимостей, отладки и безопасности (стр. 45–48).
- Контейнеризация облегчает изоляцию окружений, но сама по себе не закрывает весь набор задач оркестрации production (стр. 49–52).
- Kubernetes не обязательно развертывать в публичном облаке (стр. 43).
- Kubernetes может оказаться избыточен, если контейнеров нет или их очень мало (стр. 69).
- Источник содержит формулировки, требующие дополнительной технической проверки; см. [source-findings.md](source-findings.md).

## Next action

На основе главы: определить эксплуатационные потребности и оценить, нужен ли оркестратор; далее изучить архитектуру кластера из главы 2. Переход к изменению реального кластера **не обоснован этой главой без отдельного плана и контекста** (стр. 69–71).

## Modifying action

**Пример из источника (стр. 65), не запускать без плана изменения:**

```bash
kubectl set image deploy/myapp myapp_container=myapp:1.0.0
```

Эффект по главе: сменить образ контейнера в Deployment. Риск: изменение рабочего приложения; возможны нестабильность и недоступность при некорректном релизе (стр. 64–65). Окружение, нужная версия и реальная цель **[Needs confirmation]**.
