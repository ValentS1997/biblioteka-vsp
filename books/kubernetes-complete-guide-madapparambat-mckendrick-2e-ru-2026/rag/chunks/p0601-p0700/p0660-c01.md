660     Глава 19   •  Продвинутые методы планирования подов

Теперь, когда мы разобрались с концепцией ограничений и допусков, перейдем
к практическим упражнениям. Выполните следующие шаги.

1. Если у вас все еще работает объект Deployment nginx-app с заданными ранее
   правилами предпочтения узлов, то в данный момент все его поды размещены
   на узле 1 (minikube). Правила предпочтения узлов были сформулированы
   таким образом, что поды не могут быть назначены узлу 2 и узлу 3. Посмо-
   трим, что произойдет, если задать для узла 1 ограничение machine-check-
   exception=memory:NoExecute:

    $ kubectl taint node minikube machine-check-exception=memory:NoExecute
    node/minikube tainted

2. Проверьте статус подов и узлы, которым они назначены:

    $ kubectl get pods --namespace default \
        --output=custom-columns="NAME:.metadata.name,STATUS:.status.phase,
    NODE:.spec.nodeName"
    NAME                         STATUS    NODE
    nginx-app-7d8c65464c-5j69n   Pending   <none>
    nginx-app-7d8c65464c-c8j58   Pending   <none>
    nginx-app-7d8c65464c-cnczc   Pending   <none>
    nginx-app-7d8c65464c-drpdh   Pending   <none>
    nginx-app-7d8c65464c-xss9b   Pending   <none>

   Все поды объекта Deployment находятся в состоянии Pending, поскольку
   планировщик kube-scheduler не смог найти узел, подходящий для их запуска.
3. Отредактируйте манифест ./nginx-deployment.yaml (или просмотрите гото-
  вый файл 04_taints/nginx-deployment.yaml), удалив правила предпочтения
   узлов (affinity). Вместо них определите допуск для ограничения machine-
   check-exception=memory:NoExecute с тайм-аутом 60 секунд:
   # 04_taints/nginx-deployment.yaml
   apiVersion: apps/v1
   kind: Deployment
   metadata:
     name: nginx-app
   spec:
     ...
     template:
       ...
       spec:
         tolerations:
           - key: machine-check-exception
             operator: Equal
             value: memory
             effect: NoExecute
             tolerationSeconds: 60
   ...<фрагмент опущен для краткости>...
