696     Глава 20   •  Автоматическое масштабирование подов и узлов в Kubernetes

В качестве демонстрации мы используем кластер GKE, состоящий из двух
узлов:

 $ kubectl get nodes -o custom-columns=NAME:.metadata.name,CPU_ALLOCATABLE:.
 status.allocatable.cpu,MEMORY_ALLOCATABLE:.status.allocatable.memory
 NAME                                    CPU_ALLOCATABLE   MEMORY_ALLOCATABLE
 gke-k8sdemo-default-pool-1bf4f185-6422  940m              2873304Ki
 gke-k8sdemo-default-pool-1bf4f185-csv0  940m              2873312Ki

z Этому кластеру доступно примерно 1,88 ядра ЦП и 5611,34 МиБ памяти.
z Помните, что часть ресурсов ЦП потребляется подами из пространства имен
   kube-system.
z Точный объем доступных ресурсов ЦП и памяти можно определить с по-
  мощью команды kubectl top nodes.

К сожалению, добиться предсказуемой и изменяющейся нагрузки на ЦП внутри
контейнера встроенными средствами невозможно. Поэтому для демонстрации
нам необходимо подготовить объект Deployment с шаблоном пода, который
позволит смоделировать такую ситуацию. Мы создадим объект Deployment
elastic-hamster (см. каталог Chapter20/ca в репозитории GitHub). Shell-
сценарий hamster.sh, непрерывно выполняющийся в контейнере, будет уве-
личивать нагрузку на основе значения TOTAL_HAMSTER_USAGE. С помощью это-
го значения мы зададим общий объем работы, который должны выполнить
все генераторы нагрузки во всех подах. Каждый под будет обращаться к API
Kubernetes, чтобы определить текущее число запущенных реплик объекта
Deployment. Затем общий объем необходимой работы будет поделен на коли-
чество реплик для вычисления нагрузки, приходящейся на каждый генератор.

Например, если задать общий объем работы для всех генераторов нагрузки рав-
ным 1,0 (что соответствует суммарному потреблению ресурсов ЦП в кластере)
и развернуть пять реплик, то каждый генератор будет выполнять объем работы
равный 1,0 / 5 = 0,2 (0,2 секунды активной работы и 0,8 секунды ожидания). Если
изменить число реплик в объекте Deployment до десяти, то каждый генератор
нагрузки будет работать в течение 0,1 секунды и 0,9 секунды находиться в со-
стоянии ожидания. Таким образом, совокупный объем работы всегда остается
равным 1,0, независимо от количества реплик. Такое поведение моделирует
реальную ситуацию, когда конечные пользователи генерируют трафик, который
необходимо обрабатывать, а нагрузка распределяется между репликами подов.
Чем больше реплик подов запущено, тем меньшую долю нагрузки приходится
обрабатывать каждой из них, что приводит к снижению среднего уровня по-
требления ресурсов ЦП одним подом.

         Для увеличения нагрузки вы можете применять любые знакомые вам инструмен-
         ты и методы. Тем не менее, чтобы не усложнять пример, мы используем упро-
        щенный подход для демонстрации роста нагрузки и процесса масштабирования.
