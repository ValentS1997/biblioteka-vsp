Теперь выполним тот же curl-запрос, что и раньше:

 $ kubectl -n web1 exec nginx1 -- curl 10.244.120.72
   % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                              Dload  Upload   Total   Spent    Left   Speed
 100   615  100   615    0     0   1280k      0 --:--:-- --:--:-- --:--:--   600k
 <!DOCTYPE html>
 <html>
 <head>
 <title>Welcome to nginx!</title>
 ...<фрагмент опущен для краткости>...

Как видите, все работает так же, как и до применения сетевых политик. Это
объясняется тем, что:

z поду nginx2 теперь явно разрешено принимать входящий трафик, поступа-
  ющий на порт 80 от пода nginx1 из пространства имен web1, при этом весь
   остальной трафик по-прежнему заблокирован;
z для пода nginx1 сетевая политика не задана, а значит, отправка всего исхо-
   дящего трафика разрешена по умолчанию.

Запомните: если для пода не определена сетевая политика, весь его входящий
и исходящий трафик разрешен по умолчанию.

Мы настоятельно рекомендуем всегда использовать объект NetworkPolicy вме-
сте с подами. Также учтите, что объекты NetworkPolicy можно применять для
создания брандмауэров на основе блоков CIDR, что бывает особенно полезно
при наличии доступа к подам кластера извне. Однако для настройки бранд
мауэров между подами предпочтительнее использовать метки и селекторы, как
и при настройке сервисов.

В следующем разделе мы поговорим о защите каналов связи между компонентами
Kubernetes с помощью TLS-сертификатов. Вы узнаете, как TLS-сертификаты
обеспечивают конфиденциальность передаваемых данных и безопасную ком-
муникацию между различными частями экосистемы Kubernetes.

Защита взаимодействий компонентов Kubernetes
с помощью TLS-сертификатов
Безопасное взаимодействие компонентов Kubernetes имеет критически важное
значение. Протоколы TLS (Transport Layer Security — безопасность транс-
портного уровня) и SSL (Secure Sockets Layer — уровень защищенных сокетов)
играют ключевую роль в шифровании передаваемых данных и установлении
доверия между сервисами.
