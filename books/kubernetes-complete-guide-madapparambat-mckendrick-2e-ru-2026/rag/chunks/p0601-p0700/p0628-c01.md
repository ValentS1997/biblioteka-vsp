Создайте под с помощью приведенного YAML-манифеста следующим образом:

 $ kubectl apply -f pod-with-security-context.yaml
 pod/security-context-demo created

После создания пода выполните несколько команд внутри контейнера, чтобы
проверить действие настроенного параметра securityContext:

 $ kubectl exec -it security-context-demo -- /bin/sh
 ~ $ id
 uid=1000 gid=1000 groups=1000
 ~ $ touch /testfile
 touch: /testfile: Read-only file system

Вы увидите сообщение об ошибке Read-only file system — это вполне ожидаемо.
Чтобы узнать больше о параметре securityContext в Kubernetes, обратитесь
к официальной документации: https://kubernetes.io/docs/tasks/configure-pod-container/
security-context/.
В следующем разделе мы обсудим управление сетевыми потоками в Kubernetes
с использованием объекта NetworkPolicy, позволяющего создавать своеобразные
сетевые брандмауэры, предотвращающие нежелательные взаимодействия
между подами.

Защита подов с помощью объекта NetworkPolicy
Объект NetworkPolicy (сетевая политика) — это последний ресурс, который мы
изучим в этой главе для получения целостного представления о механизмах
обеспечения безопасности в Kubernetes. Данный объект позволяет реализовать
сетевой брандмауэр прямо внутри кластера.

Причины для использования объекта NetworkPolicy
При управлении реальными рабочими нагрузками Kubernetes вам приходится
развертывать в рабочей среде все больше приложений, которые должны обме-
ниваться данными друг с другом.

Организация сетевого взаимодействия между компонентами — это одна из
ключевых задач микросервисной архитектуры. Большая часть этого взаи-
модействия происходит по сети, которую необходимо защищать с помощью
брандмауэров (межсетевых экранов).
