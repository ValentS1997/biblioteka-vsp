612     Глава 18   •  Безопасность в системе Kubernetes

         Контроль доступа на основе содержимого полей конкретных объектов осу-
         ществляют контроллеры допуска. Их срабатывание происходит после этапа
         авторизации и только в том случае, если выполнение запроса было разрешено.
         Подробнее о контроллерах допуска мы поговорим далее в этой главе.

Результат аутентификации запроса API-сервером Kubernetes выражается
в наборе дополнительных атрибутов, таких как пользователь, группа, глагол
API-запроса, HTTP-метод и др. Затем эти атрибуты передаются модулям авто
ризации, которые на их основе определяют, имеет ли пользователь право выпол-
нить запрашиваемое действие. Если какой-либо из модулей отклоняет запрос,
пользователь получает код HTTP-ответа 403 (Forbidden).

         Важно учитывать различия между кодами HTTP-ответов. Код 401 (Unauthorized)
          означает, что система не распознала пользователя, например, из-за неверных
         учетных данных или отсутствия соответствующей учетной записи. Код 403
           (Forbidden) означает, что пользователь успешно аутентифицирован, но не имеет
         прав на выполнение запрошенного действия. Это различие особенно полезно
         учитывать при диагностике проблем с доступом к кластеру Kubernetes.

В Kubernetes предусмотрено несколько режимов авторизации, которые задаются
с помощью параметра --authorization-mode при запуске API-сервера:

# /etc/kubernetes/manifests/kube-apiserver.yaml
...<фрагмент опущен для краткости>...
spec:
  containers:
  - command:
    - kube-apiserver
    - --advertise-address=192.168.59.154
    - --allow-privileged=true
    - --authorization-mode=Node,RBAC
...<фрагмент опущен для краткости>...

Kubernetes поддерживает следующие режимы авторизации.

z RBAC (Role-Based Access Control — управление доступом на основе ролей).
   Позволяет управлять доступом с помощью ролей и привилегий. RBAC —
   это один из отраслевых стандартов управления доступом, применяемый
   не только в Kubernetes. Роли определяют набор разрешений, который
  можно назначить пользователям или группам. Это обеспечивает гибкое
   управление доступом в соответствии с принципом наименьших привилегий.
   Например, можно создать роль, предоставляющую доступ только к опреде-
  ленным файлам или ресурсам, а затем связать эту роль с пользователями
