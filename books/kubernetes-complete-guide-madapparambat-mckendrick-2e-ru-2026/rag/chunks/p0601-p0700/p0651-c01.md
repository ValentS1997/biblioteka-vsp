6. Примените манифест к кластеру:

    $ kubectl apply -f 02_nodeselector/nginx-deployment-slow.yaml

   Проверьте статус подов и узлы, которым они назначены:

    $ kubectl get pods --namespace default \
        --output=custom-columns="NAME:.metadata.name,STATUS:.status.phase,
    NODE:.spec.nodeName"
    NAME                        STATUS    NODE
    nginx-app-6c5b8b758-48c5t   Running   minikube-m03
    nginx-app-6c5b8b758-pfmvg   Running   minikube-m03
    nginx-app-6c5b8b758-v6rhj   Running   minikube-m02
    nginx-app-6c5b8b758-zqvqm   Running   minikube-m02
    nginx-app-9cc8544f4-7dwcd   Pending   <none>
    nginx-app-9cc8544f4-cz947   Pending   <none>
    nginx-app-9cc8544f4-lfqqj   Pending   <none>

   Причина, по которой три новых пода находятся в состоянии ожидания,
   а четыре старых пода продолжают работать, заключается в стандартных на-
   стройках обновления объекта Deployment. По умолчанию значение параме-
   тра maxSurge равно 25 % от числа реплик пода (при этом абсолютное значение
   округляется в бо́льшую сторону), поэтому в нашем случае можно создать два
   дополнительных пода сверх желаемых пяти. В итоге в кластере оказывается
   семь подов. Значение параметра maxUnavailable также равно 25 % от числа
   реплик (но его абсолютное значение округляется в меньшую сторону). Это
   означает, что один из пяти подов может быть недоступным. Другими слова-
   ми, четыре пода должны находиться в состоянии Running. А поскольку новые
   поды, находящиеся в состоянии Pending, не могут быть назначены узлу, объ-
   ект Deployment не может продолжить обновление. В такой ситуации можно
   выполнить откат к предыдущей версии объекта Deployment или изменить
   значение nodeSelector на то, которое соответствует существующим узлам.
  Альтернативным вариантом является добавление нового узла с нужной
   меткой или присвоение недостающих меток уже существующим узлам без
   выполнения отката.

Далее мы обсудим более продвинутый механизм планирования подов, а именно
правила предпочтения узлов.
