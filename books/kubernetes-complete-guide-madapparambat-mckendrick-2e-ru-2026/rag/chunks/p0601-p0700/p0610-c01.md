610     Глава 18   •  Безопасность в системе Kubernetes

Настройка OIDC в API-сервере Kubernetes. Включение поддержки OIDC
в Kubernetes требует настройки API-сервера с использованием ряда параметров.

z  --oidc-issuer-url — URL-адрес OIDC-провайдера, используемый системой
   Kubernetes для проверки подлинности токенов.
z --oidc-client-id — идентификатор клиента, используемый системой
   Kubernetes при аутентификации в IdP-сервисе.
z  --oidc-username-claim — указывает, какое утверждение (claim) в токене со-
   поставляется с именем пользователя Kubernetes.
z --oidc-groups-claim — сопоставляет группы в IdP-сервисе с группами
   Kubernetes для управления ролями RBAC.

Более подробные инструкции по настройке конкретных OIDC-провайдеров
можно найти в официальных источниках: https://dexidp.io/docs/guides/kubernetes/
и https://kubernetes.io/docs/reference/access-authn-authz/authentication/.
В целом OIDC представляет собой предпочтительный метод аутентификации
в Kubernetes, особенно при развертывании кластеров производственного уровня
в облачных средах.
Другие методы аутентификации. Kubernetes поддерживает несколько допол-
нительных методов аутентификации, предназначенных для более сложных сце-
нариев, например для интеграции с LDAP или Kerberos. Одним из них является
аутентификация с помощью прокси-сервера.

При использовании аутентифицирующего прокси, установленного перед API-
сервером Kubernetes, этот API-сервер можно настроить таким образом, чтобы
он извлекал информацию о пользователе из определенных HTTP-заголовков.
Иными словами, прокси выполняет аутентификацию пользователя, а затем
передает полученные данные вместе с запросом в виде дополнительных за-
головков.

Подробнее об этом методе можно узнать в официальной документации по адре-
су https://kubernetes.io/docs/reference/access-authn-authz/authentication/#authenticating-
proxy.
Еще одним методом является аутентификация токенов с помощью вебхуков,
при которой API-сервер Kubernetes использует внешний сервис для проверки
bearer-токенов. В рамках этого подхода API-сервер отправляет данные в виде
объекта TokenReview через HTTP-запрос типа POST. Внешний сервис выполняет
проверку и возвращает объект TokenReview с результатами верификации.

Подробнее об этом методе можно узнать в официальной документации по
адресу https://kubernetes.io/docs/reference/access-authn-authz/authentication/#webhook-
token-authentication.
