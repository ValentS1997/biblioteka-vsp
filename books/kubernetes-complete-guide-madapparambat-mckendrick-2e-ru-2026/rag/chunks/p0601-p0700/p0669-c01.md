Запросы и лимиты ресурсов, доступных подам     669

z Горизонтальное автомасштабирование подов — динамически изменяет
   число реплик подов объектов Deployment или StatefulSet. Эти объекты из-
   начально предусматривают удобные механизмы масштабирования, однако
   регулировка количества реплик может быть автоматизирована с помощью
   горизонтального автоскейлера (объекта HorizontalPodAutoscaler, HPA).
z Горизонтальное автомасштабирование узлов — это еще одно измерение
   горизонтального масштабирования, только на уровне узлов Kubernetes.
  Вы можете масштабировать весь кластер, добавляя или удаляя узлы. Раз-
   умеется, для этого кластер должен быть развернут в среде, поддерживаю-
  щей динамическое выделение машин, например, в облаке. Данный вариант
   автомасштабирования реализуется с помощью инструмента автомасшта-
   бирования кластера или кластерного автоскейлера (Cluster Autoscaler, CA),
   предоставляемого некоторыми облачными провайдерами.

Технические требования
Для работы с этой главой вам потребуется:
z развернутый кластер Kubernetes (желательно многоузловой);
z многоузловой кластер GKE (Google Kubernetes Engine), необходимый для
   вертикального автомасштабирования подов и автомасштабирования узлов;
z интерфейс командной строки kubectl, установленный на локальной машине
  и настроенный для управления кластером Kubernetes.

Инструкции по созданию кластера Kubernetes и настройке клиента kubectl
приведены в главах 2 и 3.

В главах 15, 16 и 17 рассматривался процесс развертывания полнофункцио-
нальных кластеров Kubernetes в различных облачных средах и установки со-
ответствующих CLI-инструментов для управления ими.

Примеры кода для этой главы можно загрузить из официального репозитория
GitHub по адресу https://github.com/PacktPublishing/The-Kubernetes-Bible-Second-Edition/
tree/main/Chapter20.

Запросы и лимиты ресурсов, доступных подам
Прежде чем перейти к теме автомасштабирования в Kubernetes, нам следует
обсудить способы управления уровнем потребления вычислительных ресур-
сов (ЦП и память) контейнерами подов. Это позволяет точнее планировать
потребности кластера и, что особенно важно, предотвращать ситуации, когда
один контейнер потребляет все вычислительные ресурсы, лишая другие поды
возможности обслуживать запросы.
