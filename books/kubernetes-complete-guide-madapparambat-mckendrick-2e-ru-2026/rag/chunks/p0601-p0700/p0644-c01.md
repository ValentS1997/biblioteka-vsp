644     Глава 19   •  Продвинутые методы планирования подов

          Корректность решений планировщика гарантируется только в момент первона-
          чального назначения пода узлу. После запуска пода компонент kube-scheduler
         не выполняет повторное планирование на протяжении всего времени работы
         пода (которое может длиться дни или даже месяцы). Таким образом, даже если
         под перестанет соответствовать узлу согласно вашим правилам, он продолжит
          работу. Повторное планирование произойдет только в случае завершения ра-
         боты этого пода и создания нового1.

Для управления распределением подов в Kubernetes можно использовать сле-
дующие механизмы:

z поле nodeSelector для сопоставления с метками узлов;
z правила предпочтения (affinity) и антипредпочтения (anti-affinity) узлов;
z поле nodeName;
z ограничения распределения подов по топологии (pod topology spread
   constraints);
z ограничения (taint) и допуски (toleration).

В следующих разделах мы подробно рассмотрим эти механизмы. Прежде чем
переходить к практическим упражнениям по планированию подов, убедитесь
в наличии многоузлового кластера Kubernetes.

В нашем случае будет использоваться кластер, развернутый с помощью mini
kube, как показано ниже (вы можете изменить драйвер на kvm2, Docker или
Podman):

 $ minikube start \
     --driver=virtualbox \
     --nodes 3 \
     --cni calico \
     --cpus=2 \
     --memory=2g \
     --kubernetes-version=v1.30.0 \
     --container-runtime=containerd

Аргумент --nodes=3 указывает minikube развернуть кластер Kubernetes с тремя
узлами, причем первый будет управляющим узлом, а второй и третий — вы-
числительными:

 $ kubectl get nodes
 NAME           STATUS   ROLES           AGE     VERSION
 minikube       Ready    control-plane   3m34s   v1.30.0

1  Для решения этой проблемы есть инструмент kubernetes-sigs/descheduler, который
   может быть установлен как Job/CronJob или Deployment в существующий кластер.
