Аутентификация и авторизация: управление пользовательским доступом     617

 8. В результате назначения учетной записи сервиса pod-logger соответствую-
   щий объект Secret с JWT-токеном будет смонтирован в файловую систему
    контейнера по пути /var/run/secrets/kubernetes.io/serviceaccount/token.
    Убедиться в этом можно с помощью команды kubectl exec:

     $ kubectl exec -it -n rbac-demo-ns pod-logger-app -- bash
     root@pod-logger-app:/# ls -l /var/run/secrets/kubernetes.io/serviceaccount/
     total 0
     lrwxrwxrwx 1 root root 13 Jul 14 03:33 ca.crt      -> ..data/ca.crt
     lrwxrwxrwx 1 root root 16 Jul 14 03:33 namespace   -> ..data/namespace
     lrwxrwxrwx 1 root root 12 Jul 14 03:33 token       -> ..data/token

 9. Переопределенные команды выполняются в бесконечном цикле в обо-
    лочке Linux (например, bash) с десятисекундными интервалами. В рамках
   каждой итерации мы обращаемся к конечной точке API Kubernetes (https://
    kubernetes/api/v1/namespaces/rbac-demo-ns/pods), чтобы получить список по-
    дов в пространстве имен rbac-demo-ns, с помощью HTTP-запроса типа
    GET и утилиты curl. Для прохождения аутентификации мы передаем со-
   держимое файла /var/run/secrets/kubernetes.io/serviceaccount/token
    в виде bearer-токена в заголовке запроса Authorization. Кроме того, мы
    передаем путь к CA-сертификату для проверки подлинности удаленного
    сервера с помощью аргумента cacert. Этот сертификат автоматически до-
    бавляется в путь /var/run/secrets/kubernetes.io/serviceaccount/ca.crt
    средой выполнения Kubernetes. При просмотре логов вы увидите множество
   сообщений с кодом HTTP-ответа 403 (Forbidden). Это объясняется тем,
    что для данной учетной записи сервиса пока не создан объект RoleBinding,
   связывающий ее с ролью pod-reader.
