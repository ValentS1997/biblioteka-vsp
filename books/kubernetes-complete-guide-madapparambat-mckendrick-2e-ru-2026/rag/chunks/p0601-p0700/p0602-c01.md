602     Глава 18   •  Безопасность в системе Kubernetes

В целом применение токенов ServiceAccount для внешней аутентификации
допустимо только в средах разработки и тестирования при невозможности
использования соответствующих услуг внешнего провайдера. Применять этот
метод в рабочей среде не рекомендуется по соображениям безопасности. Далее
мы поговорим об использовании клиентских сертификатов X.509 для аутенти-
фикации в API Kubernetes.
Клиентские сертификаты X.509. Использование клиентских сертифика-
тов X.509 является одним из отраслевых стандартов в системах аутентифика-
ции. Однако важно обеспечить надежное управление процессами подписания, от-
зыва и ротации сертификатов. В противном случае можно столкнуться с теми же
проблемами безопасности, что и при использовании токенов ServiceAccount.
Подробнее о сертификатах X.509 и связанных с ними процессах можно узнать
по адресу https://www.ssl.com/faqs/what-is-an-x-509-certificate/.

Применение этого метода в Kubernetes выглядит следующим образом.
1. API-сервер Kubernetes запускается с параметром --client-ca-file. Этот
   параметр указывает на файл с информацией о центре сертификации
   (CA, Certification authority), который используется для проверки подлин-
   ности клиентских сертификатов, предоставленных при аутентификации.
  Вы можете задать пользовательский CA-сертификат или использовать
   CA-сертификат по умолчанию, созданный при развертывании кластера.
   Например, при использовании кластера minikube можно увидеть, что в кон-
   фигурации kube-apiserver уже задан CA-сертификат по умолчанию:
   # /etc/kubernetes/manifests/kube-apiserver.yaml
   ... <фрагмент опущен для краткости> ...
   spec:
     containers:
     - command:
       - kube-apiserver
       - --advertise-address=192.168.59.154
       - --allow-privileged=true
       - --authorization-mode=Node,RBAC
       - --client-ca-file=/var/lib/minikube/certs/ca.crt
   ... <фрагмент опущен для краткости> ...
2. Для аутентификации на API-сервере пользователи должны запросить у цен-
   тра сертификации клиентский сертификат X.509. Этот процесс должен
   быть защищенным и контролируемым. После успешной аутентификации
   содержимое поля сертификата CN (Common Name) используется в качестве
   атрибута username (имя пользователя). Начиная с версии Kubernetes 1.19,
   для управления запросами на подпись сертификатов можно использовать
  API Certificates. Подробнее об этом можно узнать в официальной докумен-
   тации по адресу https://kubernetes.io/docs/reference/access-authn-authz/certificate-
    signing-requests/.
