Продвинутая маршрутизация трафика с помощью объекта Ingress     717

 $ kubectl get IngressClass -o yaml
 apiVersion: v1
 items:
   - apiVersion: networking.k8s.io/v1
     kind: IngressClass
     metadata:
       name: nginx
       annotations:
         ingressclass.kubernetes.io/is-default-class: "true"
 ...<фрагмент опущен для краткости>...
     spec:
       controller: k8s.io/ingress-nginx

В приведенном выше фрагменте можно отметить следующее:
z именем IngressClass является nginx (.metadata.name);
z  присутствует аннотация ingressclass.kubernetes.io/is-default-class: "true".

В следующем подразделе мы рассмотрим специализированный контроллер
Azure AGIC для кластера AKS.

Контроллер Azure AGIC для кластера AKS
Как было сказано в предыдущем подразделе, использование Ingress-контроллера
Nginx является достаточно гибким способом маршрутизации трафика внутри
кластера Kubernetes. Однако при переключении на облачные сервисы, такие как
AKS (Azure Kubernetes Service), этот подход может усложниться из-за несколь-
ких уровней балансировки нагрузки, увеличивающих число потенциальных
точек отказа.

Для решения этих проблем AKS предлагает собственный сервис балансировки
нагрузки уровня L7 — Azure AGIC (Application Gateway Ingress Controller, кон-
троллер входящего трафика для шлюза прикладного уровня). AGIC работает
в связке с сетевыми службами Azure и обеспечивает значительно более эф-
фективную и надежную маршрутизацию трафика, позволяя балансировщику
нагрузки напрямую взаимодействовать с подами через их приватные IP-адреса.
Это является возможным благодаря таким функциям Azure SDN, как VNet
Peering (пиринг виртуальных сетей).

Причины для использования AGIC в AKS
AGIC стоит использовать в AKS по следующим причинам.
z Упрощение процесса балансировки нагрузки. AGIC устраняет необходимость
   в использовании отдельного балансировщика нагрузки Azure, который
   должен был бы проксировать запросы к подам Ingress-контроллера Nginx
