208     Глава 5   •  Использование многоконтейнерных подов

Но зачем вообще нужен посредник для доступа к внешним базам данных? Вот
основные преимущества, которые предоставляет этот паттерн проектирования:

z разделение логики приложения и конфигурации SQL;
z управление сертификатами SSL/TLS (Secure Sockets Layer/Transport Layer
   Security — уровень защищенных сокетов/безопасность транспортного уровня).

Важно отметить, что паттерн Ambassador (Посредник) применяется не только
для создания SQL-прокси — этот пример лишь иллюстрирует его возможности.
Учтите, что такой посредник предназначен исключительно для организации
исходящих подключений от основного контейнера к внешним ресурсам (напри-
мер, к хранилищам данных или API). То есть он не является точкой входа в кла-
стер! Теперь посмотрим, как можно описать такой SQL-прокси в YAML-файле.

Пример пода с контейнером-посредником
Итак, вы познакомились с контейнерами-посредниками, а теперь рассмотрим
способ их создания в Kubernetes. Следующий YAML-манифест описывает под,
включающий два контейнера:

z  nginx-app, созданный на основе образа nginx:latest;
z  sql-ambassador-proxy, созданный на основе образа mysql-proxy:latest.

Приведенный пример предназначен исключительно для демонстрации концеп-
ции SQL-прокси. Для полноценного тестирования его работы вам необходим
действующий экземпляр AWS RDS (Relational Database Service), доступный из
кластера Kubernetes, а также подходящее приложение для проверки операций
с базой данных.

# nginx-with-ambassador.yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-with-ambassador
spec:
  containers:
    - name: mysql-proxy-ambassador-container
      image: mysql-proxy:latest
      ports:
        - containerPort: 3306
      env:
      - name: DB_HOST
        value: mysql.xxx.us-east-1.rds.amazonaws.com
    - name: nginx-container
      image: nginx:latest
