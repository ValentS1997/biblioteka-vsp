376     Глава 10   •  Запуск рабочих нагрузок производственного уровня

Сначала создадим простой манифест пода nginx-pod-bare.yaml:
# nginx-pod-bare.yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod-bare-example
  namespace: rs-ns
  labels:
    app: nginx
    environment: test
spec:
  containers:
    - name: nginx
      image: nginx:1.17
      ports:
        - containerPort: 80

Метаданные этого пода должны содержать метки, совпадающие с селектором
ReplicaSet. Примените этот манифест к кластеру:

 $ kubectl apply -f nginx-pod-bare.yaml
 pod/nginx-pod-bare-example created
 $ kubectl get pods
 NAME                             READY   STATUS        RESTARTS   AGE
 nginx-pod-bare-example           0/1     Terminating   0          1s
 nginx-replicaset-example-74kq9   1/1     Running       0          23h
 nginx-replicaset-example-qfvx6   1/1     Running       0          23h
 nginx-replicaset-example-s5cwc   1/1     Running       0          23h

Сразу после этого проверьте события, связанные с объектом ReplicaSet, выпол-
нив команду kubectl describe:

 $ kubectl describe rs/nginx-replicaset-example -n rs-ns
 ...
 Events:
   Type    Reason            Age   From                    Message
   ----    ------            ----  ----                    -------
 ...
   Normal  SuccessfulDelete  29s   replicaset-controller   Deleted pod:
                                                           nginx-pod-bare-example

Как видите, объект ReplicaSet незамедлительно обнаружил новый под с совпа-
дающими метками и удалил его.

         Аналогичным образом можно вывести поды из-под управления ReplicaSet, из-
         менив их метки так, чтобы они больше не соответствовали его селектору. Это
         бывает актуально при отладке и расследовании инцидентов.

В следующем подразделе вы узнаете, как объект ReplicaSet помогает обеспечить
высокую доступность и отказоустойчивость приложения.
