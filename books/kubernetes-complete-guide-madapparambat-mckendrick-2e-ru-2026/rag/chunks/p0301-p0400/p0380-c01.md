380     Глава 10   •  Запуск рабочих нагрузок производственного уровня

будет выполнять HTTP-запрос типа GET к пути / и проверять, возвращает ли
он код успешного ответа. Процесс nginx в контейнере может оставаться исправ-
ным (пока не произойдет сбой), но это не гарантирует работоспособность пода
в целом. Если веб-сервер не может корректно предоставлять контент, значит,
процесс работает, но возникла другая ошибка и такой под больше не должен
использоваться. Мы смоделируем эту ситуацию, удалив файл /index.html из
контейнера, что приведет к сбою проверки жизнеспособности.
Сначала создадим YAML-манифест nginx-replicaset-livenessprobe.yaml для
нового объекта nginx-replicaset-livenessprobe-example:

# nginx-replicaset-livenessprobe.yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: nginx-replicaset-livenessprobe-example
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
      environment: test
  template:
    metadata:
      labels:
        app: nginx
        environment: test
    spec:
      containers:
        - name: nginx
          image: nginx:1.17
          ports:
            - containerPort: 80
          livenessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 2
            periodSeconds: 2

Единственным отличием данного объекта ReplicaSet от предыдущих является
выделенный блок с определением проверки жизнеспособности. Эта проверка
предполагает выполнение HTTP-запроса типа GET к пути / на порте 80 контей-
нера с интервалом 2 секунды (periodSeconds). Первая проверка будет выполне-
на через 2 секунды после запуска контейнера (initialDelaySeconds).

        При модификации существующего объекта ReplicaSet необходимо сначала
          удалить его и создать заново, чтобы применить изменения к шаблону пода.
