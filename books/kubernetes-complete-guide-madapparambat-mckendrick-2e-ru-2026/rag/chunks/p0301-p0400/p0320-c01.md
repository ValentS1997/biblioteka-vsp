320     Глава 8   •  Публикация подов с помощью сервисов

Реализация проверки жизнеспособности
Проверка жизнеспособности проводится по расписанию для отслеживания со-
стояния приложения в долгосрочной перспективе. Эта проверка выполняется
компонентом kubelet и предусматривает несколько вариантов.

z Команда. Выполнение команды в контейнере. Код выхода, равный 0, озна-
   чает, что под работает корректно.
z HTTP. Выполнение HTTP-запроса к поду. Код ответа >=200 и <400 говорит
   о работоспособности пода.
z TCP. Попытка установить TCP-соединение. Если соединение успешно уста-
   новлено, значит, под работает нормально.
z gRPC. Если приложение поддерживает и реализует протокол проверки ра-
   ботоспособности gRPC (gRPC Health Checking Protocol).

Для любой проверки жизнеспособности необходимо задать параметр periodSe
conds (в виде целого числа), указывающий интервал между последовательны-
ми проверками (в секундах). Дополнительно можно использовать параметр
initialDelaySeconds, определяющий задержку перед выполнением первой про-
верки. Это важно, так как в некоторых случаях из-за слишком ранней проверки
«неработоспособным» может быть признано приложение, которое просто еще
не успело полностью запуститься.
Конфигурация LivenessProbe задается в YAML-манифесте пода (а не сервиса).
При этом каждый контейнер в поде может предусматривать собственную про-
верку.

Проверка жизнеспособности с помощью HTTP-запроса
HTTP-проверки в Kubernetes предусматривают дополнительные настраивае
мые поля: host, scheme, path, httpHeaders, port, позволяющие регулировать спо-
соб выполнения запросов для проверки состояния приложения. Ниже приведен
пример манифеста, который проверяет работоспособность пода, выполняя
HTTP-запрос к конечной точке /healthcheck в контейнере nginx:

# nginx-pod-with-liveness-http.yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod-with-liveness-http
spec:
  containers:
    - name: nginx-pod-with-liveness-http
      image: nginx
      livenessProbe:
