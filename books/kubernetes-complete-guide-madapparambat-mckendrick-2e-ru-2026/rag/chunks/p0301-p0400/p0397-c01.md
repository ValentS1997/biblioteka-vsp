Знакомство с объектом Deployment     397

Все эти проверки чрезвычайно полезны при настройке объекта Deployment.
Всегда старайтесь предвидеть возможные сценарии жизненного цикла про-
цессов, работающих в контейнерах, и настраивать соответствующие проверки
для развертываний.

Учтите, что по умолчанию контейнеры в подах запускаются без каких-либо про-
верок. Система Kubernetes будет направлять трафик к контейнерам с подами,
работающим за сервисом, только если эти контейнеры успешно стартовали.
В случае сбоя контейнеры будут перезапущены согласно политике always-
restart, используемой по умолчанию. Это означает, что ответственность за
выбор проверок и их параметров в каждом конкретном случае лежит на вас.
Важно также понимать возможные последствия некорректной настройки та-
ких проверок. Например, чрезмерно строгая проверка жизнеспособности со
слишком короткими тайм-аутами может привести к ошибочному перезапуску
контейнеров, снижающему доступность приложения.
Теперь посмотрим, как можно настроить проверку готовности объекта Deploy
ment и как она работает в реальном времени.

         Более подробно о настройке других типов проверок можно узнать в главе 8
         данной книги, а также в официальной документации по адресу https://kubernetes.
           io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/.

Используемый нами объект Deployment с сервером Nginx очень прост и не
требует настройки отдельной проверки готовности. Вместо этого мы настроим
контейнер так, чтобы иметь возможность вызывать успешное или неуспешное
прохождение проверки готовности по своему усмотрению. Идея состоит в сле-
дующем: во время инициализации контейнера создается пустой файл /usr/
share/nginx/html/ready, который будет доступен по пути /ready и предостав-
ляться сервером Nginx в качестве обычного файла. Затем настраивается про-
верка готовности типа httpGet, которая периодически обращается к пути /ready
и признает контейнер готовым при получении кода, означающего успешную об-
работку запроса. Таким образом, удаляя или воссоздавая файл ready с помощью
команды kubectl exec, мы можем легко моделировать сбои в подах, приводящие
к провалу или успешному прохождению проверки готовности.

Для настройки и тестирования проверки готовности выполните следующие шаги.

1. Удалите существующий объект Deployment с помощью команды:

    $ kubectl delete deployment nginx-deployment-example

2. Создайте новый YAML-манифест объекта Deployment:
   # nginx-deployment-readinessprobe.yaml
   apiVersion: apps/v1
   kind: Deployment
