Назначение постоянного хранилища данных     329

Убедимся, что файлы доступны в каталоге /usr/share/nginx/hello, указанном
в качестве пути монтирования:

 $ kubectl exec -t pod/nginx-hello -- ls -al /usr/share/nginx/html/hello/
 total 12
 ... <фрагмент опущен для краткости> ...
 lrwxrwxrwx 1 root root 18 Sep 7 21:19 hello1.html -> ..data/hello1.html
 lrwxrwxrwx 1 root root 18 Sep 7 21:19 hello2.html -> ..data/hello2.html

А теперь убедимся, что данные действительно предоставляются сервером
Nginx, выполнив перенаправление портов, чтобы не настраивать сервис:

 $ kubectl port-forward nginx-hello 8080:80
 Forwarding from 127.0.0.1:8080 -> 80
 Forwarding from [::1]:8080 -> 80

Затем во втором терминале можно выполнить curl-запросы к обоим URL-
адресам:

 $ curl 127.0.0.1:8080/hello/hello1.html
 <html>
   hello world 1
 </html>

 $ curl 127.0.0.1:8080/hello/hello2.html
 <html>
   hello world 2
 </html>

Это неплохое начало, однако у таких объектов есть ограничение по объему
хранимых данных. Поскольку они зависят от хранилища etcd, во избежание
проблем с производительностью этот лимит составляет 1,5 Мбайт (https://etcd.io/
docs/v3.5/dev-guide/limit). Следующая группа объектов позволяет приложению
хранить данные, объем которых ограничен емкостью хранилища хостовой
системы.

Представим кластер Kubernetes с двумя рабочими узлами, на которых могут
размещаться поды, и рассмотрим пять типов томов:

z  emptyDir;
z  hostPath;
z локальный том;
z блочный диск, подключаемый по протоколу Fiber Channel (FC);
z  том, экспортируемый по протоколу Network File System (NFS).
