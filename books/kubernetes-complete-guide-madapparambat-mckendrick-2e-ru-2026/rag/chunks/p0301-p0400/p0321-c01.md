Обеспечение работоспособности сервисов с помощью проверок     321

        initialDelaySeconds: 5
        periodSeconds: 5
        httpGet:
          path: /healthcheck
          port: 80
          httpHeaders:
            - name: My-Custom-Header
              value: My-Custom-Header-Value

Обратите внимание на ключевые параметры в блоке livenessProbe. Система
будет ждать 5 секунд перед выполнением первой проверки состояния, а за-
тем каждые 5 секунд отправлять один HTTP-запрос к пути /healthcheck на
порте 80. В запрос добавляется пользовательский HTTP-заголовок, помога-
ющий идентифицировать проверки состояния в журналах доступа. Учтите,
что путь /healthcheck, скорее всего, отсутствует в контейнере nginx, поэтому
этот контейнер никогда не будет признан работоспособным, так как проверка
LivenessProbe будет возвращать HTTP-ответ 404. Для успешного прохожде-
ния HTTP-проверки состояния необходимо, чтобы ответ содержал код >= 200
и < 400. Поскольку код 404 не попадает в этот диапазон, под будет считаться
неработоспособным.

Проверка жизнеспособности с помощью команды
Проверить состояние пода можно и с помощью команды. Сделаем это на при-
мере того же YAML-манифеста:

# nginx-pod-with-liveness-command.yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod-with-liveness-command
spec:
  containers:
    - name: nginx-pod-with-liveness-command
      image: nginx
      livenessProbe:
        initialDelaySeconds: 5
        periodSeconds: 5
        exec:
          command:
            - cat
            - /hello/world

Как видите, этот вариант гораздо проще по сравнению с HTTP-проверкой.
В данном случае каждые 5 секунд выполняется команда cat /hello/world. Если
файл существует и команда завершается с кодом выхода 0, проверка считается
успешно пройденной. Если файла нет, проверка завершится ошибкой, под будет
признан неработоспособным и отключен.
