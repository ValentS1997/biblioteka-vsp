позволяет создать запрос наподобие: «Мне нужно 10 Гбайт SSD-хранилища
с режимом доступа read/write-once». Для удовлетворения такого запроса
требуется объект PV (постоянный том) — реальный участок хранилища, вы-
деленный автоматизированным процессом кластера. Его можно представить
в виде каталога в хост-системе или диска, управляемого драйвером хранилища.
Типы PV реализуются в виде плагинов, подобно томам в Docker или Podman.
Выделение PV может осуществляться динамически. Для этого создается объект
StorageClass, который используется при определении PVC. При создании ново-
го StorageClass вы указываете параметры провиженера (или плагина), после
чего каждый объект PVC, использующий этот StorageClass, будет автоматиче-
ски создавать PV с помощью выбранного провиженера. Такие провиженеры
могут, например, создавать диски, управляемые облачным провайдером и вы-
ступающие в качестве базового хранилища. Кроме того, контейнеры, входящие
в один и тот же под, могут совместно использовать данные, монтируя общий
PV в свою файловую систему.

Это лишь краткий обзор механизмов хранения состояния, предоставляемых
Kubernetes. Их подробное описание приведено в главе 9.

Помимо управления состоянием одного пода и его контейнеров, бывает не-
обходимо управлять состоянием нескольких реплик пода. Представьте, что
вы используете объект Deployment для запуска нескольких подов с сервером
MySQL. Сначала вам нужно обеспечить сохранение состояния в томе контей-
нера. Для этого можно использовать объекты PV Kubernetes. Однако в резуль-
тате вы получите несколько независимых экземпляров MySQL-сервера, что
не обеспечит высокой доступности и отказоустойчивости. Публикация такого
объекта Deployment через сервис тоже не принесет особой пользы, так как при
каждом запросе вы будете обращаться к разным подам MySQL и получать
разные данные.

Таким образом, возникает необходимость построения многоузловой отказо
устойчивой конфигурации с синхронизацией данных между главным узлом и его
репликами или создания сложного кластера, предусматривающего шардирова-
ние данных. В любом случае каждую реплику пода с сервером MySQL нужно
наделить уникальной идентичностью и желательно предсказуемыми сетевыми
именами, чтобы узлы и клиенты могли корректно взаимодействовать.

         Разрабатывая облачное приложение для кластера Kubernetes, всегда оценивай-
          те все за и против хранения его состояния в виде stateful-компонентов внутри
          кластера.

Именно для этого в Kubernetes предусмотрен объект StatefulSet, о котором мы
поговорим далее.
