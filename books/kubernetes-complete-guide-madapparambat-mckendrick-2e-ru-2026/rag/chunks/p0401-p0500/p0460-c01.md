Как уже было сказано, объект DaemonSet гарантирует то, что поды, обеспечи-
вающие работу критически важных служб, будут запущены на всех узлах (или
только на выбранных). В следующем подразделе мы поговорим о механизме
планирования таких подов.

Планирование подов DaemonSet
Объекты DaemonSet гарантируют запуск единственного пода на каждом под-
ходящем узле кластера Kubernetes. Контроллер DaemonSet использует правила
предпочтения узлов (node affinity), обеспечивающие запуск подов DaemonSet
только на тех узлах, которые соответствуют заданным условиям, что особенно
полезно при работе со сложными кластерами. Затем стандартный планировщик
привязывает под к выбранному узлу, вытесняя существующие поды при не-
хватке ресурсов. При желании можно указать пользовательский планировщик,
однако контроллер DaemonSet в любом случае гарантирует размещение подов
в соответствии с заданными правилами предпочтения узлов.

В следующем разделе мы поговорим о проверке ресурсов DaemonSet в кластере
Kubernetes.

Проверка объектов DaemonSet
После развертывания кластера Kubernetes вы можете обнаружить, что некото-
рые объекты DaemonSet уже установлены по умолчанию в виде системных или
вспомогательных компонентов вроде службы DNS или CNI-плагина.
В качестве примера создадим многоузловой кластер minikube с помощью сле-
дующего фрагмента кода:

 $ minikube start \
   --driver=virtualbox \
   --nodes=3 \
   --cni=calico \
   --cpus=2 \
   --memory=2g \
   --kubernetes-version=v1.31.0 \
   --container-runtime=containerd
