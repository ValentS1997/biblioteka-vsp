406     Глава 11   •  Использование объекта Deployment

Обновление объекта Deployment
В этом подразделе мы применим стратегию RollingUpdate на практике. Для
начала пересоздадим объект Deployment, который использовали ранее для
демонстрации проверки готовности.

1. Сделайте копию предыдущего YAML-манифеста:

    $ cp nginx-deployment-readinessprobe.yaml nginx-deployment-rollingupdate.yaml

2. Убедитесь, что в манифесте nginx-deployment-readinessprobe.yaml указана
   стратегия RollingUpdate и используется образ nginx:1.17. Если вы выполня-
   ли шаги, описанные в предыдущих подразделах, эти параметры уже должны
   быть настроены:

   # nginx-deployment-rollingupdate.yaml
   apiVersion: apps/v1
   kind: Deployment
   metadata:
     name: nginx-deployment-rollingupdate
   spec:
     replicas: 3
   ...
     minReadySeconds: 10
     strategy:
       type: RollingUpdate
       rollingUpdate:
         maxUnavailable: 1
         maxSurge: 1
     template:
   ...
       spec:
         containers:
           - name: nginx
             image: nginx:1.17
   ...
             readinessProbe:
               httpGet:
   ...
3. В нашем примере для параметра maxUnavailable задано значение 1. Это
   значит, что из трех подов (целевое количество) только один может быть
   временно недоступен (не готов). Следовательно, в любой момент времени
   как минимум два пода должны быть готовы обслуживать трафик.
4. Параметр maxSurge, значение которого также равно 1, разрешает создание
   одного дополнительного пода сверх целевого количества (равного трем)
   во время выкатывания обновлений. Таким образом, в ходе этого процесса
   в кластере может присутствовать до четырех (готовых или не готовых) подов.
