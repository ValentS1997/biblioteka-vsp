470     Глава 13   •  Объект DaemonSet: запуск одного пода на каждом узле

Типичные сценарии использования
объектов DaemonSet
На практике объект DaemonSet чаще всего используется либо для реализации
фундаментальных функций кластера, без которых он не может работать, либо
для запуска вспомогательных рабочих нагрузок, связанных с обслуживанием
или сбором данных. Ниже перечислены наиболее распространенные и интерес-
ные сценарии использования объектов DaemonSet.

z В зависимости от способа развертывания кластера служба kube-proxy,
  являющаяся одним из ключевых компонентов Kubernetes, может быть
   установлена в виде объекта DaemonSet, а не в качестве обычной системной
   службы. Например, в сервисе Azure Kubernetes Service (AKS) определение
   этого объекта DaemonSet можно просмотреть с помощью команды kubectl
   describe ds -n kube-system kube-proxy. Это классический пример базовой
   службы, которая должна выполняться в единственном экземпляре на каждом
   узле кластера. Пример YAML-манифеста для kube-proxy доступен по ссылке:
    https://github.com/kubernetes/kubernetes/blob/release-1.30/cluster/addons/kube-proxy/
   kube-proxy-ds.yaml.
z К фундаментальным службам, запускаемым в виде DaemonSet, также от-
   носятся CNI-плагины и агенты, обеспечивающие сетевое взаимодействие
   в кластере Kubernetes. Мы уже рассматривали соответствующий пример
   в начале главы при использовании CNI-плагина Calico в кластере minikube.
  Еще одним распространенным примером является агент Flannel (https://
    github.com/flannel-io/flannel/blob/master/Documentation/kube-flannel.yml), который
   запускается на каждом узле и отвечает за выделение подсети из заранее на-
   строенного адресного пространства. Конкретный механизм работы при этом
   зависит от типа сетевой технологии, используемой в кластере.
z Кластерные службы хранения данных также часто развертываются в виде
   объектов DaemonSet. Хорошим примером является Object Storage Daemon
  (OSD) системы Ceph — распределенной платформы, предоставляющей
   единое хранилище для объектных, блочных и файловых данных. Компонент
  OSD отвечает за хранение объектов в локальной файловой системе каждого
   узла и предоставляет к ним сетевой доступ. Пример манифеста можно найти
   в составе шаблона Helm-чарта по адресу https://github.com/ceph/ceph-container/
   blob/stable-7.0/examples/helm/ceph/templates/osd/daemonset.yaml.
z  Ingress-контроллеры в Kubernetes (см. главу 21) также могут быть развер-
  нуты в виде DaemonSet. Например, при установке сервера Nginx в качестве
   Ingress-контроллера вы можете развернуть его в виде этого объекта: https://
   github.com/nginxinc/kubernetes-ingress/blob/master/deployments/daemon-set/nginx-
    ingress.yaml. Такой способ особенно распространен при развертывании кла-
   стеров Kubernetes на физических серверах.
