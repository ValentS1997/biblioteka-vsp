466     Глава 13   •  Объект DaemonSet: запуск одного пода на каждом узле

Этот пример наглядно демонстрирует ключевые принципы работы механизма
планирования подов DaemonSet в Kubernetes.

         Хорошей практикой считается задание ограничений (taints) и допусков (tole
            rations) для узлов, на которых запускаются объекты DaemonSet. Эти механизмы
          будут подробно рассмотрены в главе 19.

Теперь обсудим продвинутые параметры конфигурации DaemonSet.

Приоритизация критических объектов DaemonSet
в Kubernetes
При управлении критически важными системными компонентами с помощью
объектов DaemonSet необходимо обеспечить их бесперебойную работу. Для
этого используется механизм назначения приоритетов подов и классы прио
ритета, гарантирующие то, что критически важные поды не будут вытеснены
менее приоритетными задачами.
В Kubernetes каждому поду назначается уровень приоритета, определяющий
его относительную важность в кластере. Поды с более высоким приоритетом
считаются более значимыми по сравнению с низкоприоритетными подами.
Присвоение объекту DaemonSet более высокого класса приоритета (Priority
Class) повышает значимость его подов. Таким образом, при нехватке ресурсов
планировщик не сможет вытеснить эти поды ради выполнения менее приори-
тетных задач.
Объект PriorityClass определяет конкретный уровень приоритета подов. Его
значения могут варьироваться от отрицательных целых чисел до 1 миллиарда,
при этом большие значения соответствуют более высокому приоритету.

Ниже приведен пример YAML-манифеста для объекта PriorityClass:
# priorityclass.yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: fluentd-priority
value: 100000 # Высокое значение для критически важных подов
globalDefault: false # Не является классом по умолчанию для всех подов
description: "Fluentd Daemonset priority class"

После создания объекта PriorityClass его можно использовать в конфигурации
DaemonSet, добавив ссылку на него:

spec:
  template:
    spec:
      priorityClassName: fluentd-priority
