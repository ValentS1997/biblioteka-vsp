186     Глава 5   •  Использование многоконтейнерных подов

Что происходит при неудачном запуске контейнера
внутри пода
Система Kubernetes отслеживает все контейнеры, запускаемые в составе одного
пода. Однако бывает, что какой-то контейнер запустить не удается. Давайте спе-
циально сделаем ошибку в YAML-манифесте, чтобы посмотреть, как Kubernetes
реагирует на эту ситуацию.

В следующем файле мы указали несуществующий образ Nginx-контейнера
nginx:i-do-not-exist:

# failed-multi-container-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: multi-container-pod
spec:
  restartPolicy: Never
  containers:
    - name: nginx-container
      image: nginx:i-do-not-exist
    - name: debian-container
      image: debian
      command: ["/bin/sh"]
      args: ["-c", "while true; do date; echo debian-container; sleep 5; done"]

Теперь применим этот манифест с помощью команды kubectl apply -f failed-
multi-container pod.yaml:

 $ kubectl apply -f failed-multi-container-pod.yaml
 pod/failed-multi-container-pod created

Как видите, под все-таки был создан. Это объясняется тем, что, даже если
образ не существует, YAML-манифест остается действительным с точки зре-
ния Kubernetes. Поэтому система создает под и вносит запись о нем в храни-
лище etcd, однако во время запуска контейнера агент kubelet сталкивается
с ошибкой при попытке получить образ из реестра контейнеров (например,
Docker Hub).
Проверим статус пода с помощью команды kubectl get pod:

 $ kubectl get pod
 NAME                         READY   STATUS             RESTARTS   AGE
 failed-multi-container-pod   1/2     ImagePullBackOff   0          93s

Статус ImagePullBackOff означает, что Kubernetes пытается запустить под,
но сталкивается с ошибкой доступа к образу. Чтобы узнать причину ошибки,
нужно выполнить команду kubectl describe pod failed-multi-container-pod:
