196     Глава 5   •  Использование многоконтейнерных подов

  initContainers:
    - name: download-website
      image: busybox
      command:
        - sh
        - -c
      args:
        - |
          wget \
          https://github.com/iamgini/website-demo-one-page/archive/refs/
          heads/main.zip -O /tmp/website.zip && \
          mkdir /tmp/website && \
          unzip /tmp/website.zip -d /tmp/website && \
          cp -r /tmp/website/website-demo-one-page-main/* /usr/share/nginx/html
      volumeMounts:
        - name: website-volume
          mountPath: /usr/share/nginx/html
  containers:
    - name: nginx-container
      image: nginx:latest
      volumeMounts:
        - name: website-volume
          mountPath: /usr/share/nginx/html

Как видите, init-контейнер запускает образ busybox, который загружает прило-
жение (здесь это содержимое простого сайта со страницы https://github.com/iamgini/
website-demo-one-page) и копирует его в общий том website-volume. (О томах и по-
стоянном хранилище мы поговорим в главе 9.) Этот же том монтируется в кон-
тейнер Nginx, чтобы тот использовал его в качестве источника веб-контента
по умолчанию. По завершении работы init-контейнера Kubernetes создаст
контейнер nginx-container.

          Учтите, что в случае сбоя при выполнении init-контейнера система Kubernetes
         не сможет запустить основные контейнеры. Контейнеры инициализации не стоит
          рассматривать в качестве второстепенных компонентов, сбой которых допустим.
         Если они определены в YAML-манифесте, значит, их успешное выполнение слу-
         жит обязательным условием для запуска основных контейнеров.

Создадим под, а затем выполним команду kubectl get Pods -w, вывод которой
будет регулярно обновляться, отражая изменения в статусе пода. Обратите
внимание на столбец STATUS, в котором указано, что init-контейнер перешел
в состояние выполнения (Running):

 $ kubectl apply -f nginx-with-init-container.yaml
 pod/nginx-with-init-container created

 $ kubectl get po -w
