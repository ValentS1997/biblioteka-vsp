# Cheatsheet — глава 4. Основы работы с запросами

**Source:** PDF 70–104, `p0070:c01`–`p0104:c01`, `rag_only`. Никакие запросы не исполнялись.

## Symptom / problem framing

Нужно выбрать данные из нескольких таблиц, убрать дубли, правильно фильтровать, сгруппировать, отсортировать и ограничить объём результата. Риски: `SELECT *` на больших таблицах, неоднозначные имена, избыточный `COUNT(*)`, неверное размещение условия между `WHERE` и `HAVING`, ошибочное ожидание стабильного порядка без `ORDER BY`. Источник: `p0072:c01`, `p0076:c01`, `p0090:c01`, `p0096:c01`, `p0099:c01`, `p0103:c01`.

## Read-only checks

**Статическая проверка (без подключения):**
1. Найти перечень полей `SELECT`, избегать неоправданного `*` (`p0071:c01`–`p0073:c01`).
2. Квалифицировать неоднозначные имена `o.name`, `t.name`, присвоить `AS owner_name` и `AS tour_name` (`p0076:c01`, `p0084:c01`–`p0085:c01`).
3. Проверить, что `JOIN ... ON` опирается на указанную связь: `w.id = t.stop` (`p0083:c01`–`p0085:c01`).
4. Отнести фильтры строк к `WHERE`, фильтр по `COUNT(*)` — к `HAVING` (`p0090:c01`–`p0100:c01`).
5. Для подсчёта определить, сколько строк описывают **одну сущность**, прежде чем доверять `COUNT(*)` (`p0096:c01`).
6. Проверить необходимость `ORDER BY` перед ограничением строк; источник не гарантирует порядок при отсутствии сортировки (`p0103:c01`).

**Только при согласованных правах и среде:** выполнить разрешённый `SELECT` с ограничением строк/предикатом. Ниже пример из книги, без выполнения (`p0072:c01`):
```sql
SELECT id, name
FROM owner;
```
Могут вернуться чувствительные данные или большой объём строк: права, cardinality и результат [Needs confirmation].

## Interpretation

### SELECT vs FROM

`SELECT` задаёт возвращаемые столбцы/выражения, `FROM` — источник. `SELECT CURRENT_DATE;` показан без FROM только для определённых СУБД; результат книги `2021-12-01` — **демонстрационный, не текущая дата** (`p0073:c01`).

### Подзапросы

- `SELECT`: скалярный подзапрос — один столбец, максимум одна строка; в учебном примере среднее население добавлено каждому округу (`p0078:c01`, `p0079:c01`).
- `FROM`: производная таблица с алиасом, либо `WITH`/CTE (`p0085:c01`–`p0088:c01`).
- `WHERE`: `IN (SELECT ...)` как фильтр по другой таблице; альтернатива — JOIN (`p0091:c01`–`p0093:c01`).
- Коррелированный подзапрос ссылается на внешний `o.id`; автор предлагает JOIN, но в альтернативе пишет `waterfalls` вместо `waterfall`: [Source code mismatch], см. source-findings.

### DISTINCT, GROUP BY, HAVING

`DISTINCT` — убрать повторы комбинаций значений; `COUNT(DISTINCT type)` — число уникальных типов (`p0080:c01`–`p0082:c01`).

`GROUP BY t.name` + `COUNT(*)` — количество строк на каждый тур, **не обязательно уникальных водопадов**, если есть дубли (`p0094:c01`–`p0098:c01`).

`WHERE` фильтрует строки **до агрегирования**, `HAVING COUNT(*) = 6` — агрегированные группы (`p0098:c01`–`p0100:c01`). Автор отдельно отмечает исключение MySQL и SQLite для ссылки на `SELECT`-alias в HAVING.

### ORDER BY и LIMIT

`ORDER BY owner DESC, waterfall_name ASC`: сортировка нескольких полей; допускается сортировка и по позициям `ORDER BY 1 DESC, 2 ASC` (`p0101:c01`–`p0103:c01`).

`LIMIT 3` (MySQL/PostgreSQL/SQLite), `ROWNUM <= 3` (Oracle), `TOP 3` (SQL Server) — **разные книжные диалекты**, не универсальный оператор (`p0103:c01`, `p0104:c01`).

## Next action

1. Подтвердить РСУБД, версию, схему, права и объём данных.
2. Сначала проверить выбранные поля и JOIN/WHERE статически.
3. На разрешённой тестовой БД сопоставить предварительные результаты и число строк до/после группировки; фактическое выполнение [Needs confirmation].
4. При подозрении на дорогой correlated subquery не считать перепись JOIN ускорением без измерений; исходный вариант в книге имеет несовпадение имени таблицы.
5. Зафиксировать требуемый порядок результата через ORDER BY и применять диалектное ограничение количества строк по источнику.
