# Глава 1 — концептуальная и эксплуатационная шпаргалка

**Источник:** `how-linux-works-brian-ward-3e-ru-2022`, `p0028:c01`–`p0038:c01` (PDF/печатные страницы 28–38). Только `rag_only`.

## Symptom / problem framing — постановка вопроса

Задача главы — понять, **на каком уровне абстракции** находится компонент/действие: hardware, kernel или user space. Аналогия с автомобилем объясняет полезность последовательной локализации по составным частям (PDF 28–29). В книге **нет** готовой последовательности реальных диагностических проверок по инциденту.

## Baseline / context — базовая модель

| Уровень / понятие | Функция | Граница |
|---|---|---|
| Hardware | CPU, оперативная память, диски, сетевые интерфейсы | Физический уровень (29). |
| Kernel | Управление процессами, памятью, устройствами и системными вызовами | Режим ядра и `kernel space` (29–32). |
| User space | Пользовательские процессы: службы и приложения | Ограничения пользовательского режима и области памяти (30–31, 36). |
| RAM и состояние | Код, данные, состояние ядра/процессов в памяти | Абстрактное состояние описывает смысл расположения битов (31). |
| UID / root / groups | Принадлежность процессов и файлов, привилегии, совместный доступ | `root` — привилегированный пользователь, **не** kernel mode (37–38). |

Внутри ядра выделяются четыре направления: **планирование процессов**, **управление памятью**, **драйверы**, **системные вызовы и поддержка** (`p0032:c01`).

## Read-only checks — проверка без изменений

Глава упоминает **`ls`** только как пример команды, отображающей содержимое каталога (`p0035:c01`). Конкретные команды для проверки CPU, RAM, процессов, прав доступа или драйверов **не приводятся**: **[Needs confirmation]**. Нельзя подставлять `ps`, `top`, `free`, `id` или другие привычные команды без основания в RAG главы.

## Interpretation — как читать архитектуру

1. **Режим ядра ≠ пользовательский режим.** Ядро имеет широкий доступ к памяти и процессору; пользовательские процессы ограничены. Их сбои обычно локальны, но особые права пользователя могут позволить повредить данные (PDF 30–31).
2. **Многозадачность на одном CPU.** Программы видятся параллельными из-за быстрых переключений по квантам. Прерывание → ядро сохраняет контекст → выбирает готовый процесс → готовит память/CPU → возвращает управление в user mode (PDF 32–33).
3. **Виртуальная память.** Ядро поддерживает таблицы страниц; MMU преобразует адрес процесса в физический адрес. Цели: изоляция, совместное использование по правилам, отдельные read-only области, возможность опоры на дисковую память (PDF 34).
4. **Драйверы.** Устройства обычно доступны через ядро, которое предоставляет более единообразный интерфейс независимо от различий оборудования (PDF 34–35).
5. **Системные вызовы.** Процесс запрашивает действия ядра; для запуска `ls` приведён пример `fork()` → `exec()` (PDF 35–36).
6. **Условная иерархия user space.** Основные службы → промежуточные службы → приложения. Это иллюстративная схема, **не строгое правило** (PDF 36–37).
7. **Идентификаторы и права.** Ядро оперирует UID; пользователь владеет процессами и файлами, группа помогает совместному доступу, root — особое исключение с повышенным риском (PDF 37–38).

## Next action — что делать после концептуальной классификации

Определить релевантный уровень/компонент и **обратиться к следующему источнику с детальными действиями**. Эта глава не задаёт команд и критериев локализации для конкретного инцидента; выбор тестов и исходных метрик — **[Needs confirmation]**. Раздел 1.6 направляет к главе 2, где начинается практический разбор user space и файлов/дисков.

## Modifying action — изменение состояния

- В главе нет рецепта изменения конфигурации или прав: **[Not applicable]**.
- `fork()` создаёт дочерний процесс; `exec()` заменяет выполняемую программу. Это **примеры программного API**, а не приглашение запускать их в терминале (`p0035:c01`).
- Любая реальная модификация вне этих описаний: **[Needs confirmation]**; не выполнять на основе одного концептуального объяснения.

## Verification / acceptance checks — критерии

**Проверка понимания (не хостовая диагностика):** можно объяснить три уровня, четыре области работы ядра, сохранение/восстановление контекста, роль MMU, различие UID/root/kernel mode и пример запуска `ls`. Измеряемые критерии исправления инцидента в главе отсутствуют: **[Needs confirmation]**.

## Rollback — откат

Глава не описывает конфигурационные изменения или процедуры отката: **[Not applicable]**. Для самостоятельно выбранного изменения вне содержания главы нужен отдельный план rollback: **[Needs confirmation]**.

## Риски и оговорки

- `root` опасен из-за возможного воздействия на процессы других пользователей и файлы; root остаётся в user mode (`p0038:c01`).
- Изоляция процессов в тексте не означает абсолютную невозможность ущерба: глава отдельно обсуждает специальные привилегии (`p0031:c01`).
- Графика рисунков 1.1–1.3 не восстановлена из мультимодального RAG; использованы лишь текстовые утверждения (`source-findings.md`).
