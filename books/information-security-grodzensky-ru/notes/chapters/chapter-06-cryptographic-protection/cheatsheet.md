# Шпаргалка: криптографическая защита информации

Цель: различать три базовых механизма главы — симметричное шифрование, асимметричное шифрование и хэширование — и не смешивать их назначение.

## Baseline / context

### Что защищает криптография по главе

- конфиденциальность;
- целостность;
- аутентификацию;
- неотказуемость.

### Три базовые модели

| Модель | Ключевая идея |
|---|---|
| Симметричное шифрование | Один и тот же ключ используется для шифрования и дешифрования |
| Асимметричное шифрование | Используется пара открытого и закрытого ключей |
| Хэш-функция | Данные произвольной длины преобразуются в результат фиксированной длины |

## Симметричное шифрование

### Исторические примеры

- Цезарь — подстановка;
- Виженер — полиалфавитная подстановка с ключевым словом;
- Гронсфельд — полиалфавитная схема с числовым ключом;
- маршрутная/вертикальная перестановка — перестановочные шифры.

### Подстановка vs перестановка

```text
substitution:
символы заменяются другими символами/группами

transposition:
сами символы сохраняются,
но меняется их порядок
```

### Достоинства

По источнику:
- простота;
- высокая скорость;
- меньшая длина ключа по сравнению с асимметричным шифрованием.

### Недостатки

- общий ключ должен быть безопасно передан;
- ключ может быть скомпрометирован;
- управление ключами усложняется в больших сетях;
- в описанной модели общий ключ не подходит для электронной подписи.

## Асимметричное шифрование

```text
public key  → шифрование / проверка подписи
private key → расшифрование
```

Названные области применения:
- PKI;
- электронная подпись;
- шифрование сообщений;
- SSH.

Источник также приводит сочетание симметричного и асимметричного подходов на примере SSL.

## Хэш-функция

Источник определяет её как разновидность односторонней функции:

```text
arbitrary-length input
        ↓
hash function
        ↓
fixed-length bit string
```

Названные применения:
- хранение паролей;
- хранение биометрических данных;
- электронная подпись через подписание хэша.

Ключевое свойство, отдельно упомянутое в главе: минимальная вероятность коллизии.

## Read-only checks

Глава не содержит инструментальных команд. Концептуальная проверка:

1. Требуется ли обратимое шифрование или необратимое хэширование?
2. Если шифрование — используется один общий ключ или пара ключей?
3. Как доставляется/хранится ключ?
4. Нужна ли проверка электронной подписи?
5. Есть ли риск компрометации общего ключа?
6. Масштабируется ли управление ключами на количество участников?

## Verification / acceptance checks

Поддерживаемые главой логические критерии:

- зашифрованные данные должны быть нечитаемыми без требуемого ключа;
- легитимный получатель должен иметь возможность восстановить исходные данные для обратимых схем;
- при хэшировании обратное восстановление исходного значения не предполагается;
- для хэш-функций важна устойчивость к коллизиям;
- открытый ключ должен позволять проверку электронной подписи в модели главы.
