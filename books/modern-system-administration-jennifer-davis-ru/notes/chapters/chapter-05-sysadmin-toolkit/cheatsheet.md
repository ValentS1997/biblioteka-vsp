# Шпаргалка — глава 5. Набор инструментов сисадмина

**Происхождение:** RAG PDF 73–82, chunks `p0073-c01` — `p0082-c01`; печатные с. 77–86. Только содержание главы.

## Symptom / problem framing — задача

- Эксперименты и исправления в продуктивной среде создают риск нарушения сервиса.
- Ручные повторяемые операции, несогласованные настройки и непрозрачные изменения повышают когнитивную нагрузку.
- Зависимость от личных предпочтений редактора, языка или конфигурации осложняет совместную работу.

Основание: PDF 73–74, 76, 82.

## Baseline / context — исходное состояние

- Подготовить отдельную рабочую среду, насколько возможно моделирующую рабочие условия: локально, на рабочей станции либо в изолированной удалённой среде.
- Зафиксировать назначение инструментов: редактор; языки; фреймворки; библиотеки; приложения.
- Учитывать языки и навыки команды, уже существующий код, затраты на поддержку, практики безопасности и версии зависимостей.

Основание: PDF 73–74, 77–79.

## Read-only checks — наблюдение без изменения среды

- Проверить возможности редактора: статический анализ, автозавершение, форматирование/отступы, совместная работа и интеграция с Git.
- Просмотреть языки существующих проектов, зависимости и правила команды.
- Убедиться, что версии фреймворков и библиотек документированы.
- Проанализировать чужие dotfiles до применения, а не копировать их вслепую.
- Использовать поиск по коду (Ag) и представление дерева каталогов (tree) для исследования.

Основание: PDF 75–81. Конкретные команды для этих проверок: **[Needs confirmation]** там, где их нет в тексте главы.

## Interpretation — как принимать решение

| Ситуация | Интерпретация автора |
|---|---|
| Нужна быстрая автоматизация повседневной задачи | Bash или PowerShell могут быть разумной отправной точкой |
| Сценарий стал сложным, содержит сложные структуры данных | Рассмотреть полноценную утилиту на Python, C#, Ruby либо Go; ориентир «более 50 строк» — эвристика книги, не технический порог |
| Несколько людей поддерживают общий код | Согласовать стиль, редакторные проверки и рабочий процесс Git |
| Изменяются версии языков/библиотек | Учитывать совместимость, стоимость рефакторинга и версии зависимостей |
| Изменение рискованно для production | Сначала испытать его в изолированной среде, учитывая различия с реальной системой |

Основание: PDF 74–79.

## Next action — следующий шаг

Сформировать минимальный согласованный инструментарий под конкретную задачу, с изолированным местом испытаний и документированными версиями. Не выбирать язык только по личным предпочтениям; учитывать навыки и процессы команды (PDF 73–79).

## Modifying action — изменения, эффект и риск

1. **Создание/настройка изолированной среды.** Эффект: отдельное место для экспериментов. Риск: неполное сходство с production, особенно при зависимости от оборудования (пример LTO на PDF 74).
2. **Подключение редакторных расширений и соглашений.** Эффект: ранние предупреждения и единый стиль; риск: неподходящая проверка или изменение представления кода (PDF 75–76).
3. **Выбор/установка языка и библиотек.** Эффект: новые возможности автоматизации; риск: несовместимость, сложная миграция. В книге рекомендовано не заменять системную версию языка, а устанавливать нужную отдельно (PDF 77–79).
4. **Применение dotfiles.** Эффект: персонализация рабочей среды; риск: чужая конфигурация может быть неуместна или небезопасна (PDF 79–80).

## Verification / acceptance checks — проверка результата

- Проверить предполагаемое изменение **в изолированной среде**, сопоставляя условия с production; учитывать, что аппаратные сбои могут быть не воспроизведены виртуализацией (PDF 74).
- Проверить, что линтер предупреждает о типичных проблемах и редактор помогает с согласованным стилем (PDF 75–76).
- Подтвердить, что версии библиотек известны и результат работы согласован в команде (PDF 79).
- Формальная процедура acceptance, команда запуска и критерии измерения для конкретного проекта: **[Needs confirmation]**.

## Rollback — возврат

Глава не задаёт универсальных команд отката изменений среды/языков/конфигураций: **[Needs confirmation]**. Испытания предлагается изолировать **до** производственного изменения. Откат конкретного проекта необходимо разработать отдельно, не подменяя его предположениями.
