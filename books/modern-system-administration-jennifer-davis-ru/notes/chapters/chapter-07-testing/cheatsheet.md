# Шпаргалка — глава 7 «Тестирование»

**Provenance:** RAG PDF 89–99, `p0089:c01` — `p0099:c01`. Никаких внешних дополнений.

## Symptom / problem framing — симптом и задача

- Изменение инфраструктуры может нарушить зависимые сервисы; одних субъективных ручных проверок может быть недостаточно.
- При избытке сквозных тестов проверка становится дорогой, медленной и менее точной при локализации причин.
- **PASS не означает абсолютного отсутствия ошибок**; FAIL не обязательно означает дефект целевого кода (PDF 94–99).

## Baseline / context — исходный контекст

- Уже выполняемые человеком эксперименты в непроизводственной среде — форма исследовательского тестирования (PDF 89).
- Разделить проверки по назначению: линтинг (статический анализ), модульные, интеграционные, E2E (PDF 90–93).
- Учитывать особенности инфракода, реалистичность тестовой среды, внешние зависимости и стоимость тестового цикла (PDF 93–96).

## Read-only checks — что изучить без изменения

- Прочитать существующие тесты продукта, посмотреть используемые уровни и их количество; обнаружить дублирование или нехватку проверок (PDF 93–95).
- Просмотреть предупреждения линтера до изменения кода; затем согласовать правила команды (PDF 91).
- При падении теста начать со сведений об окружении, разрешениях, сети, оборудовании и расхождении сред; затем оценить логику теста и его предположения (PDF 97–98).
- Конкретные диагностические команды: **[Needs confirmation]** (глава не даёт CLI runbook).

## Interpretation — выбор уровня

| Тип | Что проверяет | Полезность и ограничение |
|---|---|---|
| Линтинг | Правила кода, потенциальные проблемы | Ранние предупреждения, стандартизация; не заменяет поведенческие тесты (PDF 90–92) |
| Модульный | Отдельный блок логики с изоляцией внешнего | Быстрая локализация; не выявляет реальные проблемы сети и зависимостей (PDF 92) |
| Интеграционный | Несколько компонентов во временной среде | Проверяет взаимодействие; настройка занимает дольше и ошибка хуже локализуется (PDF 93) |
| E2E | Сквозной поток и реалистичные данные | Проверяет границы системы; дорогой, нестабильный и плохо локализующий (PDF 93) |

**Пирамида:** больше быстрых, узких проверок; меньше дорогих сквозных — полезная отправная точка. Для определённого кода конфигурации инфраструктуры допустима иная структура с более весомыми интеграционными тестами (PDF 94–96).

## Next action — следующий шаг

Начинать не с «идеального» набора, а с конкретных проблем и короткого цикла улучшений: сопоставить типы тестов, устранить дублирование, сфокусировать проверки на желаемом результате своей логики, отслеживать цену поддержки (PDF 92, 94–99).

## Modifying action — контролируемое изменение

- **Настройка линтера:** может изменить правила предупреждений; риск — спорные или лишние замечания и затраты на исправление стилистики. Автор предлагает сначала проанализировать предупреждения и определить общие правила (PDF 91–92).
- **Добавление/перенос проверок между уровнями:** влияет на скорость обратной связи и диагностическую ценность; риск — потеря важных сквозных сценариев или избыточное дублирование (PDF 94–96).
- **Моделирование длительной нагрузки:** создаёт тестовый workload и потребляет ресурсы; автор предлагает это при возможных утечках памяти в долгоживущих компонентах. Для эфемерных систем необходимость может отсутствовать (PDF 98).
- **Изменение кода после падения теста:** опасно до исключения ошибок окружения, тестовой логики и предположений (PDF 97–98).

## Verification / acceptance checks — критерий проверки

- Сравнить реальную обратную связь тестов: быстро ли выявляется ошибка, можно ли определить класс причины, не дублируется ли проверка на нескольких уровнях (PDF 94–97).
- Убедиться, что модульные тесты проверяют **свой** инфракод, а не возможности сторонней платформы (PDF 92).
- Для интеграционных тестов проверять взаимодействие, например возможность настроить и подключить БД (PDF 93).
- Для E2E проверять важные потоки поведения системы (PDF 93).
- Численные пороги, точные команды и эксплуатационный acceptance для конкретного сервиса — **[Needs confirmation]**.

## Rollback — откат

В главе не дан универсальный порядок отмены изменений тестового набора, линтера или развёртываний: **[Needs confirmation]**. Не выполнять state-changing действия без отдельного согласованного плана возврата. Факт прохождения тестов не гарантирует безопасный rollback (PDF 99).

## Диагностика падения

Исследовать последовательно вероятные **классы причин**, описанные автором (PDF 97–98): инфраструктура → неправильная логика теста → изменившиеся предположения → возможный дефект кода. Это средство исследования, а не гарантия, что каждый сбой принадлежит только одной группе. Кейс на PDF 98 показывает маскировку дефекта неожиданным порядком конфигурационных шагов.
