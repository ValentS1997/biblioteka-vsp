## Главный принцип

Глава показывает исходный жизненный цикл Git-репозитория: проверить и установить Git → задать идентификацию автора → создать локальный репозиторий → осмотреть состояние и **избирательно** добавить файлы → зафиксировать коммит → при необходимости настроить удалённый репозиторий и обмен изменениями. Отдельно рассматриваются клонирование, помощь по командам, SSH и варианты установки.

Это вводный обзор, а не подтверждение актуальности старых установочных URL, версий или поведения удалённых Git-хостингов.

## Основной маршрут (§1.1)

1. Убедиться в наличии Git: \`git --version\` (на Unix-подобной системе также \`which git\`).
2. Установить личные \`user.name\` и \`user.email\` **до первого коммита** (§1.4).
3. В каталоге проекта выполнить \`git init\`. Получится скрытый каталог \`.git\`.
4. Выполнить \`git status\`, проверить файлы и отсутствие секретов. Для файлов, которые не должны отслеживаться, подготовить \`.gitignore\` **до** добавления.
5. Добавить **явно выбранные файлы**: \`git add <путь-к-файлу>\`. В RAG есть дефектное место для варианта «добавить всё»; см. [source-findings.md](source-findings.md), не восстанавливать команду по памяти.
6. Создать первый снимок: \`git commit -m "Initial commit"\`.
7. Если внешний репозиторий уже создан, можно связать его именем \`origin\` с помощью \`git remote add origin <URL>\` (§1.1). Операции публикации изменений (§1.3) требуют отдельной проверки адреса, прав доступа и исходной команды.

## Остальные понятия

- **Клонирование (§1.2):** \`git clone <URL>\` копирует репозиторий, его файлы и служебную \`.git\`; допускается явное имя каталога. Формулировка о клонировании «в текущий каталог» противоречит показанной команде — отмечена отдельно.
- **Совместная работа (§1.3):** удалённый bare-репозиторий хранит Git-объекты без рабочей копии; \`upstream\` описывает отслеживаемую удалённую ветвь. В командах этого раздела есть искажения текста.
- **Идентификация (§1.4):** \`git config --global user.name/user.email\` действует для пользователя; локальная настройка репозитория имеет приоритет. Авторство коммита не является аутентификацией на GitHub/Bitbucket/GitLab.
- **Удалённые репозитории (§1.5):** \`git remote -v\` показывает адреса; команды \`git remote add\` и \`git remote set-url\` связывают имена с URL. \`origin\` и \`upstream\` — разные именованные подключения.
- **Справка (§1.6):** \`git help <команда>\`, \`git <команда> --help\`, \`git checkout -h\`.
- **SSH (§1.7):** осмотр \`~/.ssh\`, генерация ключевой пары, подключение закрытого ключа к агенту; осторожность с приватным ключом.
- **Установка (§1.8):** исходная сборка либо установщик/пакет дистрибутива; примеры \`yum\`, \`apt-get\`, MacPorts и Homebrew приведены в историческом тексте книги.

## Проверка и ограничения

Изменяющие действия нужно отделять от проверок. Перед \`git add\` и \`git commit\` проверить \`git status\`; после \`git remote add\` — \`git remote -v\`. Для отката ранее выполненных операций глава **не задаёт универсальной процедуры**: **[Needs confirmation]**. Не запускать повреждённые OCR/текстовым слоем команды без обращения к [реестру проблем](source-findings.md).

В главе не обнаружены отдельные завершающие разделы с итоговым резюме или контрольными вопросами, поэтому условные \`summary.md\`, \`review-questions.md\` и \`review-answers.md\` не создаются.
