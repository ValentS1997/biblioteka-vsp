# Глава 1 — рабочая памятка (RAG-only)

**Область:** PDF 10–16, RAG \`p0010:c01\`–\`p0016:c01\`; все пункты выводятся из §§1.1–1.8. Для испорченных текстовых команд — [source-findings.md](source-findings.md).

## Symptom / problem framing

Нужно создать или получить Git-репозиторий, сделать первый коммит, связать его с сервером, настроить автора и разобраться с SSH. Частые риски в примерах главы: случайно включить нежелательные файлы, использовать неправильные данные автора или перепутать \`origin\` и \`upstream\`.

## Baseline / context

- Локальный репозиторий: папка проекта с \`.git\` (§1.1).
- Индекс: файлы, подготовленные к фиксации через \`git add\`; коммит фиксирует подготовленный снимок (§1.1).
- Удалённый репозиторий: другая копия, доступная по URL (§§1.1–1.3).
- Bare-репозиторий на сервере: хранилище без рабочей копии (§1.3).
- \`user.name\` и \`user.email\` — автор коммита, **не** способ входа на сервер (§1.4).
- В книге приведены исторические версии Git и старые установочные URL, актуальность которых RAG не подтверждает.

## Interpretation

- \`git --version\` не отвечает → автор рекомендует установить Git (§1.1).
- \`git status\` показывает неизвестные или конфиденциальные файлы → исключить их из отбора и настроить \`.gitignore\` до добавления (§1.1).
- Настройки автора нужны для конкретного проекта → задать \`git config user.name\` / \`user.email\` локально; они приоритетнее глобальных (§1.4).
- У пользователя есть форк без прав публикации в основной проект → разделить \`origin\` (свой форк) и \`upstream\` (исходный проект) (§1.5).
- Ключевая пара SSH не обнаружена → глава предлагает \`ssh-keygen\`; не публиковать закрытый ключ (§1.7).

## Next action

Выбрать сценарий: **новый проект** (\`git init\`) или **уже существующий проект** (\`git clone\`). До фиксации: задать автора, посмотреть \`git status\`, выбрать файлы. Для совместной работы: проверить и настроить remote. Для SSH: проверить \`~/.ssh\`, только затем работать с ключами.

## Modifying action

| Действие | Эффект / риск | Опорный раздел |
| --- | --- | --- |
| \`git init\` | Создаёт локальную метаинформацию \`.git\`; осторожно с выбранным каталогом | §1.1 |
| \`git add <путь>\` | Индексирует конкретный файл; может включить нежелательные данные | §1.1 |
| \`git commit -m "Initial commit"\` | Создаёт коммит с сообщением и настроенным автором | §§1.1, 1.4 |
| \`git remote add origin <URL>\` | Записывает адрес remote; ошибочный URL ведёт не в тот репозиторий | §1.1 |
| \`git clone <URL>\` | Создаёт локальную копию с \`.git\`; важно выбрать каталог | §1.2 |
| \`git config [--global] user.name/user.email\` | Меняет идентификацию в будущих коммитах | §1.4 |
| \`ssh-keygen\` / \`ssh-add\` | Создаёт пару ключей / загружает закрытый ключ в агент | §1.7 |

Спорные образцы команд (§§1.1–1.4) записаны в реестре проблем и **не** предлагаются для безусловного копирования.

## Verification / acceptance checks

- \`git --version\` показывает версию после установки.
- После создания/добавления файлов сверить \`git status\` с ожидаемым составом.
- После настройки remote проверить \`git remote -v\`.
- После конфигурирования автора проверить, что выбрана ожидаемая область настроек (способ вывода эффективной конфигурации в этой главе не установлен: **[Needs confirmation]**).
- Перед публикацией изменений оценить URL, права доступа и набор файлов; детальная проверка успешной отправки в разделе **[Needs confirmation]**.

## Rollback

**[Needs confirmation]**. Глава 1 не задаёт надёжной общей процедуры отмены \`init\`, \`add\`, \`commit\`, \`push\`, изменений remote, ключей и установки; не подменять её командами из других глав или памяти модели. До изменяющих шагов сохранить ожидаемое состояние и выполнить проверки.
