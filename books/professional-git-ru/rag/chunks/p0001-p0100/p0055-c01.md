54                                                                 Глава 1 О. Фиксация изменений
   Или для того, чтобы добавить все изменения, за исключением удаленных файлов, из ката
лога верхнего уровня и всех подкаталогов, можно использовать команду:
    git add
   Для того чтобы добавлять только те файлы, которые отслеживаются в данный момент
("update"), можно использовать команду:
    git add -u
   При желании просмотреть поэтапную индексацию изменений можно с помощью ко
манд:
    git status               # вывести список измененных файлов
    git diff --cached        # отображает поэтапные изменения внутри
                             # проиндексированных файлов

   Наконец, зафиксируем все изменения:
    git commit  -m "Commit message here"
   В качестве альтернативы, если вы только изменяли существующие или удаляли файлы,
но не создавали новых, можно объединить действия команд git add и git commit в од
ной команде:
     git commit -am "Commit message here"
   Обратите внимание, что при этом все измененные файлы будут проиндексированы так
же, как и в результате работы команды git add  --all.
  Чувствительные данные
  Ни в коем случае не следует передавать в коммитах конфиденциальные данные, такие
как пароли или даже закрытые ключи. Если это произошло, а изменения уже перенесены
на центральный сервер, считайте, что все конфиденциальные данные скомпрометированы.
В противном случае впоследствии эти данные можно удалить. Быстрым и простым реше
нием в данном случае будет использование "BFG Repo-Cleaner". Подробности можно посмо
треть по адресу https://rtyley.github.io/Ьfg-repo-cleaner/.
   Команда bfg  -- replace-text passwords  . txt my- repo  . gi t считывает пароли из фай
ла passwords  . txt и заменяет их на ***REMOVED***· При этом учитываются все предыду
щие коммиты всего репозитория.

Раздел 1 0.2. Хорошие сообщения для коммита
   Важно, чтобы человек, просматривающий журнал версий, вызываемый по команде
gi t  log, мог бы легко понять, в чем заключалась каждая фиксация. Хорошие сообщения
для коммита обычно включают номер задачи или проблемы в трекере и краткое описание
того, что и почему бьшо сделано, а иногда и того, как это было сделано.
   Лучшие сообщения могут выглядеть следующим образом:

    TASK-1 23  : Реализация входа в систему через OAuth
    TASK-1 24 : Добавить автоматическую минификацию JS/CSS файлов
    TASK-1 25  : Исправить ошибку минификатора при имени  > 200 символов

   В то время как следующие сообщения будут не столь полезны:

    исправить                  // Что было исправлено?
    небольшое изменение       // Что изменилось?
    TASK-371                      // Описание отсутствует,  читатель должен посмотреть
                                  //  на трекере
    Реализация IFoo в !Ваг    // Зачем это нужно?
