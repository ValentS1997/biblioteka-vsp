## Главные выводы

1. **Не превращать значения измерения в имена метрик.** `http_requests_total{path="/login"}` и `{path="/logout"}` позволяют фильтровать и агрегировать общую метрику; вместо пяти отдельных имён (PDF 97–98).
2. **Не смешивать provenance меток:** `path` и `method` знает приложение; `job`, `instance`, регион, окружение и команда чаще добавляются при обнаружении/обработке целей (PDF 98–100).
3. **Семейство, дочерний элемент, временной ряд — разные уровни.** При наличии меток `labels()` создаёт/получает child. Для неинициализированного child временной ряд в `/metrics` может отсутствовать (PDF 100–103).
4. **Агрегировать по нужным измерениям:** `sum without(path,instance)(rate(...))` сохраняет `method`, `job` и прочие метки. `by` сохраняет только заданные метки (PDF 103–104).
5. **Enum/Info:** состояния можно показать one-hot датчиком; `_info` содержит атрибуты с числовым значением 1, пригодные для объединения с другими метриками (PDF 105–108).
6. **Кардинальность — ресурсный бюджет, а не косметика.** Число серий зависит от значений меток, числа экземпляров и дополнительных серий гистограмм. Перенос значений из меток в имя метрики не сокращает число серий (PDF 109–111).

## Ограничения

- Обнаружен конфликт данных таблицы 5.4 (PDF 104): `sum without(method, instance)` и строка `{job="myjob",method="POST"} 36` не согласованы с заявленным результатом и таблицей 5.1.
