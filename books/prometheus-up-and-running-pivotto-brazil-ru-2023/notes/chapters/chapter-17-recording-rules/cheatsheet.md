# Cheatsheet — глава 17. Правила записи

**Источник:** PDF 294–305, `p0294:c01`–`p0305:c01` (`rag_only`). Никакие команды не исполнялись; текущий Prometheus/runtime [Needs confirmation].

## Symptom / problem framing

- **Дашборд медленно выполняет `query_range` для сотен/тысяч экземпляров:** регулярный предварительный `sum without(instance)(rate(...[5m]))` записывает более компактные series (PDF 297–298).
- **Нужно применять `max_over_time` к агрегированному `rate`:** сохранить instant-vector результат первым правилом, а последующим правилом применить range selector; источник также упоминает subqueries (PDF 299).
- **После правки rules.yml результат не меняется:** rule files не auto-reload, в отличие от `file_sd_configs`; нужен restart, SIGHUP или включённый HTTP reload (PDF 295).
- **Reload оказался неудачным:** `prometheus_config_last_reload_successful=0` и лог; предварительно прогонять `promtool check config`/`check rules` (PDF 295).
- **В результате неожиданно разные временные метки:** зависимые правила следует выполнять в одной группе, обеспечивая порядок и одинаковый evaluation timestamp (PDF 296, 298).
- **Ресурсы растут из-за правил:** проверить `/rules` и `prometheus_rule_group_last_duration_seconds`, отказаться от повторяющихся тяжёлых диапазонов, ненужных агрегатов и слишком высокой кардинальности (PDF 296–301).

## Read-only preflight

1. Проверить будущий `prometheus.yml` и вложенные файлы `promtool check config`; отдельно `promtool check rules` на `rules.yml`, до любого reload (PDF 295). Команды валидации читают файлы; локальный путь [Needs confirmation].
2. Проверить уникальность имён групп в одном файле, соответствие `record` и `expr`, существование входных series, намеренные labels. Отдельные `record` с одинаковыми именами/конфликтами требуют проверки конкретной конфигурации (PDF 295–296).
3. Оценить число исходных series, сколько labels устраняется, насколько снижается кардинальность и оправдана постоянная периодическая запись (PDF 297–299).
4. После активации наблюдать `http://localhost:9090/rules`, `prometheus_rule_group_last_duration_seconds` и `prometheus_config_last_reload_successful` (PDF 295–296).
5. Для двухступенчатого правила проверить, что зависимое правило следует за источником **в одной группе**; порядок и UTC timestamp результата (PDF 296, 298).
6. Для отношения сначала проверить одинаковую длительность окон, уровни агрегации и единицы; исходный `rate5m/rate10m` на PDF 303 помечен как **намеренно неправильный** (PDF 303).
7. Числа «до 90% неиспользуемых метрик» нельзя использовать как baseline пользователя: это наблюдение авторов из других систем (PDF 301).

## Interpretation

- Правила записи не эквивалентны произвольным `query`: результат **вновь пишется в TSDB**, потребляет ресурсы и получает время evaluation (PDF 296, 301).
- `rate(sum(x_total)[5m])` нельзя превращать в обычную практику: при reset отдельного Counter и исчезновении series получаются всплески (PDF 299).
- `without(instance)` подходит, когда надо уменьшить кардинальность; сохранение `instance` бывает оправдано только при дорогих множественных instrumentation labels (PDF 297, 301).
- Одно крупное rule query с длинным range может быть дороже множества коротких распределённых scrape. По возможности `max_over_time` для редкой плановой отчётности вычислять по требованию (PDF 297–299).
- Правила как API подразумевают контракт семантики для других команд; смена ярлыков исходной метрики должна не разрушать опубликованную внешнюю метрику (PDF 300).
- В names `job_device:node_disk_read_bytes:rate5m` отражены уровень, метрика и операции; `:federate`, `:longterm` — нежелательные суффиксы политик (PDF 302–305).

## Next action и modifying action

- **State-changing:** редактирование `prometheus.yml` / `rules.yml`, запуск/reload группы правил изменяет конфигурацию и TSDB. Проверять scope, backup/owner/rollout, доступ и возможности rollback: **[Needs confirmation]** (PDF 294–296).
- **State-changing и повышенный риск:** `kill -HUP <pid>` сигнализирует процессу Prometheus; POST `/-/reload` меняет активную конфигурацию и доступен только с `--web.enable-lifecycle`; не выполнять без разрешения (PDF 295).
- **Workload-generating:** `query_range`, тяжёлые rules и частая eval увеличивают CPU/ввод-вывод; окна больше часа особенно осторожно (PDF 297–299).
- **Не делать:** не переписывать имена исходных metrics через rules без необходимости; лучше исправлять source или `metric_relabel_configs`, понимая риск для потребителей (PDF 301).

- Успешное чтение config/правил, `/rules`, отсутствие ошибки reload, появление требуемых series с ожидаемыми labels и evaluation timestamp, длительность группы существенно меньше evaluation interval (PDF 295–298).
- Для двух правил `rate5m` → `max_over_time1h_rate5m` проверить порядок выполнения/наличие исторических samples. Исторические численные значения [Needs confirmation].
