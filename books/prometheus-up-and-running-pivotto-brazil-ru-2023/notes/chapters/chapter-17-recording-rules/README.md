## Основные положения

1. **Правила записи реально создают новые samples TSDB**, а не только вычисляют результат ad hoc. Конфигурация `prometheus.yml` ссылается на `rules.yml` через `rule_files`; изменения не подхватываются автоматически и требуют restart/reload (PDF 294–296).
2. **Распорядок и временные метки:** правила в одной группе вычисляются последовательно, результат предыдущего доступен следующему; все правила группы получают одинаковое время оценки/записи. Разные группы исполняются независимо (PDF 296, 298).
3. **Приёмка:** `promtool check config` проверяет основную конфигурацию и подключённые файлы, `promtool check rules` проверяет отдельный файл; `prometheus_config_last_reload_successful=0` сигнализирует о неудачном reload. На `http://localhost:9090/rules` есть статус и время исполнения; `prometheus_rule_group_last_duration_seconds` характеризует группу (PDF 295–296).
4. **Ресурсы:** регулярное предварительное вычисление агрегатов обменивает дополнительные затраты CPU/TSDB на низкую задержку дашбордов. Авторы не рекомендуют применять долгие диапазоны на каждой минуте, если расчёт нужен только ежемесячно (PDF 297–299).
5. **Сохранение семантики Counter:** сначала `rate`, потом `sum`; в противном случае reset одного Counter вызывает ложные пики. Нельзя переносить `rate(sum(x_total)[5m])` как рабочее правило (PDF 298–299).
6. **Потребители как API:** если чужая автоматизация зависит от метрик, запись отдельного стабильного ряда может изолировать внешний контракт от изменений исходных labels/PromQL; это редкий случай, требующий владения и поддержки (PDF 300).
7. **Антипаттерны:** избегать `device=sda` в самом имени метрики, правил для всех сырых рядов по умолчанию, бессмысленной сохранности `instance`, редкого `evaluation_interval=1h` для выравнивания на границы часа, коррекции плохих исходных имён через правила записи (PDF 300–301).
8. **Naming:** `job_device:node_disk_read_bytes:rate5m` — уровень с сохранёнными labels, базовая метрика и применённые операции. `_total` может сокращаться, `ratio` описывает деление, `mean5m` — отношение скоростей sum/count. Имя должно раскрывать семантику и позволять обнаружить несогласованность окон (PDF 302–305).

## Finding / ограничение источника

- **PDF 304**: у «правильного» расчёта `job:go_gc_duration_seconds:mean5m` из `_sum` и `_count` в `expr` несбалансированные закрывающие скобки. Это source code issue; не копировать как готовый рабочий YAML.
- **PDF 303**: `job:foo_per_bar:ratio_rate5m` делит `job:foo:rate5m` на `job:bar:rate10m` — **намеренный учебный антипример**, а не дефект, подлежащий исправлению в источнике.
- **PDF 299**: `max_over_time(sum without(instance)(rate(x_total[5m]))[1h])` показан как ошибочный без записи/subquery; сам текст признаёт поддержку subqueries. Нельзя утверждать, что подобные композиции вообще невозможны.
- **PDF 301**: утверждение «до 90 % метрик остаются неиспользуемыми» опирается на опыт авторов, а не универсально измеренное значение для системы пользователя.
- **PDF 296**: рисунок 17.1 в RAG доступен лишь как подпись — SVG/Mermaid являются производными схемами.
