# Шпаргалка: идентификация и трассировка устройств

Цель: определить, какое физическое или виртуальное устройство стоит за именем в системе, связать <code>/dev</code> с sysfs/udev и только после этого выполнять любые изменения.

## Symptom / problem framing

Нужно установить, какое физическое или виртуальное устройство стоит за конкретным именем в системе, и не перепутать короткое device name с устойчивой identity.

Типовые вопросы главы:
- какой type/major/minor у device node;
- какой sysfs path соответствует `/dev` node;
- есть ли persistent symlink;
- какие kernel/udev events сопровождают устройство;
- безопасно ли выполнять state-changing action над выбранным target.

## Baseline / context

Source-derived chain:

~~~text
hardware
  ↓
kernel driver/subsystem
  ↓
sysfs
  ↓
devtmpfs + udev
  ↓
/dev node / persistent symlink
  ↓
user-space process
~~~

Короткие имена вроде `/dev/sdX` зависят от discovery order и не должны считаться постоянной hardware identity.

## Read-only checks

~~~bash
ls -l /dev
ls -l /dev/sda
ls -l /sys/block
udevadm info --query=all --name=/dev/sda
ls -l /dev/disk/by-id
udevadm monitor
journalctl -k
cat /proc/devices
lsscsi
lsscsi -g
nvme list
lsusb
~~~

Сначала подтвердить device node, sysfs path и persistent identity; только затем переходить к write operations.

## Interpretation

- type + major/minor связывают node с kernel device interface;
- sysfs path отражает аппаратную иерархию;
- udev attributes и symlinks добавляют user-space identity/configuration;
- `KERNEL` и `UDEV` events показывают разные стадии обработки события;
- persistent link предпочтительнее короткого `sdX` имени для устойчивой идентификации.

## Next action

Если identity ещё не подтверждена — продолжать read-only discovery.

Если identity подтверждена — определить конкретный subsystem/driver и только затем выбирать state-changing operation, если она действительно требуется задачей.

## Modifying action

Source-confirmed state-changing examples:
- учебный `dd`, пишущий в обычный файл;
- `chvt`;
- ручной `mknod`.

Глава отдельно предупреждает о риске неверного `dd of=` и не даёт универсального write workflow для реального block device.


## 1. Начать с device node

Read-only checks:

~~~bash
ls -l /dev
ls -l /dev/sda
~~~

Первый символ mode:

- <code>b</code> — block device;
- <code>c</code> — character device;
- <code>p</code> — named pipe;
- <code>s</code> — Unix-domain socket.

Для block/character device в listing отображаются major/minor numbers.

Interpretation: имя вроде <code>/dev/sda</code> — удобный интерфейс, но не гарантированная постоянная идентичность hardware.

## 2. Связать /dev с sysfs

~~~bash
ls -l /sys/block
udevadm info --query=all --name=/dev/sda
~~~

Что искать в <code>udevadm info</code>:

- <code>P:</code> — sysfs path;
- <code>N:</code> — device node name;
- <code>S:</code> — symlink;
- <code>E:</code> — attributes/environment generated by udev rules.

Для block device sysfs path отражает реальную аппаратную иерархию значительно лучше короткого имени из <code>/dev</code>.

## 3. Проверить persistent identity

~~~bash
ls -l /dev/disk/by-id
~~~

Причина: устройства семейства <code>/dev/sd*</code> назначаются в порядке обнаружения. После изменения topology прежний <code>/dev/sdc</code> может стать <code>/dev/sdb</code>.

Persistent symlink позволяет ссылаться на hardware identity, а не только на discovery order.

## 4. Наблюдать device events

~~~bash
udevadm monitor
udevadm monitor --kernel
udevadm monitor --udev
udevadm monitor --udev --property
udevadm monitor --kernel --subsystem-match=scsi
~~~

Interpretation:

- <code>KERNEL</code> — входящее uevent ядра;
- <code>UDEV</code> — событие после обработки udevd;
- <code>--property</code> показывает attributes;
- subsystem filter помогает сузить поток событий.

Это хороший read-only способ наблюдать подключение/отключение устройства.

## 5. Дополнительная discovery

~~~bash
journalctl -k
cat /proc/devices
lsscsi
lsscsi -g
nvme list
lsusb
~~~

Назначение:

- <code>journalctl -k</code> — kernel messages;
- <code>/proc/devices</code> — major numbers зарегистрированных block/character drivers;
- <code>lsscsi</code> — SCSI-address и mapped device node;
- <code>lsscsi -g</code> — дополнительно generic SCSI node;
- <code>nvme list</code> — NVMe devices;
- <code>lsusb</code> — USB topology/devices.

## 6. Понимать роль devtmpfs и udev

Упрощённый event flow:

~~~text
hardware change
      ↓
kernel detects device
      ↓
devtmpfs exposes base device node
      ↓
kernel sends uevent
      ↓
udevd reads attributes + rules
      ↓
permissions / symlinks / additional actions
      ↓
other user-space processes see configured device
~~~

Rules:

- defaults: <code>/lib/udev/rules.d</code>;
- local overrides: <code>/etc/udev/rules.d</code>.

Глава объясняет формат rules, но не требует редактировать их для базовой работы.

## 7. Device naming map

| Категория | Типичные имена |
|---|---|
| SCSI/SATA/USB storage | <code>/dev/sd*</code> |
| Xen/virtual disks | <code>/dev/xvd*</code>, <code>/dev/vd*</code> |
| NVMe | <code>/dev/nvme*</code> |
| Device Mapper/LVM | <code>/dev/dm-*</code>, <code>/dev/mapper/*</code> |
| Optical | <code>/dev/sr*</code> |
| Legacy PATA | <code>/dev/hd*</code> |
| Virtual terminals | <code>/dev/tty*</code> |
| Pseudoterminals | <code>/dev/pts/*</code> |
| Serial | <code>/dev/ttyS*</code>, <code>/dev/ttyUSB*</code>, <code>/dev/ttyACM*</code> |
| Parallel ports | <code>/dev/lp*</code> |
| Audio | <code>/dev/snd/*</code> and legacy names |
| Generic SCSI | <code>/dev/sg*</code> |

## 8. dd: safety boundary

Источник показывает безопасный учебный пример, где вход берётся из <code>/dev/zero</code>, а output пишется в новый обычный файл:

~~~bash
dd if=/dev/zero of=new_file bs=1024 count=1
~~~

Ключевые параметры:

- <code>if=</code> — input;
- <code>of=</code> — output;
- <code>bs=</code> — block size;
- <code>ibs=</code>/<code>obs=</code> — отдельные input/output block sizes;
- <code>count=</code> — число blocks;
- <code>skip=</code> — сколько input blocks пропустить.

Risk: автор прямо предупреждает, что неверный output способен повредить файлы или данные на реальном устройстве.

Правило: до <code>dd</code> подтвердить source, destination, device identity и размер операции. Для учебной проверки — новый обычный файл.

## 9. SCSI mental model

~~~text
user space
   ↓
class device / generic SCSI node
   ↓
SCSI upper layer
   ↓
SCSI middle layer
   ↓
SCSI lower layer / bridge
   ↓
USB / ATA / host adapter
   ↓
hardware
~~~

USB mass storage использует SCSI commands внутри USB transport. SATA/ATA подключается к SCSI subsystem через <code>libata</code> и bridge logic.

## Verification / acceptance checks

Для device investigation результат считается достаточным, если подтверждены:

- expected device node;
- type + major/minor;
- sysfs path;
- persistent symlink или hardware attributes;
- relevant kernel/udev event;
- конкретный subsystem/driver path, если это требуется задачей.

## Rollback

Read-only discovery rollback не требует.

Для state-changing device operations:

- <code>mknod</code>, редактирование udev rules и любые записи в реальные block devices: rollback <code>[Needs confirmation]</code> без конкретного контекста;
- переключение virtual console можно обратить переходом обратно на нужную console;
- учебный файл, созданный примером <code>dd</code>, может быть удалён после проверки, если он больше не нужен.

## Минимальный flow

~~~text
/dev node
  ↓
ls -l → type + major/minor
  ↓
udevadm info → sysfs + attributes
  ↓
/dev/disk/by-id → persistent identity
  ↓
udevadm monitor / journalctl -k
  ↓
подтвердить subsystem / driver
  ↓
только после этого state-changing action
~~~
