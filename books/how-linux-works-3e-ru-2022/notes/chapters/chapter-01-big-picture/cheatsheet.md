# Шпаргалка: как читать работающую систему Linux

Цель: использовать модель главы 1 для локализации механизма или проблемы до подходящего уровня абстракции без преждевременного погружения в детали.

## Symptom / problem framing

Глава начинает с проблемы сложности: одновременно работают приложения, службы, библиотеки, ядро и оборудование, поэтому попытка объяснить систему сразу на уровне всех деталей становится неуправляемой.

Рабочий приём главы — сначала определить компонент и уровень, а затем углубляться только туда, где это необходимо.

## Baseline / context

Три основных уровня:

~~~text
пользовательское пространство
        ↑ системные вызовы / интерфейсы
ядро
        ↑ управление оборудованием
оборудование
~~~

Оборудование включает процессоры, оперативную память, диски и сетевые интерфейсы.

Ядро:
- управляет процессами;
- управляет памятью;
- содержит/обслуживает драйверы устройств;
- предоставляет системные вызовы и другую поддержку.

Пользовательское пространство — процессы, работающие в пользовательском режиме.

## Read-only checks

Глава 1 не предоставляет набора диагностических shell-команд для проверки состояния CPU, памяти, устройств или процессов.

Единственная shell-команда, используемая как рабочий пример, — <code>ls</code>; она нужна для объяснения запуска процесса через <code>fork()</code> и <code>exec()</code>, а не как диагностический probe.

Для эксплуатационных checks: <code>[Not applicable in chapter 1]</code>.

## Interpretation

### Если речь об отказе отдельного приложения

Сначала рассматривать пользовательское пространство: обычный пользовательский процесс выполняется с ограниченным доступом к памяти и безопасным операциям процессора, а его сбой обычно локализуется ядром.

### Если механизм связан с распределением CPU

Рассматривать управление процессами ядром:

1. истекает квант времени;
2. процессор передаёт управление ядру;
3. ядро сохраняет состояние прерванного процесса;
4. обрабатывает накопившиеся задачи;
5. выбирает следующий готовый процесс;
6. подготавливает память и процессор;
7. возвращает выполнение в пользовательский режим.

### Если вопрос связан с адресами памяти

Рассматривать связку ядро + MMU:

- процесс видит своё адресное пространство;
- MMU преобразует адрес процесса в физическое местоположение;
- ядро поддерживает таблицы соответствий;
- реализация таблицы соответствий называется таблицей страниц.

### Если вопрос связан с оборудованием

Рассматривать драйверы устройств как kernel-side интерфейс, скрывающий различия аппаратных интерфейсов от пользовательских процессов.

### Если пользовательский процесс просит привилегированную операцию

Рассматривать системный вызов как границу process ↔ kernel. В главе открытие, чтение и запись файлов приведены как действия, связанные с системными вызовами.

## Next action

После определения слоя сузить область:

~~~text
hardware?
  └─ конкретное устройство / память / CPU

kernel?
  ├─ процессное управление
  ├─ память
  ├─ драйверы
  └─ системные вызовы

user space?
  ├─ базовые компоненты
  ├─ службы
  └─ приложения
~~~

Детальную диагностику и конкретные команды брать уже из соответствующей следующей главы, а не достраивать из памяти.

## Modifying action

<code>[Not applicable]</code>

Глава 1 не задаёт системных конфигурационных изменений и не предлагает state-changing shell-команд как эксплуатационный workflow.

<code>fork()</code> и <code>exec()</code> изменяют состояние выполнения процессов, но представлены как механизмы ОС, а не как действия администратора по изменению конфигурации.

## Verification / acceptance checks

Для концептуального анализа результат считается согласованным с главой, если можно явно ответить:

- это hardware, kernel или user space?
- если kernel — относится ли механизм к процессам, памяти, драйверам или системным вызовам?
- где проходит граница kernel mode / user mode?
- кто владеет процессом и какие права пользователя применимы?

Командные acceptance checks: <code>[Not applicable in chapter 1]</code>.

## Минимальная карта памяти

~~~text
Linux
├─ Hardware
│  ├─ CPU
│  ├─ RAM
│  ├─ disks
│  └─ network interfaces
├─ Kernel
│  ├─ process management
│  ├─ memory management
│  ├─ device drivers
│  └─ syscalls/support
└─ User space
   ├─ processes
   ├─ services
   └─ applications

Security boundary:
kernel mode > user mode

Identity boundary:
user → UID → process/file ownership
root → broad user-space privileges, но не kernel mode
~~~
