## SF-02 — `INADDR_IN` и `INADDR_ANY`

**[Source wording/code mismatch]** — [PDF 143](../../../rag/chunks/p0101-p0200/p0143-c01.md) (PDF 143, печатная 142).

Текст объясняет универсальный серверный адрес «константой `INADDR_IN`», в следующем приведённом блоке инициализации UDP-сервера явно применяется **`htonl(INADDR_ANY)`**. Факт несоответствия подтверждён RAG, предполагаемая авторская правка **[Needs confirmation]**.

## SF-03 — `udpserv.c` приведён как UDP-клиент

**[Source code mismatch]** — [PDF 152](../../../rag/chunks/p0101-p0200/p0152-c01.md) и [PDF 153](../../../rag/chunks/p0101-p0200/p0153-c01.md) (PDF 152–153, печатные 151–152).

Сначала приведён `dgecho.c` с `dg_echo`, выполняющей `recvfrom` и `sendto` (код сервера). Следующая страница имеет заголовок **`Файл udpserv.c`**, однако весь показанный `main` создаёт сокет и вызывает **`dg_cli(stdin, sockfd, ...)`**, идентично клиентскому `udpcli.c`, вместо использования `dg_echo` и сервера с `bind`. При этом далее приведён протокол `./udpserv` + `./udpcli`, будто один из процессов принимает пакеты. Указание на реальный файл сопровождающего архива: **[Needs confirmation]**; не копировать этот листинг как проверенный UDP-сервер.

## SF-04 — `fdi` и `fo[0]` в неблокирующем коде

**[Source code mismatch]** — [PDF 178](../../../rag/chunks/p0101-p0200/p0178-c01.md) (PDF 178, печатная 177).

В демонстрации `int fdi = open(...)` и `read(fdi,buf,buflen)`, но обе операции `fcntl(fo[0], F_GETFL)` и `fcntl(fo[0], F_SETFL, ...)` обращаются к **`fo[0]`**, не показанному в локальном фрагменте. Применение режима к реально открытому дескриптору из данного листинга не доказано. Не исправлять автоматически, поскольку полные исходники примеров доступны только в отдельном архиве, который не исследовался.

## SF-05 — граница буфера в UDP socket-activated сервере

**[Source code mismatch]** — [PDF 173](../../../rag/chunks/p0101-p0200/p0173-c01.md) и [PDF 174](../../../rag/chunks/p0101-p0200/p0174-c01.md) (PDF 173–174).

Код серверного фрагмента `udpsocserv.c` содержит буфер `char rbuf[MAXLEN];`, затем чтение `recvfrom(..., rbuf, MAXLEN, ...)` и после успешного чтения запись **`rbuf[n] = '\0'`**. При возможном `n == MAXLEN` указанная запись обращается к индексу за объявленным буфером. Это именно условно выявляемая опасность в приведённом тексте; альтернативного проверенного исходника RAG не содержит. Корректная граница или отдельная проверка: **[Needs confirmation]**.

## SF-06 — имена API в прозе о socket activation

**[Source wording/code mismatch]** — [PDF 173](../../../rag/chunks/p0101-p0200/p0173-c01.md) по сравнению с [PDF 147](../../../rag/chunks/p0101-p0200/p0147-c01.md) и [PDF 150](../../../rag/chunks/p0101-p0200/p0150-c01.md).

В перечислении функций, применимых к стандартным дескрипторам, напечатаны `getpeerbyname(0,...)`, `reqv(0,...)`, `reqvfrom(0,...)`. В изложении API ранее встречаются `getpeername`, `readv`, `recvfrom`. Без архивного исходника и прямого PDF разрешить происхождение странных имён нельзя; в `commands.md` они не объявляются валидными программными вызовами.

## Дополнительные замечания по воспроизводимости

PDF 160 ([PDF 160](../../../rag/chunks/p0101-p0200/p0160-c01.md)) сообщает, что из иллюстраций исключена обработка `SIGCHLD` для дочерних процессов; это **оговорённое ограничение демонстрационных листингов**, а не повод домысливать подробный production-код. Лабораторные числа CPU cycles/µs и команды `sudo nice -n-19` не переносить без контроля контекста. Работа с `SOCK_RAW` описана концептуально и требует root ([PDF 186](../../../rag/chunks/p0101-p0200/p0186-c01.md)), эксплуатационная безопасность на неизвестном хосте **[Needs confirmation]**.

Исходный RAG **не редактировался**. Материал остаётся RAG-only.
