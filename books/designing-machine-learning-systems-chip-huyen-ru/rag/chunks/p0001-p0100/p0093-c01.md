92           |  Гпава 3

А что если использовать брокер, координирующий передачу данных между серви
сами? Вместо запроса сервисами данных друг у друга и создания сложной сети
межсервисной передачи данных каждый сервис будет взаимодействовать только
с брокером, как показано на рис. 3.9. Например, вместо того, чтобы другие сервисы
запрашивали у сервиса по управлению водителями прогнозируемое число водите
лей, все эти прогнозы может собирать брокер. Какой бы сервис ни запрашивал дан
ные от сервиса по управлению водителями, он может проверить у брокера послед
ний прогноз. Аналогично каждый раз, когда сервис оптимизации цен прогнозирует
повышение тарифа на следующую минуту, прогноз передается брокеру.

              Рис. 3.9. При наличии брокера сервисы взаимодействуют только с брокером
                     вместо взаимодействия со всеми остальными сервисами

Технически брокером может служить база данных. Каждый сервис может записы
вать данные в базу данных, а другие сервисы, которым эти данные нужны, могут
считывать их из этой базы данных. Однако, как отмечалось в разд. «Передача дан
ных через базы данных», чтение и запись из баз данных выполняются слишком
медленно— особенно это чувствительно для приложений со строгими требова
ниями по задержке. Поэтому вместо баз данных в качестве брокера мы используем
хранение данных, предоставляемых сервисами, в памяти (in-memory). При этом
в качестве способа хранения данных in-memory можно рассматривать именно пере
дачу данных в реальном времени.

Фрагмент данных, передаваемый в реальном времени, называется событием. По
этому архитектура, поддерживающая этот тип передачи, носит название управ
ляемой событиями. Такая архитектура лучше подходит для систем  с большим
объемом данных.

Два самых распространенных типа передачи в реальном времени: pub/sub (сокра
щение от publisher/subscriber, издатель-подписчик) и очередь сообщений. В pub/sub-
модели любой сервис способен публиковать в разных темах в режиме реального
времени, и любой сервис, подписавшийся на ту или иную тему, может читать все
сообщения в этой теме. Производящие данные сервисы не заботятся о том, какие
службы используют их данные. Pub/sub-решения часто регулируются политикой
хранения — данные хранятся в режиме реального времени в течение определенно
го периода (например, семь дней), после чего удаляются или перемещаются в по
стоянное хранилище — например, как у Amazon S3 (рис. 3.10).
