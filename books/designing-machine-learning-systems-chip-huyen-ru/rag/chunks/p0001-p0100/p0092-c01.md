Передача данных в режиме реального времени

Чтобы разобраться в мотивации передачи данных в режиме реального времени,
вернемся к примеру приложения для райдшеринга с тремя простыми сервисами:
управления водителем, управления поездками и оптимизации цен. В предыдущем
разделе мы обсудили, как сервис оптимизации цен запрашивает данные из сервисов
управления водителями и поездками, чтобы спрогнозировать оптимальную стои
мость поездки.

Теперь представьте, что сервису управления водителями также необходимо полу
чать информацию по количеству поездок из сервиса управления поездками, чтобы
знать, сколько водителей задействовать. Кроме того, он будет обращаться к сервису
оптимизации цен — чтобы использовать полученные данные для мотивации води
телей (например, предлагая двойную оплату за срочность поездки). Аналогичным
образом сервис управления поездками может запрашивать данные из двух осталь
ных сервисов. Если мы передаем данные через сервисы, как описано в предыдущем
разделе, каждый из этих сервисов должен отправлять запросы по схеме, показанной
на рис. 3.8.

                          Рис. 3.8. В управляемой запросами архитектуре
                каждый сервис должен посылать запросы к двум другим сервисам

Даже при наличии трех сервисов  передача данных  представляется сложной.
А представьте, что у вас их сотни, если не тысячи, подобно тому, что есть у круп
ных компаний. Межсервисная передача данных может привести к сбоям и стать
узким местом, замедлив работу вашей системы.

Управляемая запросами передача данных синхронная: целевой сервис должен при
нять запрос, чтобы произошел другой запрос. Если сервис оптимизации цен запра
шивает данные у сервиса управления водителями, который не работает, сервис
оптимизации цен будет повторно отправлять запросы до окончания времени ожи
дания. Если сервис оптимизации цен отключится до того, как получит ответ, этот
ответ потеряется. Таким образом, отключение одного сервиса может привести
к отключению всех остальных сервисов, использующих данные от него.
