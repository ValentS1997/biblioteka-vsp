Процесс обновления модели, как правило, ручной и разовый. Кто-то (обычно ин
женер по обработке данных) делает запрос в хранилище данных на получение но
вых данных. Какой-то другой специалист чистит эти новые данные, извлекает из
них признаки, переобучает модель с нуля как для старых, так и для новых данных,
и экспортирует обновленную модель в двоичный формат. Затем следующий испол
нитель берет эту информацию и развертывает из нее обновленную модель. Часто
код, инкапсулирующий данные, признаки и логику модели, в процессе переобуче
ния меняется. Но эти изменения не всегда удается воспроизвести в производстве,
что приводит к ошибкам, которые сложно отследить.

Если описанный здесь процесс кажется вам до боли знакомым, вы не одиноки. По
давляющее большинство компаний за пределами технологической отрасли — на
пример, любая компания, внедрившая ML менее трех лет назад и не имеющая
отдельной команды по разработке ML-платформы, — находится на этом этапе
(ML-платформы мы рассмотрим в разд. «ML-платформа» главы 10).

Этап 2: автоматизированное переобучение

Спустя несколько лет у вашей команды получилось внедрить модели для решения
большинства очевидных проблем. В производстве сейчас работают 5-10 моделей.
И у вас по-прежнему в приоритете разработка новых моделей, а не поддержка и
улучшение существующих. Но ручной способ обновления моделей, соответствую
щий предыдущему этапу, стал слишком большой проблемой, чтобы его игнориро
вать. Команда решает написать скрипт для автоматизации выполнения всех этапов
переобучения. Этот скрипт периодически запускается при использовании пакетно
го процесса типа Spark.

На этом этапе находится большинство компаний с развитой инфраструктурой. Кое-
кто из них проводит эксперименты для определения оптимальной частоты пере
обучения. Но для большинства компаний частота переобучения на этом этапе уста
навливается интуитивно — например, «кажется, раз в день будет нормально» или
«давайте начнем переобучать каждую ночь, когда простаивают вычисления».

При создании скриптов для автоматизации переобучения системы нужно учиты
вать, что для разных моделей системы могут потребоваться разные планы переобу
чения. Возьмем, например, рекомендательную систему, состоящую из двух моде
лей: для генерации эмбеддингов всех продуктов и для ранжирования релевантности
продукта с учетом запроса. Модель для эмбеддинга, вероятно, потребуется пере
обучать гораздо реже модели для ранжирования. Поскольку характеристики про
дуктов меняются не очень часто, вам может сойти с рук обновление модели для
эмбеддинга раз в неделю, в то время как модель для ранжирования надо будет об
новлять ежедневно (впрочем, если каждый день будет появляться много продуктов,
вероятно, модель для эмбеддинга придется обучать чаще).

Скрипт для автоматизации может стать еще сложнее при наличии между моделями
зависимостей. Например, поскольку модель ранжирования зависит от эмбеддингов,
при их изменении модель ранжирования также необходимо будет обновлять.
