## Symptom / problem framing

Стоит ли решать проблему ML? Машинное обучение извлекает сложные закономерности из данных и использует их для прогнозирования новых наблюдений; применять его просто из-за популярности технологии не следует. [p0026-c01; p0027-c01]

## Read-only checks

Это **проверочные вопросы**, не терминальные команды.

1. Является ли паттерн сложным для обычной программы? По книге почтовый индекс → штат решается таблицей поиска, а прогноз цены аренды на основе множества признаков — кандидат для ML. [p0027-c01]
2. Есть ли подходящие обучающие данные и основания ожидать сходных закономерностей в новых данных? [p0028-c01; p0029-c01]
3. Повторяется ли задача, достаточен ли масштаб, допустима ли цена ошибок, меняются ли паттерны? [p0029-c01; p0030-c01]
4. Не нарушает ли решение этику, нет ли более простого и дешёвого подхода? [p0030-c01; p0031-c01]
5. Согласованы ли продуктовые требования, ожидания инженеров, руководства и инфраструктуры? [p0035-c01; p0036-c01]
6. Рассмотрены ли latency (p50/p90/p95/p99), throughput, качество данных, объективность и объяснимость? [p0038-c01 — p0043-c01]

## Interpretation

- Простая устойчивая логика → обычное программное решение может быть лучше. [p0027-c01]
- Сложные обучаемые паттерны + данные + повторяемость + управляемый риск → ML обоснован для рассмотрения, но не гарантирует успех. [p0026-c01 — p0031-c01]
- Высокая точность offline не означает пригодность production: участники предъявляют разные требования, критичны задержки, данные, fairness и интерпретируемость. [p0035-c01 — p0043-c01]
- Отличие от SWE: помимо тестирования и версий кода нужны проверка/версии данных и контроль моделей. [p0043-c01; p0044-c01]
